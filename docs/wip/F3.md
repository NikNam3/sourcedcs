# F3: mission session (ADR 0086)

## What the briefing and the usage guide should say

- **Where it lives.** "Which mission are we in" is decided in `crc-sync/src/mission-session.js` and
  persisted to `state/mission-session.json`.
- **When a new session starts:**
  - on a DCS `mission_start`;
  - on a mission-load of a different mission (a different fingerprint);
  - when the mission clock steps back more than 5 min.
- **When it stays the same.** A reconnect, or a crc-sync restart onto the same mission.
- **Who uses it:**
  - the wind-derived runway (H22);
  - the metrics session number (H32);
  - the traffic-count `missionSession`;
  - H36's archiver, through `missionSession.onNewSession(fn)` (L24).
- **Operator-visible.** Restarting the same `.miz` now re-reads the wind for the active runway and
  starts a new metrics session. Before this, it did neither.
- **Behaviour change (fixed).** Once TWR has changed the runway, it now survives a gRPC reconnect or a
  crc-sync restart. Before, the next reconnect put the runway back to the wind end, because a TWR
  change overwrote the `missionKey` the guard compared against. The guard now reads its own
  `windDerivedSession` field on the field-state record, which also appears on the wire as a harmless
  extra field.

## Defaults taken

- **The `mission_start` roll happens at the following mission-load, not at the event itself.** This
  way the new session carries the load's fingerprint and theater, and the H22 wind derivation never
  runs on the previous mission's airports. Events in the few seconds between the two count toward
  the old session.
- **Clock observation happens only on `game-time`.** Server.js calls `observeClock()` after
  `missionClock.sample()`. `current()` never reads the clock. The reason: inside the mission-load
  handler, before `setTheatre`, the clock can carry the old theater's offset.
- **A clock-step roll followed within 2 min (wall) by a load of a different fingerprint gives one
  session.** The load names the session instead of opening a second one. This covers a reconnect
  where the first clock poll lands before the mission data.
- **A wind call made while a runway change is open counts as "applied" for that session.**
- **No migration.**
  - Existing `efsp-metrics.json` and `efsp-traffic-count.jsonl` can hold session numbers from L5's
    old counter, and the new counter starts again at 1. **Clear those two files, or accept repeated
    numbers, when F3 merges on a machine with state.**
  - A persisted field state has no `windDerivedSession`, so its wind is re-applied once.

## Walks not done

- **Not checked against live DCS: whether DCS-gRPC sends `mission_start` to a stream that connects
  after the mission has already started.** If it does, every crc-sync restart would roll the session.
  Check it once: restart crc-sync against a running server and watch `[mission-session]` in the log.
- **A real `.miz` restart through DCS was not walked.**
- **A smoke boot on port 3986** with a temp `CRCSYNC_STATE_DIR` did reach the configured DCS-gRPC
  host. It wrote session 1 with the Syria fingerprint, and the field state derived 05 from the wind.
  The :3000 instance was not touched.

## Findings for other lanes

- **L24 (H36 archiver):**
  - Subscribe with `missionSession.onNewSession((session, previous) => …)`.
  - `session.reason` is one of `MISSION_START`, `MISSION_CHANGED` or `CLOCK_STEP_BACK`.
  - The instance is the `missionSession` const in `server.js`, declared in the "F3 mission session"
    block.
- **L5 / L15:** `EfspMetrics` takes `missionSession`. `noteMissionLoad` is gone from both the store
  and the instrumentation facade.
- **L1 / L1b:**
  - `missionKeyOf` is gone from `field-state.js`; it is now `missionFingerprint` in
    `mission-session.js`.
  - `setActiveRunwayFromWind` takes `{ missionSession }` (a number) and can return `skipped: true`.
  - The server.js wind block is now the `deriveActiveRunwaysFromWind(missionData)` function.
- **grpc-client.js:** one line was added, `this.emit('mission-start')` in the `mission_start`
  branch, before the fetch.
