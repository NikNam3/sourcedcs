## Defaults taken (P2)

1. **"Detected airborne"** = CORRELATED contact, aircraft category, ground speed >= 60 kt, >= 200 ft above the
   nearest airfield when within its 5 km footprint (speed alone beyond it), held 5 s. ON_GROUND is
   `checkOnGround`. The band between is UNKNOWN. All four numbers are in the tuning file.
2. **Only CORRELATED counts**, never PROVISIONAL.
3. **The chip exists only for a DEPARTURE on the ground side** (PUSHBACK, TAXI, RUNWAY_QUEUE, LUAW) and
   offers `SetState` to `DEPARTED`. Not `InvokeNla`: from TAXI the NLA would be "to runway queue", and the
   suggestion is about what was observed. The arrival-side contradiction (LANDED expected, contact still
   airborne, or the reverse) is staleness only, with no chip: §10.3 permits "detected airborne".
4. **Staleness threshold 120 s** after the 5 s hold (so the chip is the prompt, the badge is what is left
   when it was ignored). Any gap in the contradiction ends the episode; the next is a new occurrence and a
   new log line. Logged once per episode, on the mission clock.
5. **The chip and the badge are quiet indicators** (`_litIndicator` cases, like `ar`/`trk`), not alert chips:
   they add neither the Strip's attention styling nor a reason line (the title carries the sentence). That
   keeps the l4-badges height budget and "low-severity".
6. **A hint written against a state the Strip has since left is not drawn** (`surveillanceHintsForStrip`
   compares `stripState`), so the chip never survives its own acceptance for the round trip.
7. **The chip is a click target only for a Position the controller holds** that owns the Strip; for anyone
   else it is information. It goes through the board-wide `_swallowRepeatAdvance` guard like the NLA button.
8. **Takeoff stamp**: DEPARTURE only (not MISSION `AIRBORNE`); stamped on entering DEPARTED or HANDED_OFF from
   a non-airborne state (not from DROPPED); first stamp wins; cleared when the Strip is taken back to a
   pre-airborne state (Undo, `SetState`); kept through a Drop. It bumps `fdr.rev` but not `fdr.updatedAt`
   (the AMENDMENT_INSIDE_30MIN obligation reads that as "the plan was amended").
9. **The misbinding memory is by track id** and is dropped when the contact leaves the picture or on a mission
   reload.

## Walks done and not done

- Done: a lingering aircraft does not bind a new flight with the same callsign, and the new flight binds its
  own contact when it appears; an explicit bind still works (reconciler tests).
- Done: takeoff chain through the real board: NLA, Undo, SetState, a typed time, clearing it, a hand-off, a
  Drop (`efsp-scenario-time-chains.test.mjs` T3).
- Done: the e2e `l19-surveillance-hints.spec.js` (lane 1): drawn, moves nothing, one click, takeoff stamped,
  and the quiet badge.
- **Not done**: a live DCS run. The harness has no contact, so the real chain
  (track -> phase -> hint -> `efsp-alerts` -> chip) is unit-tested in pieces and e2e-tested from the wire
  slice onward, not end to end. Worth one walk by the integrator with a real mission: taxi a jet, line up,
  take off without pressing Airborne, and watch the chip appear 5 s after rotation.
- **Not done**: a SetState to DEPARTED is refused while the runway is suspended (`_setStateRunwayRefusal`,
  H19). If TWR forgot Airborne and the runway has since gone into works, the chip's click is refused with
  the existing runway reason. That is the correct rule for a clearance and a strange one for a recorded fact;
  the controller's other route (Drop) still works. Owner: field-state (L1b).

## Soak (acceptance: misbinding 0)

- `npm run soak:smoke`: misbinding 0. `npm run soak -- --minutes 240` (seed 1, 151 flights, callsigns reused):
  PASS, misbinding 0.
- **I could not reproduce S-L27's `LINGERING_TRACK` on this base.** 20 seeds x 240 min (and seeds 2-7 x 480 min)
  on the unfixed `d9e9176` reconciler show no `LINGERING_TRACK` at all. What the soak does show are 1-3
  `FAULT_wrongSquawk` / `FAULT_noTransponder+sharedCallsign` per affected run (seeds 2, 5, 10, 16), identical
  before and after the change. Those are the injected faults: a pilot squawking another flight's code binds
  that flight, which is the beacon rung working as designed. They are not the callsign misbinding and the
  fix does not claim them. The fixed code has the same count as the base on every seed (seed 2 at 480 min
  differs only because the changed correlation outcomes changed the driver's RNG sequence).
- So the fix is proven by a deterministic unit test, not by the soak. If the integrator's 240-min run still
  shows a `LINGERING_TRACK`, the likely cause is the known limit: a lingering aircraft DCS **re-minted under a
  new track id** is a new contact to the reconciler, and the memory is by id. Handling that needs a callsign
  memory with a position test, which I did not build without a case showing the cost (the standing
  "defer, then harden what exists" rule).
