# F2 — magnetic variation, convergence, per-theater transition altitude (ADR 0085)

## What landed

- `crc-sync/src/magnetic.js`: WMM2025 (`data/wmm/WMM2025.COF`, verbatim from NCEI) evaluated at a
  position and the mission date. It also has a per-theater override (`magneticVariation: {fixedDeg} |
  {offsetDeg}`), `convergenceAt`, and the true/magnetic conversions. The module is tested against both
  NCEI test tables.
- `crc-sync/src/theater-context.js`: the server's single conversion point. It provides `variationAt`,
  `convergenceAt`, `trueToMagnetic`, `magneticToTrue`, `gridToMagnetic` and `transitionAltFt`, and it
  builds the `theater` wire message.
- `config/theaters.json`: new fields `transitionAltFt` (Syria 10000) and `tmCentralMeridianDeg`.
- `theater-settings.js`, its config, its `theater-settings` / `theaterSettingsSet` messages and its test
  are **deleted**.
- `GET /api/magnetic/to-true`, proxied by crc-desktop's local server.
- Client: `app/public/js/magnetic.js` provides `toMagneticDisplay`, `magneticText`,
  `magneticVariationAt`, `gridConvergenceDeg` and `requestTrueFromMagnetic`. `hdgCorrection` is gone,
  and so is the APRT "Theater" input section, which is now a read-only TA and variation line.

## For wave-2 lanes (S-W3c)

- Show a TRUE bearing with `magneticText(trueDeg, lat, lon)` (`"045"` / `"---"`) or
  `toMagneticDisplay(trueDeg, lat, lon)` (a number or null). Never apply a variation or convergence
  yourself.
- A value the controller TYPES as magnetic is converted by crc-sync. On the server, call
  `theaterContext.magneticToTrue(deg, lat, lon)`. The client has `requestTrueFromMagnetic()`, but only for
  local drawing. Anything stored goes to the server as typed, and the server converts it.
- A DCS grid heading/course (`track.course`, `orientation.heading`) goes to magnetic with
  `theaterContext.gridToMagnetic(deg, lat, lon)`. For L4/L17's injected inputs, use
  `theaterContext.convergenceAt(lat, lon)` and `theaterContext.variationAt(lat, lon)`.
- The transition altitude is `theaterContext.transitionAltFt()` on the server and
  `settings.transitionAltFt` on the client (read-only, set from the `theater` message).

## Defaults taken

- The variation travels in **its own `theater` message** (a grid, not a number), not on `game-time`.
  The task allowed either. Reason: the value depends on position, and the grid is a few hundred numbers
  that change once per mission day.
- The client converts typed runway courses (topbar approach vector, APRT centreline) by **asking
  crc-sync** over HTTP. It does not use its own grid, which would be a client-side magnetic-to-true
  conversion.
- Non-Syria `transitionAltFt` = **18000 `[SOURCE-DEFINED]`**, which is today's value everywhere.
- For mission dates outside 2025–2030, WMM2025 is **extrapolated linearly** and flagged
  (`modelDateValid: false`). No older WMM epochs were added.
- The mission date is snapped to the UTC day. The model is re-evaluated on a new day, or when the clock
  switches from WALL to MISSION.
- The grid is 1°, covering the airfields' bounding box plus 3°, clamped at the edge. Its values are
  rounded to 0.01°.
- Where the variation is unknown (no mission, no grid), displays show `---` rather than a true value.
- The topbar approach course input was already drawn as if it were TRUE (a pre-existing bug). It is now
  treated as magnetic.

## Findings for other lanes / the supervisor

1. **Conformance heading check mixes frames** (`crc-sync/src/efsp/conformance.js:59,65`). It compares
   the typed magnetic HDG with `track.course`, which is DCS **grid**, and reports `actual` in grid. The
   client prints that value as if it were magnetic (`geojson.js` `HDG…` tag, the track panel alert
   line). Over Syria the two frames differ by about 7°, so a pilot flying the assigned heading exactly
   can trip the 10°/persist alert. Fix, in an EFSP lane: feed
   `theaterContext.gridToMagnetic(track.course, track.lat, track.lon)` into `evaluateConformance`
   (inject it, as `transitionAltFt` is injected today).
2. **Wind direction** in the airport weather popup and the ATIS text is DCS's (true). Real ATIS winds are
   magnetic. H15 does not list wind. Needs the human's decision.
3. **Six theaters have no central meridian** (TheChannel, MarianaIslandsWWII, Kola, Afghanistan, Iraq,
   GermanyCW), so their grid headings cannot be converted. `tools/miztoyaml/projection.py` needs the same
   additions, and a test keeps the two tables equal.
4. **Stale comments inside `src/efsp/`** still name `theater-settings.js` (`efsp-ws.js:6`,
   `facility-config.js:5,42`, `mutation-log.js:5,41`). They are comments only, and I left them because
   F2 does not touch EFSP.
5. ADR 0048's table and ADR 0079's "`gameTimeOffset` is gone" paragraph describe `theater-settings.json`,
   which no longer exists. This belongs in the next errata ADR.
6. L1's wind-to-active-runway logic in `server.js` compares runway headings with the wind. I did not
   check which frame it uses (not in scope). Worth a look alongside finding 2.

## Follow-up after the merge (S-F2 finding 1, H76)

- **Conformance** (`src/efsp/conformance.js`): `ConformanceMonitor` takes an injected
  `gridToMagnetic(deg, lat, lon)`, which `server.js` wires to `theaterContext.gridToMagnetic`.
  - The HDG check compares magnetic with magnetic, and `actual` is reported in magnetic.
  - When the answer is unknown (no projection, no variation, or no converter injected), heading is not
    checked at all.
  - The soak host and the mission-clock test inject the identity function, because their courses are
    synthetic.
- **Wind (H76)**: `/api/apt-weather` sends `windFromMagnetic` and `windFromTrue`, computed by
  `theaterContext.windFrom()` at the airfield. It no longer sends the raw `windFrom`.
  - The APRT ref card and the weather popup show `NNN°M` (the ref card's tooltip shows the true value).
  - The ATIS text uses the magnetic value, or says "Wind not available." when the variation is unknown.
  - No client surface shows METAR-style text today. `windFromTrue` is on the wire for one when it comes.

## L1 wind-to-runway check (S-L1c): reported, not changed

`deriveActiveRunwaysFromWind` (`server.js`) → `activeEndIntoWind` (`efsp/field-state.js:290`) compares
`windFromTrue: w.windFrom` with each end's `endHeadingsTrue`. Both are labelled TRUE, so the comparison
is consistent with itself, and the magnetic end number is never used. Nothing is clearly wrong. Two
doubts sit upstream, in `grpc-client.js:764`, `windFrom = heading·180/π + 270`:
1. **The +270 is not explained.** `protos/dcs/atmosphere/v0/atmosphere.proto` says `heading` is
   already "the heading the wind is coming from". With that reading, the formula yields
   `from + 270 = from − 90`. It may have been fitted by observation, because DCS-gRPC's Lua could
   return the vector angle rather than what the proto says. This needs a live check against the mission
   editor's wind before anything changes.
2. **The DCS wind vector lives in DCS's map (grid) frame**, like unit headings (L4). That would make the
   value grid rather than true, differing by the convergence (about −2° at Incirlik). This is immaterial
   for choosing a runway by headwind, and for H76's magnetic readout it is an error of the same size. I
   followed S-L1c (treated as true).
