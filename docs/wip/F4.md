# F4 — typed time Blocks store epoch ms (S-R2-17)

Bugfix between waves. No ADR.

## What changed

- **Server (`crc-sync/src/efsp/fdr-store.js`).** One table, `TYPED_TIME_LABELS`, and one function,
  `normalizeTypedTime(path, value, nowMs)`, are now the only rule for a typed time. The table lists every
  `…TimeUtc` path a controller writes, plus the two MTR times (which L2 already handled and which now go
  through the same function):
  - `filed.proposedDepartureTimeUtc` (Block 6, DEPARTURE)
  - `filed.estimatedArrivalTimeUtc` (Block 6, ARRIVAL)
  - `assigned.releaseTimeUtc` (14), `assigned.edctTimeUtc` (14B), `assigned.callForReleaseTimeUtc` (14C),
    `assigned.voidTimeUtc` (14D)
  - `assigned.movementAreaEntryTimeUtc` (16), `assigned.taxiTimeUtc` (17), `assigned.takeoffTimeUtc` (18)
  - `military.mtr.entryTimeUtc` (9G-TIME), `military.mtr.exitEstimateUtc` (9H-TIME)
- The rule: a finite number is taken as epoch ms already. An empty value clears to null. A string goes
  through `zulu-time.js`'s `resolveZuluHhmm` against the FdrStore's injected mission clock (H11): the
  nearest occurrence within ±12 h (S-L2b). Anything else is refused as `VALIDATION_ERROR`,
  `"<label> must be a UTC time as HHMM, e.g. 1432"` (the same wording as L2's MTR refusal), with no
  partial write and no rev bump.
- `setField` applies it before the write, so `voidDeadlineUtc` and the EDCT/CFR windows derive from a
  number. `createFdr` applies it to the two filed times in the seed too, before a beacon code is allocated.
- **Client (`crc-desktop/app/public/js/panels/efsp/strip-template.js`).** `ZULU_HHMM_BLOCKS` now holds
  `6`, `14`, `14B`, `14C`, `14D`, `16`, `17` and `18` beside the MTR times, so they render and open for
  editing as `1432`. Each of these ids is a `…Utc` FDR path on every role map that has it (a test pins that).
- **Tests.** `crc-sync/tests/efsp-scenario-typed-times.test.mjs` (new, 5 scenarios, all fail without the
  fix): a typed void time expires at +30 min (NLA inhibited and a `VOID_TIME_EXPIRED` obligation);
  a typed release time holds the HELD NLA until it is reached, then the flight pushes; typed EDCT/CFR times
  derive their windows; a typo (`1472`) is refused with the FDR unchanged, and empty clears; Blocks 6/16/17/18
  and a cross-midnight ETA via `createFdr`. The client test for `ZULU_HHMM_BLOCKS` was updated and one added.

## Left alone (and who owns them)

- **M6/M7, the vul window** (`mission.vulWindowStartUtc`/`EndUtc`). Still stored as typed when written
  through a MISSION Strip's cell, and still rendered as the raw number. The ATO path (L3's
  `ato-mapping.js`) already hands `createFdr` epoch ms. Owner: **L14/L16**. When they fix it, add the two
  paths to `TYPED_TIME_LABELS` (but decide first whether ±12 h is right for a window whose end may be more
  than 12 h from now) and `M6`/`M7` to `ZULU_HHMM_BLOCKS`. Not a `…TimeUtc` path, so out of F4's scope.
- **Existing persisted FDRs** that already hold a string time in `state/` are not migrated (no backwards
  compatibility, lane rule 5). A string left there still compares as before until the Block is retyped.
- Nothing else found storing a typed time as a string: airspace schedules (`fromUtc`/`toUtc`) and the
  carrier's Charlie time already refuse anything but epoch ms, and the other times are system-stamped.

## For L16 (fallback chains on top of this)

- Keep `normalizeTypedTime` the single rule. A fallback chain should hand `setField`/`createFdr` either
  epoch ms or the controller's typed string, never a pre-formatted date string.
- The client mirror stays `ZULU_HHMM_BLOCKS` + `formatZuluHhmm`.

## Defaults taken

- The two filed times in a `createFdr` seed are validated the same way as `setField` (refused, not
  silently dropped). Only the scenario helpers and the client's CreateStrip (which sends `null`) seed them today.
- Refusal wording follows L2's MTR message, lower-case label first (e.g. `void time must be a UTC time as HHMM, e.g. 1432`).

## Walks not done

- No browser walk (no E2E lane assigned). The e2e spec `obligation-retract.spec.js` writes 14D as a number
  and is unaffected.

## For the usage guide

- Release, void, EDCT, call-for-release, proposed departure / ETA, movement, taxi and takeoff times are
  typed as `1432` or `14:32Z`, in-game Zulu, dated by the mission. Anything else is refused at the cell.
