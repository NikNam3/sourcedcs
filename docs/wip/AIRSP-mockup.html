AIRSP: the airspaces panel, for approval

Mockup for the human's approval before any product code (H49). It shows the AIRSPACE dock panel with editing added: the list, the edit form (valid, then with validation errors), the conflict state when two controllers edit, the audit trail, and a refused delete. It uses the real Layout C tokens and field grid (ADR 0056/0057) and the colour rule of ADR 0056/0058: everything is grey, and orange-red appears only when something is wrong. Dark is today's panel; the light variant is new (ADR 0056 left it as a follow-up). All names, numbers and times are invented sample data. The design is in docs/wip/AIRSP.md; the open questions there are marked Q1 to Q11.

The editor opens inline in the card, same field grid, no modal. One filled blue button (Save). A changed field gets a small dot on its label and the old value in grey beneath it, not a colour. ID is fixed after create; USING POSITION is read-only in v1 because it creates or removes a range Position that is derived at load (Q3). The note is grey information, not amber: it is not a fault. There is no draft on the server and no future "effective at" time; the form is the draft (Q4). Phase 2: the same validator runs client-side as you type and again on the server.

4 problems to fix before Save: NAME, CTRL POSITION, WORK FREQ, ALT UPPER.

Errors are --efsp-bad (orange-red, kept apart from the Attention red), on the field and summarised beside Save. Save is disabled while anything is invalid and says why. These are the server's hard rules: name present and unique, a real Position at the named Facility, 30 to 400 MHz, whole feet 0 to 100000 with upper above lower (the first three are new, the last two are today's). A shared frequency is a grey note, never a refusal. Changing TYPE changes nothing else: it is a label only (D14, ADR 0038).

Conflict is decided per field, from the airspace's edit history after the revision you opened. Two controllers changing different fields never collide, and an unrelated state change (someone approving activation) never makes an edit stale. The same field changed by both is refused with both values shown, so a frequency is never silently reverted. Orange-red marks the one clashing row; the rest is grey. The server logs the refusal (ADR 0083). Same-field last-writer-wins was rejected on purpose (AIRSP.md section 7).

Accepted changes only, newest first, in mission time (Zulu). It joins the airspace's state history with its definition edits. Refused attempts, with the reason, are in the Mutation log (the audit trail of record), not here (Q7). The panel keeps the last 50 edits.

One edit that changes several fields is one entry with a change list (ADR 0083: one outcome, one entry). Every row names the Position and the controller. Times come from the mission clock, never the wall clock (H11, ADR 0079). Entries are neutral: nothing here is wrong.

The server refuses with a reason that lists the blockers (VALIDATION_ERROR, so a range booking or a flight on the block's frequency is never orphaned); the panel shows the same list from the data it already has, so the button is disabled with the reason instead of failing. When nothing blocks, Delete is a confirm step and removes the airspace from every client with one delta. Old Strips and log lines keep the id and show it bare. Q6: hard delete versus retire.

What this does not show

  • The create form is the edit form with ID editable and an empty definition (the "+ New airspace" button, shown only to a Position that may create).
  • No authentication UI (out of scope). A session holding no Position sees the list and every Edit is the dashed outline.
  • No geometry fields and no scheduled "effective at" time (Q9, Q4).
  • Strip-side marking of a flight left on an old frequency is a follow-up (AIRSP.md F2); v1 lists those flights in the edit note and the History row.
