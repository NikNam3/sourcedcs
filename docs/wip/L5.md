# L5: WP8 metrics, traffic count and Mutation-log retention: working notes

Branch `lane/L5-metrics`, ADR `0065`. This covers the server only. There is no client code and no
e2e lane.

## Defaults taken (P2)

The briefing questions (§10), with the ruling or default that answers each:

- **Q1: where the tap goes.** Default: `createEfspInstrumentation` reassigns `efsp.handleMessage`
  and `efsp.onDisconnect` from server.js. `index.js` is untouched.
- **Q2: refusals in the log.** Yes, from the tap. The rule is every refused `efsp-mutation`, plus
  `NOT_HOLDING_POSITION` on any `…-mutation` type (S-R2-5). Each entry adds `type` beside the
  fields the briefing lists.
- **Q3: the unit.** One record per DROPPED Strip per Facility. `flights` is the headline and
  `aircraft` sits beside it. H34 confirms a formation is one operation.
- **Q4: the countability thresholds.** Default. OVERFLIGHT's unreachable exclusion is named
  `NEVER_TRANSITED`.
- **Q5: the home airports.** Default: `config/efsp-instrumentation.json`.
- **Q6: the hour.** Default: `droppedAt`, on the mission clock.
- **Q7: retention.** Default: 30 / 30 / 400 days, on the wall clock (a storage lifetime, per H11's
  line).
- **Q8: persistence.** Yes for the hour buckets, the session list and `sources`. The rolling
  last-hour minute buckets and the per-connection records are memory only.
- **Q9: transfers.** Default, plus S-R2-5: an owner's press on an inhibited NLA is counted as
  `inhibitedPress`, not as an attempt.
- **Q10: `recordMet`.** Not mine. The value is read verbatim. After L7, `met` is non-zero only for
  ADVANCE_FORWARDING and VOID_TIME_EXPIRED, so the dashboard should show counts, not rates.
- **Q11: alert scramble.** Default: a latch plus `noteFdr`.
- **Q12: transport.** Default: WS for L15, and HTTP GETs for reads.
- **Q13: keying by `positionId`.** Default, guarded by a uniqueness test.

Defaults I took myself, not covered by any ruling:

- **Mutation-log rotation uses the wall clock.** The constructor option is `wallNow`, not the
  briefing's `now`, so it can't be mistaken for the mission clock.
- **`hours` is optional.** With no `hours`, the metrics body covers the whole current metrics
  session, capped at 720 hours (S-R2-4's default view). `hours=N` means the last N hours of the
  session.
- **The traffic window.** `from`/`to` omitted or null means the last 24 h of mission time. A
  literal `0` means epoch 0. It is not a placeholder, although the briefing's example uses it as one.
- **A mission load that continues the same mission is not a new session.** A crc-sync restart or a
  gRPC reconnect keeps the session when the theater is the same and the mission clock runs on
  within 5 min. The first load adopts the "before any mission" session rather than leaving a stub.
  A mission clock that falls back to wall time and then returns is not a new session. This whole
  seam goes when F3's `mission-session.js` lands (S-R2-2).
- **An unreadable metrics file is renamed to `.corrupt-<wallms>`** and the service starts empty,
  so the next write can't destroy the evidence.

## What the usage guide should say

- There is a metrics endpoint, `GET /api/efsp/metrics`, with optional `?hours=1..720` and
  `?missionSession=N`, and a traffic count endpoint, `GET /api/efsp/traffic-count`, with optional
  `facilityId`, `from`, `to` (mission-time epoch ms, `to` exclusive), `detail=1` and
  `missionSession`. Both need an authenticated user. Nothing in either body names a controller.
- Retention lives in `config/efsp-instrumentation.json`, or in a `state/` copy of it. Restart to
  apply a change.
- The Mutation log is `state/efsp-mutations.jsonl` plus day segments
  `efsp-mutations.YYYY-MM-DD[.n].jsonl`, each named by its newest entry. Reading the whole audit
  trail means reading the segments in day order, then the live file (`MutationLog.readAll()`).
- `ok:false` log entries are refusals. `source:'wire'` means the tap wrote the entry.
- How to read the count:
  - Local + transient + unknown = flights.
  - Formation, SUA and scramble are overlapping subsets, not further partitions.
  - `excludedByReason` explains the drops that aren't traffic.
  - CENTER and TACTICAL show locality `UNKNOWN` by design, because they have no home airport.

## What the briefing should say

- `positionStore.observersOf()` returns `{controllerId, controllerName, since}` records, not ids.
  L5's briefing said `observersOf(p).includes(controllerId)`, which is wrong. Fixed here, and caught
  by a test.
- `airspace-store.apply()` returns STALE_REV and NOT_FOUND **before** `_recordAudit`, so those
  airspace refusals are not logged either. (The briefing said airspace logs refusals. It logs only
  the ones that reach the op switch.)
- Scenario tip: nearly every DEPARTURE NLA is transfer-shaped (OPS→CD, CD→GND, …). The only
  non-transfer NLA on a DEPARTURE is the terminal Drop.

## For the integrator (action items)

- **L15 needs one proxy line per route in crc-desktop's local server** (`crc-desktop/app/server.js`,
  the `:101–112` pattern): `/api/efsp/metrics` and `/api/efsp/traffic-count`. That's L15's edit.
- **The contract for L15 (ADR 0072)** is in `tests/efsp-metrics-contract.test.mjs`. It differs from
  the L5 briefing's §5.6 in these ways:
  1. There is no `rejectedMutations.sessions` (H35, S-R2-4).
  2. New top-level keys: `missionSession {seq, theatre, startedAt, lastAt, current}`,
     `missionSessions[]`, and `lastHour {from, to, metrics}`. `lastHour.metrics` has the same shape
     as `metrics`, with empty `byHour` series.
  3. Every `byHour` entry is an object that carries `missionSession`. `systemReassigned.byHour`
     values are now `{missionSession, total}`, not numbers.
  4. `transfers.inhibitedPress` is new.
  5. `windowHours` defaults to the whole session, not 24.
  6. The `efsp-metrics` WS answer carries `ok`. On a bad query it is
     `{ok:false, reason:'VALIDATION_ERROR', detail}` with `requestId` echoed.
  7. A client event's `at` is ignored; the server stamps events on receipt (S-R2-3).
  8. A duplicate `reportId` is acked `{ok:true, accepted:0, rejected:[], duplicate:true}`.
  9. The traffic body adds `missionSession` (the filter echoed), and `records` (with `detail=1`)
     have `actorId` stripped.
  10. `missionSession=N` returns 404 `NOT_FOUND` for an unknown session.
- **L19's hook.** Call `efspInstrumentation.metrics.declareSource('staleness')` once where the
  detector is wired, then call
  `efspInstrumentation.metrics.recordStaleness({ at, facilityId, positionId, stripId, fdrId, stripState, trackState, durationMs })`
  once per detection. An unknown source name throws.
- **L13 and `alertStatus`.** Route `alertStatus` writes through a logged Strip Mutation, or call
  `efspInstrumentation.trafficCount.noteFdr(fdrId)` after `fdrStore.setMilitary(...)`. Until then,
  a SCRAMBLE that is set and reset between two logged Mutations of the Strip is missed.
- **L24 (archiving, S-R2-13).** Archive only after the drop's count record exists. That is
  synchronous in `onRecord`, so it is always true for a live drop. A backfill of an archived FDR
  gets locality `UNKNOWN`/`ARCHIVED`. A backfill whose Strip is gone from every Board gets
  `facilityId: 'UNKNOWN'`, because the log entry carries no Facility.
- **F3 (S-R2-2).** Replace `EfspMetrics._mission()` with `mission-session.js`. `TrafficCount`
  already takes `missionSessionOf` injected.
- **server.js.** One self-contained block, placed between `/api/apt-weather` and `// ── Stale
  reaper`. It includes its own `require`, a second `grpcClient.on('mission-load')` listener, two

## Audit gaps found (not fixed; outside L5's files)

1. **Peer-side replica writes are unlogged.** `receiveCoordinationProposal`, `receive*Response` and
   the TOFI receive paths mutate the peer Board without a log entry.
2. **Log entries carry no `facilityId` and no FDR.** The traffic count has to look the Facility up
   on the Boards (T6), and backfill can't recover it once a Strip is archived. Wire refusals written
   by the tap do carry `facilityId`.
3. **`efsp-ws.js` does not pass `clientMutationId` to `airspaceStore.apply()`**, so airspace
   entries, success and refusal alike, have `clientMutationId: undefined`. Check the correlation
   and MARSA paths for the same gap.
4. **Some refusals remain unlogged:**
   - airspace STALE_REV and NOT_FOUND (returned before `_recordAudit`);
   - `efsp-ws.js`'s class-based PERMISSION_DENIED on the airspace, correlation and MARSA paths;
   - "no store" VALIDATION_ERRORs.
   The tap cannot tell these apart from store-logged refusals by reason alone.
5. **The SUA latch in reconciliation.** An `ApproveAirspaceEntry` older than the log's retention,
   on a Strip dropped inside it, would reconcile as `mismatched`. That needs a Strip life longer
   than 30 days, so it's theoretical.
