## Code as found (§4)

- **V1.** L6's numbers reproduce at the base (`baseline-*.txt`, identical digests). `driver.js` generates **no
  field-state traffic**, so `efsp-field-state-mutation` was not added to the cmid list or to `_checkBroadcast`.
- **V2.** Every `_touch` is followed by a `rev` bump. Before this lane the Mutation broadcast carried only
  `result.strip`, so `_rebalanceRack`'s touches were never carried. `reassignPositionStrips` is carried by
  `_handleSetPositions`' full re-send. The peer `receive…` touches were carried only through `result.peerStrip`, which
  missed a rebalance of the peer's Rack. A replayed success used to re-broadcast the cached live Strip, which was harmless
  noise. **T2:** in the current ops every refusal returns before its first touch (transfer and create validate before
  `_resolveOrderKey`). Only the `applyMutation` catch-all could leave touches, and if it does they are broadcast.
- **V3.** There are 11 `_resolveOrderKey`/`_appendOrderKey` sites. Two of them (`receiveCoordinationProposal`,
  `receiveTofiProposal`) place Strips on the **peer** Board.
- **V4.** The Board delta is sent from these places, and every one now carries `boardEpoch`: the `_handleMutation`
  broadcast and `peerBroadcast`, the MARSA FDR-only delta, `_handleSetPositions`, the `_handleResync` delta, and
  `ws-hub.js` `broadcastEfspBoardDelta` (the NLA monitor, and L24's archiver). L1's wind hunk sends a field-state
  delta and goes through `nlaStatusMonitor.tick()`, so `server.js` needed no change. `efsp-heartbeat` carries
  `boardSeq`. It is not a delta, and it has no epoch.
- **V5.** Confirmed: `_handleSetPositions` never persisted. It now persists when it reassigned anything.
- **V6.** `_appliedMutations` was read only by `applyMutation` in `src/`, and by name in the harness. Every name the
  harness wraps is kept.
- **V7.** Confirmed: nothing in the client calls `sendEfspResync`. The tests that send resync were updated to add
  the epoch. Their assertions are unchanged.
- **V8.** `ws-hub-wire-strictness.test.mjs` pins no EFSP keys.
- **V9.** The metrics tap sees `handleMessage` only, never log entries, so a marker is never counted as a Mutation or
  a drop. The traffic count is handled (see below).
- **V10.** `applyEfspMutationAck` applies `ack.strip` whenever it is present, and `applyEfspDelta` ignores unknown
  keys. **No client change and no browser.**
- **V11.** The allocator snapshot was `[[code, fdrId]]` under `fdr.codes`. The cursor goes beside it as

## Defaults taken (P2)

- Q1 (a), confirmed by S-W3d: L27 rewrote the cache. Q2 (a), Q3 (a), Q4 (a), Q5 (a) (no client change), Q6 (a) (no
  rebalance audit line).
- The cursor is persisted as a separate key, `fdr.codeCursor`, rather than nesting `{codes, cursor}` under
  `fdr.codes`. This keeps the one-line edits and leaves every reader of `codes` untouched.
- `restore()` loads **every** replay record in the snapshot, without filtering by age at restore time. The snapshot is
  already cut to 10 minutes. Filtering again at boot would make the boot reconcile mark persisted lines after a long
  outage.
- The boot reconcile reads from `persistedWallAt − 60 s` and marks any successful, cmid-bearing, non-system Board line
  whose cmid no Board holds. It does not use the briefing's `wallAt > persistedWallAt` test, because under the soak's
  virtual clock the two can be equal. Every persisted Mutation is in the window anyway.
- **Traffic count, beyond "one branch each".** The retried drop carries the same clientMutationId and so gets the same
  `countId` as the voided one. To make it count again, `liveCountRecords` and `_index` now read COUNT/VOID in file
  order, so a COUNT written after a VOID revives it. `reconcile({ backfill })` replays the markers, because they are
  written before the count subscribes. A marker voids only a COUNT written before it.
- **Harness, beyond §5's list.** `driver.js` skips M8's broadcast check for a replay, which now broadcasts nothing by
  design. `logLinesFor` (R2's classifier) applies the marker rule, as the ledger does. No detector was weakened.
  `selfcheck` passes.
- Two existing tests, `replaying … does not double-apply` and `idempotent replay works even for a Mutation that
  originally failed`, asserted `deepEqual(r2, r1)`. Now that a replay is a rebuilt result they assert the outcome,
  `replayed: true` and the current Strip.
- The table-driven epoch test and the four F13 tests are in `efsp-ws-replay.test.mjs` (createEfsp with temp paths),
  not in `efsp-ws.test.mjs`. `efsp-ws.test.mjs`'s ctx has no MARSA store, and calling `createEfsp` there would write
  the real state paths.
- The persist change (S-L24) is compact JSON plus **dirty-only** in the sense "skip a write whose body is unchanged
  since the last successful write". It stays synchronous before the ack, and there is no debounce and no batching:
  either would let an acknowledged change die with the process and break F5.

## What the usage guide should say

- §5.2: "A retried Mutation is answered with its original outcome and the record as it is now. This holds on every
  path, and for 10 minutes across a crc-sync restart (Board ops only)."
- §5.6: "A resync is served as a delta only within one Board lifetime: send back the `boardEpoch` from the last
  snapshot, delta or ack. Without it you get a snapshot."
- Ops: "`efsp-mutations.jsonl` can contain `op: 'NotPersisted'` lines, written at boot. Each one voids the earlier
  line with the same clientMutationId, which never took effect because crc-sync died before saving it."

## What the briefing should say

- §3.10 / §5: every `efsp-board-delta` carries `boardEpoch`, and a Mutation's broadcast carries every Strip it
  touched, not only the addressed one.
- Beacon codes rotate. A released code comes back only after the whole pool has cycled.

  Add `session` as the second parameter, and put the OWNED-session early return between step 1 and step 2.

  before its `apply`, plus one `_rememberOutcome(...)` line right after it. Your refusal returns sit just above.
  `traffic-count.js`: there are new branches in `expectedFromLog`, `_onLogEntry`, `_index`, `liveCountRecords` and
  `reconcile`, and none in `_buildRecord` or `_facilityOf`. Audit entries you add `facilityId` to will help
  `_reconcileLogTail` (it matches on cmid only).

  `logLinesFor` changed.

  not BEACON. A no-transponder flight got a recycled soak callsign (`traffic.js` `callsignFor` wraps every 90) and

  every later cmid-less Mutation was answered with the first one's result. That is fixed (never cached).
