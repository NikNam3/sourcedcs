## 2. Mission

The guide gives an OVERFLIGHT lifecycle (`EFSPImplementationGuide.md:214`, under §3.4's
`[SOURCE-DEFINED]` tables):

> Overflight: `INBOUND` → `IN_SECTOR` → `HANDED_OFF` → `DROPPED`.

ADR 0023 built `TRANSITING → DROPPED` instead, and its comments say that the guide has no table
(L9's D10: *"it understates the guide"*). **H63: switch to the guide's four states.** This is a
behaviour change, not a comment fix.

**Done means:**

1. `OVERFLIGHT_STATES = ['INBOUND', 'IN_SECTOR', 'HANDED_OFF', 'DROPPED']` everywhere the Role's
   states live (server and client mirrors, §4 V1). `TRANSITING` no longer exists anywhere
   (`grep -rn TRANSITING crc-sync crc-desktop --include=*.js --include=*.mjs` finds nothing but
   ADR/history text).
2. A new OVERFLIGHT Strip starts `INBOUND`. The NLA walks it `INBOUND → IN_SECTOR → HANDED_OFF →
   DROPPED` (§5.2). Ownership, Bays, coordination, TOFI eligibility and the traffic count follow
   (§5.3–§5.6).
3. **F14 is fixed** (L6: *"an OVERFLIGHT can never propose coordination"*, `coordination.js:65`):
   an `IN_SECTOR` overflight can HANDOFF / POINT_OUT / TRAFFIC to the next Facility (§5.4).
4. The comments L9 flagged (D10, F24, F27, F32) now tell the truth: the guide's table is used, and
   its labels and owners are ours.
5. A persisted Board holding `TRANSITING` Strips comes back in a legal state (§5.7).
6. Playwright walk (`E2E_LANE=8`): an overflight from CTR creation to APP drop, with screenshots in
   `docs/wip/L28/`.
7. ADR `0087`, `docs/wip/L28.md`, both suites green and larger.

**Out of scope:**
- dedicated overflight FDR fields (entry/exit fix; ADR 0023 deferred them);
- Block Map changes (OVERFLIGHT's Blocks are unchanged);
- ATC-scope symbology (L22);
- any other Role's lifecycle.

## 5. Design

### 5.1 The states

`nla.js`: `OVERFLIGHT_STATES = ['INBOUND', 'IN_SECTOR', 'HANDED_OFF', 'DROPPED']`. The comment says
the table is **the guide's** (`:214`, `[SOURCE-DEFINED]` in the guide itself) and that ADR 0087
replaced 0023's two-state one. The NLA labels and owners are ours.

`INBOUND` and `HANDED_OFF` share names with ARRIVAL's and DEPARTURE's states. That is fine: states
are per Role (`STATE_SETS_BY_ROLE`), and nothing keys on a bare state without its Role. Grep for
bare `=== 'INBOUND'` / `=== 'HANDED_OFF'` comparisons that do not check the Role, and list them
(V1). Every one must now also be right for an OVERFLIGHT.

`board-store.js:44`: `OVERFLIGHT: 'INBOUND'`.

### 5.2 The NLA (`computeOverflightNla`)

| State | NLA (label, client) | Result | Inhibited when |
|---|---|---|---|
| `INBOUND` | **Radar Contact** | → `IN_SECTOR` | never |
| `IN_SECTOR` | **Hand Off** | → `HANDED_OFF` (no `transferTo`: the flight leaves our airspace for an agency this server does not model) | never. To hand to **another Facility of ours** (CTR → APP), the controller uses Coordinate/HANDOFF (§5.4), as ARRIVAL does at CENTER. The NLA stays the "leaving our airspace" path (Q2) |
| `HANDED_OFF` | **Drop** | → `DROPPED` | never |

The labels are `[SOURCE-DEFINED]` (Q1). There is no occupancy gating, because no `transferTo` is
issued. The client's `efsp-nla.js` label table and owner mirror change to match, and its drift test
(`efsp-nla-client.test.js` reads `permission.js`) stays green.

### 5.3 Who owns each state (`permission.js` `OVERFLIGHT_STATE_OWNERS`)

```js
INBOUND:    ['APP', 'CTR'],
IN_SECTOR:  ['APP', 'CTR'],
HANDED_OFF: ['APP', 'CTR'],
```

This is the "self-originator owns it" precedent, unchanged. `CREATE_ROLE_PERMISSIONS` is
unchanged.

**`permission.js` is L23's alone in wave 2 (S-L8).** You change **only** the
`OVERFLIGHT_STATE_OWNERS` literal and its comment. That needs a supervisor ruling (Q5); the default
is allowed, merged after L23.

### 5.4 Coordination (F14) and TOFI

- `coordination.js` `COORDINATION_ELIGIBLE_STATES` gains `OVERFLIGHT: 'IN_SECTOR'`. An IN_SECTOR
  overflight may now propose all five primitives.
- **The receiving side** (Q3, HUMAN): the guide's table is per sector, so an overflight handed to
  the next Facility is **`INBOUND` there** and walks the same four states. The default:
  - the replica is minted with Role OVERFLIGHT and state **`INBOUND`**, not the sender's
    `IN_SECTOR`. This is one mapping table in `board-store.js`,
    `REPLICA_STATE_ON_RECEIPT = { OVERFLIGHT: { IN_SECTOR: 'INBOUND' } }`, read in
    `receiveCoordinationProposal` with a fallback to `fromState`. ARRIVAL and DEPARTURE are
    unchanged (ADR 0022);
  - on HANDOFF **ACCEPT**, the sender's Strip moves to `HANDED_OFF` (it may then Drop). Check what
    ACCEPT does today for ARRIVAL/DEPARTURE (V3), and follow it.
  - Say both in ADR 0087.
- The receiving Bay: the replica lands in the receiving Position's overflight Bay (`app-overflight`
  / `ctr-overflight`) through the existing `coordinationBayFor` rule, **if** that is what the code
  does for other Roles. If replicas always land in the coordination Bay, keep that (V3), and record
  it.
- `TOFI_ELIGIBLE_STATES.OVERFLIGHT`: `'TRANSITING'` becomes `'IN_SECTOR'`, in the server and the
  client mirror.

Tests (`efsp-scenario-coordination.test.mjs`, appended):
- `an IN_SECTOR overflight at CENTER hands off to APP, arrives INBOUND, and the sender goes HANDED_OFF on accept`;
- `an INBOUND overflight cannot propose coordination`;
- `POINT_OUT from an IN_SECTOR overflight leaves both states unchanged`.

### 5.5 Bays

`app-overflight` and `ctr-overflight` imply `TRANSITING` today. Default (Q4 (a)): **they imply no
state.** One Bay holds an overflight in every live state, and a drag inside it never changes state.
Remove `impliesState` from both, and check `validateConfig` accepts a Bay without it (V5). Other
Bays are unchanged. `facility-config.js` is shared: L13 edits INCIRLIK's `fieldState.pads.alert`
and L23 TACTICAL's `coveringChain`. You touch only these two Bay lines.

### 5.6 The traffic count

`traffic-count.js:47`: an OVERFLIGHT counts once it reached `IN_SECTOR` or `HANDED_OFF`
(`Object.freeze(['IN_SECTOR', 'HANDED_OFF'])`). `NEVER_TRANSITED` keeps its name (the dashboard,
L15, may show it) and its meaning (dropped while still INBOUND: it never worked the sector). Adjust
to V7's finding (visited vs at-drop). Tests in `efsp-traffic-count.test.mjs`.

### 5.7 A persisted Board with `TRANSITING` Strips

The human's live server has a Board snapshot (ADR 0002). A restored `TRANSITING` Strip would be in
a state its Role does not have, with no NLA. Default (Q6 (a)): **map it at restore, once**:
`TRANSITING → IN_SECTOR` (the flight was being worked), in the existing restore-migration spot
(`index.js` `_restore`, beside `migrateClearanceAnnotations`). Use a small pure function in
`clearance-migration.js`'s style, in a **new** file `crc-sync/src/efsp/overflight-migration.js`,
logged once with a count. "No backwards compatibility" (lane rules) is about the wire and APIs,
not about stranding a live flight.

### 5.8 The soak

`tools/soak/traffic.js`'s `overflight` script becomes the four-state walk. Half the overflights hand
off CTR → APP by HANDOFF (F14 is fixed), and the rest NLA to `HANDED_OFF` and Drop. Its comment
citing `coordination.js:65` goes. `driver.js:746`'s predicate names the new states. Run
`node tools/soak/selfcheck.mjs` and `run.js --minutes 240 --seed 1`. No new failure is allowed
beyond what the base already shows.
