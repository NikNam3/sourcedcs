## 2. Mission

The Mutation log (`state/efsp-mutations.jsonl`, ADR 0065) is the squadron's audit trail and the
traffic count's source. L5 and L6 found four gaps:

| # | Gap | Where (at `3b27390`) |
|---|---|---|
| G1 | **Airspace entries have no `clientMutationId`** (F12). `efsp-ws.js` does not pass it to `airspaceStore.apply` | `efsp-ws.js:334–337`; `airspace-store.js:107–128` logs `mutation.clientMutationId` = `undefined` |
| G2 | **Some refusals are never logged:** airspace `NOT_FOUND`/`STALE_REV` (returned before `_recordAudit`); `efsp-ws.js`'s class `PERMISSION_DENIED` on the correlation and MARSA paths; the "no store" `VALIDATION_ERROR`s. The tap cannot tell these from store-logged refusals by reason alone | `airspace-store.js:158–165`; `efsp-ws.js:313, :377, :405, :446, :472`; `metrics.js` `_post` ~`:935–958` |
| G3 | **Peer replica writes are unlogged:** coordination and TOFI change the receiving Facility's Board with no log entry | `board-store.js` `receiveCoordinationProposal` `:1762`, `receiveCoordinationResponse` `:1837`, `receiveTofiProposal` `:2250`, `receiveTofiExitProposal` `:2349`, `receiveTofiResponse` `:2375` |
| G4 | **Entries carry no `facilityId` and no FDR**, so the traffic count looks the Facility up on the Boards (`traffic-count.js:419` `_facilityOf`), and a backfill cannot recover it once L24 archives the Strip | `board-store.js:373` `_recordAudit`, the `SystemReassign` literal in `reassignPositionStrips` (`:2410`); the other stores' `_recordAudit` |

**Done means:** every EFSP Mutation outcome that reaches crc-sync (applied or refused, from the
wire or from a peer Board) produces **exactly one** log entry. Every entry names:

- its `clientMutationId`, or `null` with a stated reason (system/peer);
- its `facilityId`, or `null` for the theater-wide stores;
- the FDR(s) it concerns, where there are any.

Also done: ADR `0083`, `docs/wip/L26.md`, and the suite green and larger.

**Out of scope:**
- idempotency / replay (L27, F13: a retried op answered from cache is **not** logged again; that
  is L27's rule and you keep it);
- archiving (L24; its `Archive`/`ArchiveFdr` lines are L24's);
- FDR-store writes that are not Mutations (the reconciler's `setBeaconObserved`, MARSA regime
  writes): see Q4;
- log retention and format (L5).

## 5. Design

### 5.1 G1: pass the cmid

`_handleAirspaceMutation` passes `clientMutationId: msg.clientMutationId` in the object it gives
`airspaceStore.apply` (as correlation and MARSA already do). This is one key. Add the test
`an airspace entry carries the clientMutationId of the message that caused it`. In
`tools/soak/ledger.js`, the airspace reconciliation becomes per-message like the others, and the
aggregate workaround goes (L6 F12). Run `node tools/soak/selfcheck.mjs` after.

### 5.2 G2: every refusal logged exactly once, by one rule

**Stores log what reaches them. The tap logs what does not.** The tap stops guessing by reason:

- `airspace-store.js` `apply` (`:158`) logs its `NOT_FOUND` and `STALE_REV` returns through
  `_recordAudit`, as correlation and MARSA already do (`correlation-store.js:229–247` is the model).
  Rewrite the store's comment that says it does not.
- `efsp-ws.js`: every refusal returned **before** a store is consulted adds a sibling key to the
  handler's result, **`unaudited: true`**. It goes next to `ack`, never inside it, so it never
  reaches the wire (ws-hub sends `result.ack`/`.broadcast`). It covers:
  - the "no store" `VALIDATION_ERROR`s;
  - `NOT_HOLDING_POSITION` on every path (Board, airspace, correlation, MARSA, field state);
  - the class `PERMISSION_DENIED` on correlation (`:405`) and MARSA (`:472`);
  - the Board path's unknown `facilityId` (`:139` ff.).
- `metrics.js` `_post`: the condition becomes
  `!ok && (msg.type === 'efsp-mutation' || result.unaudited === true)`. This is one line.
  `efsp-mutation` refusals stay tap-logged, because `BoardStore` logs successes only (L5's T1). Do
  not change that.
- A test table over every refusal path of V2: one entry each, with `ok:false`, the reason and the
  cmid. Name it `every refusal is logged exactly once`, and drive it through `createEfsp` plus
  `createEfspInstrumentation` together, as `efsp-metrics-tap.test.mjs` does.

### 5.3 G3: peer replica writes

Each `receive…` method writes one entry for the change it makes on **its** Board:

```js
{ clientMutationId: null, causedBy: <originating cmid>, op: 'PeerCoordinationProposal' | 'PeerCoordinationResponse'
  | 'PeerTofiProposal' | 'PeerTofiExitProposal' | 'PeerTofiResponse',
  stripId, fdrId, facilityId: this._rules.facilityId, fromFacilityId,
  actingPositionId: null, actorId: <by>, at, before, after }
```

- `causedBy` is the sender's cmid. The sender passes it as **one more key** in the object literal
  it already hands `receive…` (every `receive…` takes a destructured object, so the edit is
  additive). The cmid is in scope because the sender's `_apply…` is running inside `applyMutation`.
  Keep it in a `this._activeCmid` that `applyMutation` sets and clears around `_dispatch`. Do not
  thread it through every `_apply…` signature.
- `clientMutationId` stays `null`, so no reader mistakes a peer line for a second application of
  the sender's Mutation (V6: `auditDuplicate`).
- Test: `a coordination proposal writes one entry on each Board, linked by causedBy`, and the same
  for each TOFI step.

### 5.4 G4: facility and FDR on every entry

| Writer | Adds |
|---|---|
| `BoardStore._recordAudit` (`:373`) | `facilityId: this._rules.facilityId`, `fdrId: result.strip.fdrId` |
| `reassignPositionStrips`' `SystemReassign` literal | the same two keys |
| the peer entries (§5.3) | already have them |
| `AirspaceStore._recordAudit` | `facilityId: definition.controllingFacilityId` (the airspace's own Facility), or `null` when unknown |
| `CorrelationStore._recordAudit` | `facilityId: null` (theater-wide, ADR 0013); `fdrId` is there already |
| `MarsaStore._recordAudit` | `facilityId: null`, `fdrIds: relation participants` (or the op's participants for a refused declaration) |
| `FieldStateStore._recordAudit` | `facilityId: mutation.facilityId` beside the existing `fieldStateFacilityId`, so every reader keys on one name |
| the tap's wire entries | already carry `facilityId`; add `fdrId` when the message names one |

Then the traffic count: `traffic-count.js` `_buildRecord` (`:457`) uses `entry.facilityId` when
present and falls back to `_facilityOf(entry.stripId)`. This is one expression, and it is what lets
L24's archived Strips keep their Facility on backfill (L5's note). Test:
`a backfilled drop of a Strip no Board still holds keeps its Facility from the entry`.

## 9. Traps

- **T1: double logging.** A store-logged refusal must not also be tap-logged. That is why the rule
  is `unaudited`, not a reason list.
- **T2: the wire.** `unaudited` must never reach a client. Assert that the ack has no such key.
- **T3: replays.** After L27, a cached replay is answered before the store and is **not** logged
  again. Do not mark it `unaudited`.
- **T4: `BoardStore` refusals stay tap-logged.** Moving them into the store would double-log with
  the tap. That is L5's T1 and is not yours to reopen.
- **T5: readers.** A new `op` value must not match `isDropTransition` (V6). Peer ops never have
  `after.state === 'DROPPED'` from a live state... check it anyway: a peer response can drop
  nothing, but assert it.
