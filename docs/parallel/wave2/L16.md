## 2. Mission

**Done means:**

1. **`9F` (STEREO) is a `<select>` of the configured stereo routes**, never free text. Picking one
   re-files the flight exactly as typing the name did (ADR 0050's `setField` path, unchanged
   server-side); "—" clears the label and keeps the route; a flight on a route since retired still
   shows its name; with no table configured the cell is plain text, not a control that cannot work.
2. **§10.5's ordered fallbacks** for **departure time, off-block time and takeoff time**: each has an
   explicit, ordered list of sources; the Strip shows the value the first available source gives,
   marks an estimate as an estimate, and **the chosen source is visible on hover**.
3. **Every epoch time Block renders as `HHMM`** (§11.2 rule 1) — today only L2's two MTR times do;
   the rest (6, 14, 14B–14D, 16, 17, 18, ARRIVAL 6, M6, M7) show raw epoch numbers. F4 fixed what is
   *stored* when a controller types a time; you fix what is *shown*.

ADR `0073` and `docs/wip/L16.md` written; a pilot-request walk of the picker written up.

The guide, verbatim (`EFSPImplementationGuide.md:1183–1191`):

> Where a time or value has multiple possible sources, implement an explicit ordered fallback and
> record which source was used. The pattern to copy, from ATD-2: *"UOBT is normally equal to the EOBT
> if the EOBT is set. If there is no EOBT, then LOBT; if no LOBT, then flight plan departure time; if
> no POBT, then SOBT; if no SOBT, then IOBT."* Apply the same shape to departure time, off-block time
> and takeoff time. The chosen source MUST be visible on hover.

**Out of scope:**

- The **server** half of typed times — F4 did it (S-R2-17). Do not re-implement it; build on it.
- Stereo **table** content (squadron data, D11) and a table editor (§8.4's versioned config; P5).
- **MTR designators as a picker** — H23: MTRs stay free text until the human supplies the list.
- Departure metering / TOBT / TMAT, Block 16's computation (guide §12: *"do not compute it"*).
- Taxi-duration or climb-out estimates of any kind: a computed "off-block + N minutes" is invented

- Surveillance-derived times ("detected airborne") — L19 defines that (ADR 0047 left it open).

## 5. Design

### 5.1 The `9F` picker

- **One option source, runtime:** `efsp-stereo-routes.js` keeps the last successful list in a module
  cache and exports `cachedStereoRoutesClient()`. `listStereoRoutesClient()` updates it on every
  successful fetch (an ok response with an empty list empties it; a failed fetch keeps the last good
  list). `efsp-panel.js`'s existing fetch on snapshot therefore refreshes it with no edit there.
- **`enumSelectOptionsFor(blockId, fdr)`** in `strip-template.js` gains an optional second argument.
  For `9F` it returns, in order: every cached **active** route's canonical name, plus the flight's
  current `filed.stereoRouteName` if it is not among them (a retired route stays visible on the
  flight that is flying it — ADR 0050: deactivation is not retroactive). It returns **`null`** when
  the cache is empty **and** the flight has no stereo, so nothing is offered that could only fail
  (standing rule 1: an enabled control that cannot act).
- **`isBlockEditable('9F', role)`** is `true` only while the cache is non-empty; with an empty cache
  and no value the cell is a plain span with `title` "no stereo routes configured". With an empty
  cache and a value, the picker offers just that value and "—" (clearing is still meaningful).
- **Clearable:** add `9F` to `ENUM_CLEARABLE_BLOCKS` — "—" sends `''`, the server clears the label
  and keeps the route (ADR 0050). Its comment block (`strip-template.js:462–486`) gets a `9F` line.
- **`bay-view.js` `_buildBlockCell` (`:176`)**: pass the FDR it already has —
  `enumSelectOptionsFor(blockId, fdr)` (Q-L16-2). `_buildEnumSelectCell` is untouched: it already
  shows the current value, commits on Enter/pick, reverts on Esc, and sends `{ kind:'SetBlock',
  blockId, value }`.
- Option labels: the route name, with the `description` (if the table has one) in the option's
  `title`. Sorted as the table orders them.
- Rewrite `strip-template.js:70–78`'s comment to say what is true now, citing 0073.

### 5.2 §10.5: three chains, computed at read, one pure module on each side

**Where the answer lives.** A chain's answer is a pure function of data the FDR already carries
(plus one new input, §5.3). *Default* (Q-L16-1): **compute at read** — no stored derived field, so
no writer (yours, L14's `applyAtoTasking`, F4's `setField`) has to remember to recompute it, and the
stored actual-time fields never hold an estimate that a later reader could mistake for an actual.
"Record which source was used" is met because the answer is deterministic from recorded inputs, and
the resolver returns the source with the value.

- Server: `crc-sync/src/efsp/time-chains.js` (new, pure, no requires except `zulu-time.js` if needed).
- Client: `crc-desktop/app/public/js/panels/efsp/time-chains.js` (new), a **literal duplicate** —
  the two packages never share code (ADR 0001's reason, `efsp-stereo-routes.js:61–64`'s precedent) —
  held equal by a parity test on a shared fixture table
  (`crc-sync/tests/fixtures/time-chains.json` read by `crc-sync/tests/efsp-time-chains.test.mjs`
  and, by relative path, `crc-desktop/tests/efsp-time-chains.test.js`).

```js
// [SOURCE-DEFINED] order (ADR 0073), ATD-2's shape per guide §10.5.
const TIME_CHAINS = {
  departure: { blockId: '6',  path: 'filed.proposedDepartureTimeUtc', sources: ['CONTROLLER', 'FLIGHT_PLAN', 'ATO'] },
  offBlock:  { blockId: '17', path: 'assigned.taxiTimeUtc',           sources: ['CONTROLLER', 'EST_DEPARTURE'] },
  takeoff:   { blockId: '18', path: 'assigned.takeoffTimeUtc',        sources: ['CONTROLLER', 'EST_OFF_BLOCK'] },
};
resolveTimeChain(name, fdr) // → { valueUtc: number|null, source: string|null, estimated: boolean,
                            //     candidates: [{ source, valueUtc }] }   never throws; fdr may be null
```

| Source | Reads | Meaning on hover |
|---|---|---|
| `CONTROLLER` | the chain's own field (`path`), when non-null | "entered by a controller" |
| `FLIGHT_PLAN` | `fdr.timeInputs.flightPlanDepartureUtc` (§5.3) | "from the filed DD-1801 (item 13, EOBT)" |
| `ATO` | `fdr.ato.departure.timeUtc` (L14, C1) | "from the ATO (AMSNDAT departure time)" |
| `EST_DEPARTURE` | `resolveTimeChain('departure')` | "estimate: P-time, from <its source>" |
| `EST_OFF_BLOCK` | `resolveTimeChain('offBlock')` | "estimate: off-block, from <its source>" |

- `estimated` is true when the source is an `EST_*` — a planning value standing in for an actual
  that has not happened. Departure's own sources are plans, so it is never "estimated".
- A controller-typed value always wins and stops the fallback for that Block (§10.2 rule 3's
  "once a controller modifies it, stop auto-updating"); clearing it (`''` → `null`) resumes the chain.
- No chain touches Block 16 (metering deferred) or computes a duration (D11).
- The state-transition source (TWR presses Airborne → takeoff time) is **not** in this lane
  (Q-L16-3): no state change writes a time today, and adding one is `board-store.js`.

### 5.3 The one new input: the DD1801 departure time

- `flight-plan-lookup.js` `toFdrFiledSeed` (`:84`) adds `flightPlanDepartureTimeHhmm: plan.depTime ||
  ''`. Nothing else in that file. (Both callers — the lookup and the ops-filed queue — share it.)
- `createFdr` (`fdr-store.js`): resolve it with `resolveZuluHhmm(seed.flightPlanDepartureTimeHhmm,
  this._clock.now())` and store **`fdr.timeInputs = { flightPlanDepartureUtc: ms|null }`** in the
  literal (a new top-level key, `null` members when absent — §12's "present and unpopulated"). An
  unparseable value is dropped silently (the lookup is best-effort by design,
  `flight-plan-lookup.js:66–83`). **Not** written into `filed.proposedDepartureTimeUtc`: that field
  stays the controller's, so a cleared P-time falls back to the plan instead of losing it.
- `restore()` seeds `timeInputs` onto FDRs that predate it (the `ensureMilitary` pattern,
  `fdr-store.js:241–244`): readers must never throw on a restored board.
- Readers (both `time-chains.js`) treat a missing `timeInputs` and a missing `fdr.ato` as null.

### 5.4 Display: every epoch time Block as `HHMM`, estimates marked, sources on hover

- `strip-template.js`: extend L2's `ZULU_HHMM_BLOCKS` to **every** Block whose target is an epoch
  `…Utc` path: DEPARTURE `6, 14, 14B, 14C, 14D, 16, 17, 18`; ARRIVAL `6`; MISSION `M6, M7`. Keep L2's
  two. A test derives the expected set from the Block Maps (every `fdr` target path ending `TimeUtc`
  or `…Utc` that is epoch-typed) so a Block added later without formatting fails.
- **L2's rename trap:** the set is also what makes the click-to-edit cell open on `1432` and send
  `1432` back — exactly what F4's `setField` now resolves. So one set fixes display and editing.
- `resolveBlockValue` for `6`/`17`/`18` (DEPARTURE only): when the field is null, return the chain's
  value (formatted) with `provenance: 'COMPUTER_GENERATED'` and a new `timeSource` field; when the
  field has a value, `timeSource: 'CONTROLLER'`. Add a boolean `estimated`.
- **Marking an estimate (Q-L16-5, HUMAN):** *default* — the value in italics via a class
  `efsp-block-estimated` (no colour: ADR 0056 reserves colour for something wrong), with `~` before
  it in the hover text only. The class is added where the cell is built: `bay-view.js`
  `_buildBlockCell` gets one line reading `resolveBlockValue(...).estimated` (Q-L16-2). An estimate is
  still click-to-edit: typing the actual replaces it.
- **Hover (§10.5's MUST):** extend L2's `blockTitleFor(blockId, fdr)` for `6`/`17`/`18`: the Block's
  name, the value's source sentence (§5.2's table), and the fallback that would apply next ("if

  line in `bay-view.js` `_appendExpandedView` sets `label.title = blockTitleFor(blockId, fdr)` when

  controller hovers the number, not the word): same `_buildBlockCell` line, only when the cell has no
  refusal title already.
- `formatZuluHhmm` stays the only formatter; `HHMM` without `Z` on the Strip (§11.2, L2's
  convention), `HHMMZ` in hover text.
