## 2. Mission

Today nothing leaves memory. A DROPPED Strip stays in `_strips` forever, its FDR stays in `_fdrs`,
and both are written into every Board snapshot. L6 measured the cost in the realistic 4-hour soak:

- `strips.dropped` went from 19 to 378;
- the snapshot went from 23 KB to 470 KB, and 1.75 GB was written in total;
- `handleMessage` latency p50 went from 0.8 to 13 ms;
- about 7.8 KB of heap per DROPPED Strip.

H36 decided the fix: *archive DROPPED Strips (and FDRs with no live Strip) after 2 h or at mission
change, once L5 has counted them; the log keeps history.* S-R2-13 fixed the rules. Apply them
**exactly**:

1. A **Strip** is archived when it is `DROPPED` and either **2 h of wall time** have passed since
   its drop, or the mission session rolls over (F3). It must also be **counted** (L5's traffic count
   has its record).
2. An **FDR** is archived only if it **had a Strip**, and every Strip that referenced it is DROPPED
   or archived. In practice: the FDR goes in the same sweep that archives its last Strip. An FDR
   that never had a Strip (a future ATO-seeded one, L14) is never touched.
3. **Mission change = F3's session roll-over.** Everything DROPPED is archived at once, whatever its
   age, as long as it is counted.
4. **Nothing archived can be undone.** An `Undo` of an archived Strip's drop is `NOT_FOUND`. Only
   the mission-change path can archive inside the 30 s Undo window.
5. **L5's backfill treats a missing FDR as `UNKNOWN`/`ARCHIVED`.** L5 already does this
   (`traffic-count.js:457` `_buildRecord`: `localityBasis: 'ARCHIVED'`). You prove it with a test
   and change nothing there.

"Archived" means **removed from memory and from the snapshot**. The Mutation log keeps the history,
and you add one audit line per archived Strip (§5.3). There is no archive file (Q2).

**Also done means:**

- Everything that pins a finished flight lets go:
  - the Board's `_strips`, `_nlaHistory` (F7) and `_log` ring;
  - `_appliedMutations` (F4: done by L27 if the supervisor accepts L27-Q1, and verified by you);
  - `fdrStore._fdrs`;
  - MARSA relations whose participants are all gone (`marsaStore.evictMissingFdrs`, today only
    called at restore);
  - correlation records (`correlationStore.evictMissingFdrs`; `retireFinished` already handles
    most);
  - the NLA-status monitor's `_last`, and conformance's `_mem`/`_alerts`. Both already prune
    against live sets; prove it (V8).
- The soak's memory gates pass on the criterion §8 names (see **Q1, HUMAN**: a 2-hour retention
  cannot pass L6's net-growth gate as it is measured today).
- ADR `0082`, `docs/wip/L24.md`, both suites green and larger.

**Out of scope:**
- an archive UI or a "recent flights" lookup (Q3, HUMAN);
- log retention (L5's, 30 days);
- the traffic count's own in-memory record list (L5's `_entries`, retained for reconciliation; see
  "Findings" if the soak shows it matters);
- audit-entry fields (`facilityId`, the FDR): that is **L26**. Your archive line carries them from
  the start;
- idempotency and sync (L27).

## 5. Design

### 5.1 When a Strip dropped, in wall time

`BoardStore` gains `this._droppedWallAt = new Map()` (stripId → `Date.now()` at the drop), which is:

- set in `_retireStrip` right after `strip.state = 'DROPPED'`;
- deleted if `_applyUndo` revives the Strip.

It is **not** a Strip field, so the wire is unchanged (V7's strictness test), and it is persisted in
`snapshot()` as `droppedWallAt: [[id, ms], …]` and restored. A DROPPED Strip restored with no entry
(written before L24) gets `Date.now()` at restore, so it is archived 2 h after boot. That is safe:
it has been counted (L5 backfills at boot). This is wall time on purpose: retention is a storage
lifetime (H11's line; L5's rotation does the same). The soak virtualises `Date.now`, so the rule
runs on its clock.

### 5.2 The archiver

A new module, **`crc-sync/src/efsp/archiver.js`**:

```js
class Archiver {
  constructor({ facilityIds, boardStoreFor, fdrStore, correlationStore, marsaStore, mutationLog,
                clock, wallNow = () => Date.now(), retentionMs = ARCHIVE_AFTER_MS,
                isCounted = null })
  setIsCounted(fn)              // wired by server.js to the traffic count (V5)
  sweep({ all = false, reason = 'AGE' } = {}) // → { stripsByFacility: {fid: [stripId]}, fdrIds: [], relations: n }
  onMissionSessionChange()      // → sweep({ all: true, reason: 'MISSION_CHANGE' })
}
const ARCHIVE_AFTER_MS = 2 * 60 * 60 * 1000; // H36: 2 h
```

- `ARCHIVE_AFTER_MS` is a module constant, not a tuning file. H36 fixed the value, so it is a
  decision, not tuning. If the supervisor prefers `config/efsp-instrumentation.json` (read once,
  P5), that is Q4.
- **`isCounted`**: the default `null` means "no counter wired". The sweep then archives anyway and
  warns **once** at the first sweep. Unit tests and the soak (V9) run that way. The server wires
  `trafficCount.hasCountFor(stripId)`, a new one-line accessor on `_liveByStrip` appended to
  `traffic-count.js`. An uncounted DROPPED Strip is **skipped** and retried on the next sweep, and
  a warning with its id is logged, so a count bug never becomes silent data loss.

**One sweep, per Facility:**

1. Collect the candidates: DROPPED, and (`all` or `wallNow() - droppedWallAt ≥ retentionMs`), and
   counted.
2. For each candidate, `boardStore.archiveStrip(stripId, reason)`, a new method appended to
   `BoardStore` after `reassignPositionStrips`. It does five things:
   - deletes the Strip from `_strips`;
   - deletes it from `_droppedWallAt` and `_nlaHistory` (F7);
   - pushes a ring entry `{ seq: ++this._seq, type: 'gone', id }`, so `getDeltaSince` reports it in
     `gone` (L27's seam; V2);
   - writes the audit line (§5.3);
   - returns the Strip's `fdrId`.
3. For each `fdrId` returned: if `rules.liveStripsForFdr(fdrId) === 0` **and** no Strip on any Board
   (live or DROPPED-not-yet-archived) still references it, call `fdrStore.archiveFdr(fdrId)`. That
   is a new method appended **directly before** `fdr-store.js`'s `// ── Persistence` comment. It
   deletes from `_fdrs` and releases the code if one is still held (it should already be free; it
   is idempotent). This is rule 2: an FDR goes only with its last Strip, so one that never had a
   Strip is never a candidate.
4. After every Board: `marsaStore.evictMissingFdrs()` and `correlationStore.evictMissingFdrs()`
   (both exist; today they run only at restore, `index.js:334–342`).
5. The caller persists (`efsp.persist()`) if anything was archived.

**Registration** (`index.js`, plan §2 rule: append only): construct the Archiver after the Boards,
expose `efsp.archiver` on the returned facade (appended), and add nothing to `_persist`/`_restore`.
The Board's own `snapshot()` carries `droppedWallAt`.

**Wiring** (`server.js`, one self-contained block appended right after L5's instrumentation block,
~`:481–499`):

```js
// ── Archiving (H36, docs/adr/0082) ──
efsp.archiver.setIsCounted((stripId) => efspInstrumentation.trafficCount.hasCountFor(stripId));
setInterval(() => _archive(efsp.archiver.sweep()), 60 * 1000);
<mission-session roll-over> → _archive(efsp.archiver.onMissionSessionChange());
function _archive(r) { /* if anything: efsp.persist(); one efsp-board-delta per Facility via
                          wsHub.broadcastEfspBoardDelta({ …, strips:{updated:[],gone:ids}, fdrs:{updated:[],gone:fdrIds} }) */ }
```

The broadcast keeps every client's `boardSeq` continuous (the ring advanced) and lets clients drop
archived FDRs (§5.5). Its `gone` Strips are already gone client-side, so that part is a no-op.
Build the payload with whatever the merged code requires (L27's `boardEpoch`, if merged; V2).

**The soak** (V9): `tools/soak/host-core.js` calls `efsp.archiver.sweep()` in the tick it already
runs for the monitors, and persists as the server would. That is one hunk; L27 edits other soak
files. The `--prune-retired` diagnostic flag stays as it is.

### 5.3 The audit line

One line per archived Strip, written by `archiveStrip`:

```js
{ clientMutationId: null, op: 'Archive', stripId, fdrId, facilityId: this._rules.facilityId,
  actingPositionId: null, actorId: 'system', at: this._clock.now(),
  reason: 'AGE' | 'MISSION_CHANGE', fdrArchived: <bool, filled by the archiver's second pass: see below> }
```

Keep it simple: write the Strip line in `archiveStrip`. When the FDR goes, the archiver writes a
second line, `{ op: 'ArchiveFdr', fdrId, actorId: 'system', at, reason }`. It has no `before`/`after`
(the history is in the earlier lines). Check that L5's readers ignore both ops: `isDropTransition`
/ `isUndoOfDrop` in `traffic-count.js:68–74`, and `metrics.js`'s aggregation. Add a test that the
traffic count is unchanged by a sweep.

### 5.4 F4: nothing else pins an archived Strip

- If L27 merged with compact replay records (V2): add the test `after archiving, no structure in the
  efsp object graph references the Strip`. Walk `_appliedMutations`, `_log` (ids only),
  `_nlaHistory`, `_droppedWallAt`, the monitors' maps, and the correlation and MARSA stores. A
  `WeakRef` + `global.gc` check is fine under `node --expose-gc`. If the plain runner can't do it,
  use the walk.
- If L27 did **not** do the rewrite (the supervisor ruled L27-Q1 (b)): you store the compact record
  instead of the result object in `applyMutation` (`board-store.js:245`). The record is `{ ok,
  reason, detail, warning, routedTo, selfCoordinated, stripId, fdrId }`, and a replay rebuilds
  `strip: getStrip(stripId)`. Coordinate with L27's F11 fix through the supervisor.

### 5.5 Clients forget archived FDRs

`crc-desktop/app/public/js/panels/efsp/efsp-state.js` `applyEfspDelta` (`:222`) gains **one line**
after the `fdrs.updated` loop:

```js
for (const id of (msg.fdrs && msg.fdrs.gone) || []) efspFdrs.delete(id);
```

Server-side, `fdrs.gone` appears only on the archiver's delta. Update `ws-hub-wire-strictness.test.mjs`
if it pins the `fdrs` key (V7). Test it with a client unit test that loads `efsp-state.js` in a `vm`
sandbox, following the existing client tests' pattern. Without this line a client keeps archived
FDRs until it reconnects: harmless, but a slow leak over a long session (Q5).

### 5.6 Mission change

On F3's roll-over (V1), `onMissionSessionChange()` archives every **counted** DROPPED Strip and
their FDRs. It does not touch live Strips; ADR 0002 stays true for them. That is H36's "or at
mission change". Test: a Strip dropped 10 s before the roll-over is archived, and an `Undo` then
answers `NOT_FOUND` (rule 4). A live Strip survives.
