## 5. Design

### 5.1 F1 + F8: every Strip a Board event touched goes out with it

**Principle** (guide §5.4, "one Board event"): whatever a Mutation changed on a Board reaches every
client **in that Mutation's broadcast**. Do not special-case the rebalance. Collect.

- `BoardStore` keeps `this._touchedSinceDrain = new Set()`. `_touch(stripId)` also adds to it.
- New `drainTouched()` → `stripId[]`, which clears the set. It is public, so `efsp-ws.js` can call
  it on the **peer** board too.
- `_handleMutation` (`efsp-ws.js:139`): after `applyMutation`, on success, build `strips.updated` /
  `strips.gone` from **`boardStore.drainTouched()`**, not from `result.strip` alone:
  - each id is looked up with `getStrip`;
  - DROPPED goes into `gone`, and everything else is stamped (`_stampStrip`) into `updated`;
  - `result.strip` is always included, first.

  `peerBroadcast` is built the same way from `peerBoardStore.drainTouched()`. The peer's
  coordination-Bay placement can rebalance a peer Rack (V3). On a **refusal**, drain and discard:
  a refused Mutation touched nothing. Assert that in a test.
- `_handleSetPositions` already re-sends every live Strip. It drains too, so leftovers from
  `reassignPositionStrips` do not ride on the next Mutation.
- `_handleResync`'s delta is unaffected. Every touch is logged in the ring, so a resync from a seq
  covers the rebalanced Strips once the broadcast has carried them.
- The ack is unchanged (`ack.strip` is the addressed Strip). The sender gets the side effects from
  the broadcast like everyone else.

**F8, the proactive rebalance.** In `_resolveOrderKey` (`board-store.js:187`), after a key is
computed, if `needsRebalance([key])` (length > `REBALANCE_KEY_LENGTH`):

1. `_rebalanceRack(bayId, rackId, excludeStripId)`;
2. recompute the key between the named neighbours' **fresh** keys, reusing the existing retry
   block's `a > b` normalisation.

This is the same Board event. The touched Strips ride out through the rule above. Import
`needsRebalance` from `order-key.js`, which already exports it. Leave the threshold at 40 (it is a
placeholder, and the soak gates on it). Say in 0081 that it is not researched.

**Tests:**
- `efsp-board-store.test.mjs`, appended:
  - a forced exhaustion rebalance: every re-keyed Strip is in `drainTouched()`;
  - a same-slot insert storm (the probe's loop, 400 pairs) never produces a key longer than 41;
  - a refused Mutation leaves `drainTouched()` empty.
- `efsp-ws.test.mjs`, appended:
  - `a Mutation that rebalances a Rack broadcasts every Strip it re-keyed`;
  - `a coordination proposal that rebalances the peer's coordination Rack puts the re-keyed peer Strips in peerBroadcast`;
  - `resync from the seq the rebalancing broadcast advertised returns an empty delta and the client is correct`. Use a fake client replica built the way `tools/soak/shadow.js` builds one.

### 5.2 F2: a Board epoch

**Principle:** a delta is only valid within one Board lifetime. The sequence is per process
(`restore()` deliberately does not restore `_seq`), so the lifetime must be named on the wire.

- `BoardStore` mints `this._epoch = crypto.randomUUID()` in its constructor, and mints it again in
  `restore()`. The getter is `get epoch()`. It is not persisted. A new process is a new lifetime,
  even from the same snapshot, because the ring (`_log`) is not persisted either. The soak seeds
  `crypto.randomUUID` per host lifetime (L6 default 3), so runs stay reproducible.
- **Wire:**
  - `efsp-snapshot` gains `boardEpochByFacility` (next to `boardSeqByFacility`, `efsp-ws.js:593`);
  - **every** `efsp-board-delta` gains `boardEpoch` (the V4 list, including `ws-hub.js:129`'s
    payload, stamped by its builders);
  - the mutation ack gains `boardEpoch` beside `boardSeq`;
  - `efsp-resync` accepts an optional `boardEpoch`.
- `_handleResync` (`efsp-ws.js:248`) serves a delta **only** when `msg.boardEpoch ===
  boardStore.epoch` **and** the existing window and `rewound` checks pass. A missing or different
  epoch gets the snapshot, which is §5.6's other path. Keep `rewound`: it is cheap and still true.
- **The `gone` seam for L24.** `getDeltaSince` returns `{ updated, gone, seq }`, where `gone` is the
  ids in the window that are no longer in `_strips` (always `[]` until L24 archives). `_handleResync`
  sends `gone: [...droppedIds, ...delta.gone]`. Write it now, with a test using a Strip deleted from
  `_strips` by hand. L24 then changes only `board-store.js`.
- **Leave room for L23:** keep `_handleResync`'s structure as "resolve the Board → decide delta vs
  snapshot → build". L23 adds `session` as the second parameter and one early return (an `OWNED`
  session always gets a snapshot). Do not add a `session` parameter yourself.
- **Harness:** `shadow.js` keeps `boardEpoch` per Facility (from the snapshot's
  `boardEpochByFacility`, and from each delta's and ack's `boardEpoch`). `driver.js`'s reconnect
  (`:906–921`) sends it with `lastBoardSeq`. Without this, every harness resync becomes a snapshot
  and the delta path goes untested. Acceptance requires `resync delta > 0` in the 240-minute run.
- **Client:** it never resyncs (V7), so it needs no change. Optionally, `sendEfspResync(lastBoardSeq,
  boardEpoch)` gains the parameter, and `efsp-state.js` stores `boardEpoch` (Q5). The default is no
  client change.

**Tests** (`efsp-ws.test.mjs`, appended):
- `a resync with the current epoch and a seq inside the window gets a delta`;
- `a resync with no epoch gets a snapshot`;
- `a resync carrying the previous lifetime's epoch gets a snapshot, even when its seq is inside the new lifetime's window`. This is F2 exactly: restore into a new `createEfsp`, advance the seq past the old one, then resync;
- `every efsp-board-delta carries boardEpoch`. Table-driven over the V4 senders.

Update the existing resync tests (V7) to send the epoch they got from the snapshot. The
**assertions** of `efsp-ws.test.mjs:201–243` stay as they are.

### 5.3 F5: a Mutation survives a crash exactly once

There are two failure modes (L6 F5, default 6):

- **A:** the change is applied and persisted, and the process dies before the ack. The retry
  re-applies it, because `restore()` drops the idempotency cache. Seen as `CreateStrip:appliedTwice`.
- **B:** the audit line is written and the snapshot is not. The crash happens inside `_persist`.
  The retry applies it again, so there are two audit lines for one effective change. Seen as
  `SetFlag:lost`.

Default (Q2 (a)):

1. **A persisted replay window.** `BoardStore.snapshot()` gains `replay`: the compact replay
   records (§5.4) of Mutations applied in the last **`REPLAY_PERSIST_WINDOW_MS` = 10 min of wall
   time**. That is a retry window, not a history. A constant, `[SOURCE-DEFINED]`, not a tuning file.
   `restore()` reloads them into `_appliedMutations`. A retry after the restart then answers from
   the cache, which fixes mode A. The wall time comes from `Date.now()`, like the NLA latch
   (ADR 0079's one exception). Say so.
2. **A boot reconcile of the log tail.** The snapshot also carries `persistedWallAt`. In `_restore`
   (`index.js:402`), after the Boards are restored:
   - read `mutationLog.readSince(persistedWallAt - 60 s)`;
   - for every **successful Board entry** (`stripId` present, `ok !== false`, `source !== 'wire'`,
     `clientMutationId` not null) whose cmid is **not** in that Board's restored replay window and
     whose `wallAt > persistedWallAt`, append one marker:

     ```js
     { op: 'NotPersisted', clientMutationId, stripId, voids: <that entry's op>,
       reason: 'CRASH_BEFORE_PERSIST', actorId: 'system', actingPositionId: null, at: clock.now() }
     ```

   The log stays append-only, and it now says the first line never took effect. The retry then
   applies the Mutation and writes the one line that did.
3. **Readers honour the marker.**
   - The traffic count: `traffic-count.js` `_onLogEntry` treats `NotPersisted` of a drop like
     `isUndoOfDrop`, and appends a `VOID` for its `countId`. `reconcileTrafficCount` pairs them the
     same way. That is one branch in each function (§7.2).
   - The soak ledger (`tools/soak/ledger.js`): an audit line followed by a `NotPersisted` for its
     cmid is not a duplicate.
   - `_isDrop`-style matchers elsewhere: grep for `isDropTransition` and the `op ===` readers of the
     log.
4. **V5:** `_handleSetPositions` persists when it reassigned anything. `handleMessage` passes
   `persist` to it. This is one argument and one call.

Test all four with a crash simulated in-process. Throw from a wrapped `fs.writeFileSync` for the
snapshot path, the way `tools/soak/host-env.js` does. In a new
`crc-sync/tests/efsp-crash-replay.test.mjs`:
- `a CreateStrip whose ack died with the process is not created twice on retry`;
- `a Mutation audited but never persisted gets a NotPersisted marker at boot, and its retry is audited once`;
- `a dropped Strip whose drop was never persisted is voided in the traffic count`;
- `the replay window forgets entries older than 10 minutes`.

### 5.4 F11 (and F4's live references): a replay answers the original outcome with the current record

`_appliedMutations` (`board-store.js:137`, cap 5000) stores **whole result objects**:

- a success holds the **live** Strip. That is F4: archiving cannot free it. It also means a replay
  of a success already returns the current Strip, by accident;
- a refusal holds a `deepClone` from the time of refusal. That is F11: the replica goes backwards.

**Store a compact, frozen replay record instead:**

```js
{ ok, reason, detail, warning, routedTo, selfCoordinated, stripId, fdrId, peerFacilityId, peerStripId, appliedWallAt }
```

- Nothing live, and nothing cloned. It is serialisable for §5.3's persisted window.
- On replay, rebuild the result: the same outcome, with `strip: getStrip(stripId)` (current, or
  `null` if gone) and `fdr: fdrStore.getFdr(fdrId)`.
- A replay **broadcasts nothing**. `_handleMutation` must know it was a replay: the result carries
  `replayed: true`, and it builds the ack only. Today a replayed success re-broadcasts; check and
  record it in V2. Re-broadcasting a stale view is harmless, but it is noise.
- `marsaChanged`, `fdrs` and `peerStrip` are not replayed. Their broadcasts already went out.

**Q1:** decisions S-L6 gives F4 to **L24**. This briefing proposes that L27 does the cache rewrite,
because F11 and F5 need the same code and a serialisable record, and you merge first. L24 then only
verifies that an archived Strip is collectable. The default is (a), you do it. Check the addendum.

**Tests:**
- `a replayed STALE_REV refusal returns the current Strip, not the one at refusal time` (F11);
- `a replayed success returns the current Strip and produces no broadcast`;
- `the cache holds no Strip or FDR object` (walk the records and assert that no value is an object
  with a `stripId` key).

### 5.5 F13: the non-Board paths are idempotent too

The same rule as §5.4, in one small new module, **`crc-sync/src/efsp/replay-cache.js`** (pure, no
requires):

- `new ReplayCache({ cap = 5000 })`;
- `get(kind, cmid)` / `set(kind, cmid, record)`, a Map with insertion-order eviction like
  `APPLIED_MUTATIONS_CAP`;
- `kind` ∈ `airspace | correlation | marsa | fieldState`.

It is constructed once in `index.js` (appended at the end of `ctx`) and used in the four `efsp-ws.js`
handlers (`_handleAirspaceMutation` `:310`, `_handleCorrelationMutation` `:374`,
`_handleMarsaMutation` `:443`, `_handleFieldStateMutation` `:669`):

1. **After** the session and permission checks, and **before** the store's `apply`, if
   `msg.clientMutationId` is a non-empty string and the cache has it: return the rebuilt ack (the
   original `ok`/`reason`/`detail` plus the **current** record from the store's getter). No
   broadcast, no audit, and no `persist()`.
2. Otherwise apply as today, then `set` the compact record (`{ok, reason, detail, warning, id}`).

Refusals made before the store (no store, `NOT_HOLDING_POSITION`, class `PERMISSION_DENIED`) are
**not** cached. A retry after taking the Position must be allowed through.

- `DeclareMarsa` is the case that matters. A retried declaration mints a **second relation**
  today. Test it first.
- The cache is **memory only** (Q3). The stores' own `apply()` is not changed, which leaves those
  functions to L26 (§7.3).

**Tests** (`efsp-ws.test.mjs` or a new `efsp-ws-replay.test.mjs`), one per kind:
- `a retried DeclareMarsa returns the first relation and mints no second one`;
- `a retried BindTrack is acked once, audited once`;
- `a retried airspace op is not re-applied`;
- `a retried field-state op is not re-applied`;
- `a NOT_HOLDING_POSITION refusal is not cached: the retry after selecting the Position applies`.

### 5.6 F6: a released code is not handed out again soon

`CodeAllocator.allocate()` (`code-allocator.js:67`) takes the **lowest** free code. A flight that
landed releases its code, and the next CreateStrip gets the same code while the old aircraft is
still squawking it. Correlation then binds the new FDR to the old track. The soak saw 46 in the
240-minute run and 84 in stress.

Default (Q4 (a)), a **rotating cursor**:

- `allocate()` scans from the code **after the last one it handed out**, wrapping at `7777`, with
  the same exclusions (reserved, `4000`, the synthetic `6000–6777` block).
- A released code is therefore not reused until the whole discrete pool has cycled. That is
  thousands of flights at H12's scale. There is no clock and no tuning file.
- The cursor is persisted: `snapshot()` → `{ codes: [...], cursor }` inside `fdr-store`'s snapshot.
  Alpha, so there is no compatibility shim. A snapshot without a cursor starts at `0000`.
- `validateAssignment`, `reassign` and `reacquireFdr` are unchanged.

**Tests** (`efsp-code-allocator.test.mjs`, appended):
- `a released code is not re-issued by the next allocate`;
- `the cursor wraps and still skips reserved, 4000 and the synthetic block`;
- `the cursor survives snapshot/restore`.

The soak's `misbinding LINGERING_TRACK` must be **0** in the 240-minute and stress runs.
