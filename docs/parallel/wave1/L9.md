## 1. Mission

Produce a complete, classified inventory of every place in the tree where a `[SOURCE-DEFINED]`
behaviour, figure or table lives, and of every piece of **code comment, UI text or user-facing
documentation** that presents such a thing, or any other unsourced claim, as real-world doctrine.
Each finding gets a file:line, a verbatim excerpt, a class, and suggested fix wording that L20 can
apply without re-deriving anything.

This is WP6 plan Phase 7 steps 1–3 (`docs/efsp-wp6-plan.md:473-488`) as a report only, and it
serves the WP6 acceptance criterion in `EFSPImplementationGuide.md:1386`:

> No UI text or code comment presents a `[SOURCE-DEFINED]` behaviour as real-world doctrine.
> **Audit this explicitly.**

The defect class it guards against is **D11 Doctrine fabrication** (guide `:1484`): "A
`[SOURCE-DEFINED]` behaviour presented as FAA/DoD doctrine in code, UI or wiki".

### Out of scope

- **Fixing anything.** No edit to any file other than the inventory. Not a comment, not a
  string, not a typo you notice on the way. L20 applies fixes last, because every other lane will
  add to the list (`docs/efsp-parallel-plan.md:213-217`, `:304-306`).
- Phase 7 step 4 (recording the result in the ADR and the usage guide). That is L20 and the
  integrator.
- Deciding squadron data (which radar sits at which console, real stereo routes, real thresholds).
  Classify, suggest the marker wording, and put "needs a squadron answer" in the fix column.

- Test files. Count their markers (there are 5, in `crc-sync/tests/efsp-nla.test.mjs` and

## 3. The marker conventions — restated precisely

From `EFSPImplementationGuide.md` §0.2 (`:25-35`) and its uses elsewhere in the guide:

1. **`[SOURCE-DEFINED]`** tags a clause that specifies behaviour **not documented in the real
   system**. It is SOURCE's own choice. The guide's own tagged items are: EFSP State (`:115`,
   `§3.4` at `:193`), NLA and its determination table (`:117`, `§3.5` at `:219`), the layout of
   the `PATTERN`/`MARSHAL`/`FINAL` Roles (`:95`), the "otherwise coordinated" convention (`:344`),
   the default Bay sets (`:400`), the military extension Blocks (`§6.4` at `:765`), the APVL ingest
   path (`:1009`), the carrier layout (`:1109`, "Layout is `[SOURCE-DEFINED]`; the numbers are
   not"), and OQ8's CV_APP split (`:1461`).
2. **A bracketed citation** — `[Annex §N]`, `[Coord §N]` — marks a clause that **is** grounded in a
   published source. "Rules, each verified" (`:475`) and "verified real practice" (`:1097`) mean
   exactly this. The Research Annex itself is **not in this repo** (`crc-sync/src/efsp/block-map.js:188`
   says so), so "verified" in this audit means: *the guide states it with a bracketed citation*.
3. **`[GAP]`** marks something the Annex could not establish. The rule is **do not guess — raise an
   Open Question** (`:33`). Two in the guide: APVL ingest (`:1009`, which also says model the SOURCE
   path as `[SOURCE-DEFINED]`) and scramble/interceptor priority ordering (`:1031`, "Do not
   implement … a priority *ordering*"). Also treat `:1211` ("do not encode '15 days' as if it were a
   current requirement") as a GAP-equivalent prohibition.
4. **The prohibitions** (`:31-33`): an implementer MUST NOT (a) present a `[SOURCE-DEFINED]`
   behaviour as real-world doctrine in code comments, UI text, wiki documentation or training
   material; (b) invent field names, state values or procedures and attribute them to FAA, DoD or
   NATO documents; (c) resolve a `[GAP]` by guessing.

Two consequences that trip people up, both load-bearing for this audit:

- **"Guide-sourced" is not "verified".** A table copied from a `[SOURCE-DEFINED]` guide section is
  still `[SOURCE-DEFINED]`. Example: `crc-sync/src/efsp/permission.js:342` calls DEPARTURE's owner
  table "guide-sourced", but it comes from §3.4's "Normally owned by" column, and §3.4 is tagged
  `[SOURCE-DEFINED]` in its heading (guide `:193`).
- **Everything the guide never mentions and the code invented is `[SOURCE-DEFINED]` too**, tagged
  or not: thresholds, radar figures, synthetic squawk blocks, datalink participant lists. There is
  no third category of "neutral engineering choice" once the text describes what a controller
  sees or does. (Pure plumbing — tick rates, cache sizes, retry backoff — is not behaviour; skip it.)

## 4. Classification scheme

Every finding gets exactly one class.

| Class | Meaning | Default action for L20 |
|---|---|---|
| `OK-MARKED` | SOURCE-defined, and carries `[SOURCE-DEFINED]` or an explicit equivalent ("our own choices, not doctrine") at the definition site; nothing nearby overclaims | none (add the literal token if missing — see Q1) |
| `UNMARKED-SD` | SOURCE-defined, silent about it. No overclaim, but a reader cannot tell it is ours | add a marker (code) or a provenance note (docs) |
| `PRESENTED-AS-DOCTRINE` | text claims or implies real-world authority for something unsourced. The D11 violation | reword (highest priority) |
| `DOCTRINE-CITED-OK` | text claims real-world authority, and the claim traces to a guide clause carrying `[Annex §]`/`[Coord §]` | none, or add the citation if the text lacks one |
| `GAP-HONOURED` | a `[GAP]` item is left unimplemented, or raises an indication only, as instructed | none |
| `GAP-VIOLATED` | code implements a guess at a `[GAP]` item | report; L20 flags to supervisor, does not silently delete |

### What counts as "presented as doctrine"

Any of these, applied to something that is not `DOCTRINE-CITED-OK`:

- the words **doctrine, FAA, DoD, NATO, JO 7110.65, AFI, NATOPS, real-world, real, standard,
  regulation, required by, mandatory, the rule** used as authority;
- **attributing a figure to a real facility or real equipment** ("Incirlik's field surveillance
  radar (40 nm …)");
- a **general statement about how real controllers or real military units work**, with no
  citation ("military control does not do collision avoidance the way ATC does");
- a refusal or reason line whose wording implies an external allocation or rule
  ("reserved for uncontrolled traffic").

What does **not** count: a plain label that names our own thing without claiming anything about the
real world (a button reading `Hand to Tower`, a Bay named `Pending`, a Block label `CID`). Those are
`UNMARKED-SD` at most, and see Q3 on whether they need anything at all. The word "real" meaning
"actual in this program" ("a real lifecycle stop", `docs/efsp-usage-guide.md:67`) is not a claim
either — note it only if the sentence also leans on a doctrine source.

### Severity (a column, not a class)

- **S1** — rendered UI text a controller reads (labels, reason/inhibit lines, refusal `detail`
  strings that reach the banner, tooltips/`title`, scope tags) or `docs/efsp-usage-guide.md`.
- **S2** — config file `_comment`s and ADR text the usage guide cites as its source.
- **S3** — code comments.

The criterion is "about what a controller reads" (`docs/efsp-wp6-plan.md:481-482`), so S1 comes
first in both the method and the output.

## 7. Method, step by step

Run everything from the repo root. Record each finding **the moment you find it**, straight into the
inventory file, rather than batching at the end.

### Step 1 — enumerate the marked items

```bash

grep -rIn 'SOURCE-DEFINED' docs/efsp-usage-guide.md
grep -rIn --exclude-dir=node_modules -iE 'not doctrine|our own (choice|figure)|squadron.s (own|operating)|must (never|not) be presented' crc-sync crc-desktop/app docs/efsp-usage-guide.md
```

comment whose behaviour is described as fact in the guide is one `OK-MARKED` (S3) plus one
`UNMARKED-SD` or `PRESENTED-AS-DOCTRINE` (S1). The S1 row is the one that matters.
