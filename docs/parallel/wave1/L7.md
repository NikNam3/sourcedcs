## 1. Mission

A forwarding-obligation alert (guide §4.6.1, ADR `0021`) is raised once and never cleared. The
server sends a fire-and-forget `efsp-obligation-alert`; the client stores it in a Map keyed by
`stripId`; nothing ever removes it. A Strip whose void-time clearance expired keeps its
`VOID TIME EXPIRED` badge after the controller re-clears it, and a client that reconnects after
the fact never learns about an obligation raised while it was away.

Make an obligation **state**, not an event: the server keeps the set of obligations due *right
now*, and sends that whole set in the existing `efsp-alerts` full-state message beside conformance
and STCA (ADR `0058`). Clearing is then simply the next message not listing it — the shape ADR
`0045` established for the correlation warning.

Also, while you own `forwarding-obligations.js`:
- make the WARNING→OVERDUE escalation of `ADVANCE_FORWARDING` actually reach the client (it never
  did: the de-dup key has no severity in it);
- give `recordMet()` its first honest caller (narrowly — see §5, step 5).

### Out of scope

- New obligation types, or changing *when* an obligation is due (`computeDueObligations` stays as it
  is; its existing tests must pass unchanged).
- A verification Mutation for `DATA_ONLY_VERIFICATION`, or an amendment-event feed for
  `AMENDMENT_INSIDE_30MIN` (both are ADR 0021's documented gaps and stay so).
- Metrics / dashboard: that is L5 (server) and L15 (client). L5 **reads**
  `obligationMonitor.getComplianceStats()`; keep its shape exactly `{ [type]: { met, missed } }`.
- Any restyle of the badge, `strip-view.js`, `bay-view.js`, `efsp-panel.css`. The render path stays;
  only where its data comes from changes.
- Per-session filtering of obligations (open question Q2).

## 4. Design

### The choice: (a) obligations ride `efsp-alerts`

Three shapes were on the table.

**(c) Records on the Board** (an `obligations` field on the Strip, re-stated by board deltas like
`strip.nla`). Rejected. An obligation is derived from Strip + FDR + clock + airspace state; it is not
something a controller wrote. Putting it on the Strip means either bumping `rev` outside a Mutation
(which `bay-view.js:2755–2757` forbids: it invalidates every controller's in-flight edit) or copying
the NLA-status re-statement machinery, which runs through `efsp-ws.js` and `index.js` — both L1's
shared files this wave. It would also push a board delta every time a 60-second amendment window
opens or closes.

**(b) Its own full-state message** (`efsp-obligations`). Works, but it duplicates exactly the
plumbing `efsp-alerts` already has: the stored last state, the per-session message builder, the
connect-time send, the client's wholesale replace and Bay re-render.

**(a) One more key in `efsp-alerts`.** Chosen:
- ADR 0058 made `efsp-alerts` the channel for "what is wrong right now", sent whole, cleared by
  omission. An obligation is exactly that.
- It is already **per session** (`_efspAlertsMsg`, ADR 0059). Obligations go to everybody for now,
  like conformance and like every Board broadcast; scoping them later is one line in that function
  (open question Q2).
- It is already sent **on connect**, so a reconnecting client gets current state — once the
  "only if it ever changed" gap (`ws-hub.js:410`) is closed (step 3).
- The client already re-renders every open Bay on it (`app.js:740–745`).

The cost of (a) is one trap: two producers on different cadences (1 s conformance/STCA, 15 s
obligations) now feed one message. `broadcastEfspAlerts` replaces `_efspAlerts` wholesale, so
whichever interval broadcasts must always pass **all three** keys, or it silently erases the other's.
Solve it with one server.js function that composes the state from all three monitors, used by every
caller (step 2).

### The record

Keyed per **Strip**, not per FDR — deliberately unlike correlation. Correlation is an identity
question and two replicas must not disagree (ADR 0045). An obligation is a procedural duty of the
Facility holding that Strip: the receiving side's `ADVANCE_FORWARDING` is not the sending side's.
Two replicas with different obligations are correct.

```js
// one entry in efsp-alerts.obligations
{ facilityId, stripId, obligationType, severity, dueAt, since }
```
- `since` — when this episode was first raised (mirrors conformance's `since`).
- `dueAt` — the value computed **when the episode was raised**, then held. `ETA_REVISION` and
  `AMENDMENT_INSIDE_30MIN` return `dueAt: now` from the pure function; recomputing it every tick
  would make every tick a "change" and re-broadcast forever. Change detection is on the key set and
  on `severity` only.
- Sorted by `stripId`, then `obligationType`, so the array is stable.

### Monitor semantics (replaces "alert at most once, ever")

`tick(now)` recomputes the whole due set and returns `true` iff it differs from the last one:
- a key that appears → new episode, `_recordMissed(type)` once, `since = now`;
- a key present before and now with a different `severity` → update (this is the escalation fix);
- a key no longer due, or whose Strip is DROPPED or gone → **removed** (the retraction).

`getAll()` returns the current array. `onAlert` goes away, and so do `_alerted` and `ALERTED_CAP`:
the set is bounded by live Strips.

"Missed" becomes *raised episodes*: an obligation that clears and later comes due again is counted
again. That is the honest reading (it was missed twice); record it in ADR `0067`.

### Prompt retraction after a Mutation

With only the 15 s tick, a Strip re-cleared by the controller keeps its badge for up to 15 s while
its `strip.nla` (re-stated immediately in the Mutation's own board delta) already says otherwise —
the "two answers to one question" `nla-status-monitor.js:26–38` warns about. So also re-evaluate
obligations right after any EFSP message that broadcast something: add a hook to `WsHub`
(`setOnEfspChange(fn)`), called in `_onMessage` after the broadcasts at `:503–519`, and wire it in
server.js to `if (obligationMonitor.tick()) broadcastAlerts()`. This keeps both renderings immediate
on a Mutation and both on the 15 s tick for the clock. (Default of Q4; it also makes the e2e spec fit
inside Playwright's 20 s test timeout.)

### `recordMet()` gets a caller — inside the monitor, for two types only

ADR 0021 rejected "any coordination Mutation after an alert counts as met" because it overstates
compliance. That stays rejected. "Met" must mean *done before it was due*, which needs the monitor
to have seen the obligation **pending** (clock running, not yet due) and then seen the satisfying
condition before `dueAt`. Only two types have a lead window the monitor can observe:

| Type | Pending while | Met when, before `dueAt` |
|---|---|---|
| `ADVANCE_FORWARDING` | ARRIVAL, no `strip.coordination`, ETA known, `now < ETA − 15 min` | the same live Strip now has `strip.coordination` |
| `VOID_TIME_EXPIRED` | DEPARTURE, `HELD`, `fdr.assigned.voidDeadlineUtc` set, `now < voidDeadlineUtc` | the same Strip is live and no longer `HELD` (the flight got away) |

Anything else that ends a pending window (Strip dropped, ETA removed, release state changed) is
neither met nor missed — forget it. `ETA_REVISION`, `AMENDMENT_INSIDE_30MIN`,
`DATA_ONLY_VERIFICATION` and `UNACTIVATED_AIRSPACE_ENTRY` are due the moment they exist; they have no
"met" and stay missed-only. Say so in ADR `0067` and in `docs/wip/L7.md` for L5.

The caller is `ForwardingObligationMonitor.tick()` itself — nowhere else. No Board or dispatch code
changes.

### ADR

This changes three things ADR `0021` decided in writing: the `efsp-obligation-alert` message type,
"de-duplicated, alerted at most once", and "`recordMet` not wired". A bugfix that silently
contradicts a standing ADR leaves the next reader misled. **Write ADR `0067`**
(`docs/adr/0067-obligations-are-state.md`, Context / Decision / Alternatives considered /
Consequences). It names `0021` and each statement of it that no longer holds, covering the three
points plus "missed = raised episodes" and the two met-able types. **Never edit `0021`** — an ADR is
not edited once committed; corrections are new prose (`docs/parallel/decisions.md` P4, ADR `0060`).
`0014`'s "Update" section is historical, not a precedent. (Settled: decisions.md D1.)

## 8. Traps

- **Composing the message.** `broadcastEfspAlerts` stores whatever it is given as the whole state.
  Any call that passes only `{ conformance, stca }` wipes obligations for a second, and a 15 s tick
  passing only obligations wipes STCA. One function, every caller.
- **`dueAt: now`.** `ETA_REVISION` and `AMENDMENT_INSIDE_30MIN` report the current time as `dueAt`.
  Comparing `dueAt` for change detection re-broadcasts every tick. Hold the episode's first value.
- **`AMENDMENT_INSIDE_30MIN` now shows for about a minute** (it is true for 60 s after
  `fdr.updatedAt`), where before it stuck forever. That is the pure function's definition, not a new
  bug; record it (Q3). Do not latch it.
- **`_efspAlerts` starts undefined.** Without the constructor init and unconditional connect send,
  "reconnect shows current state" fails exactly after a crc-sync restart with no alerts.
- **The hook runs inside `_onMessage`.** Any throw there would lose the sender's round trip; guard it.
  It must run *after* `result.broadcast` so the client sees the Strip change before the alert change.
- **Do not key by `fdrId`.** ADR 0045's lesson is about identity; obligations are per Strip replica.
- **Old tests encode old semantics.** "alerts once, even across repeated ticks" is still right for an
  unchanged obligation (`tick()` false, one entry) — but "stays raised" is not. Do not preserve an
  assertion that the badge survives a resolution.
- **e2e injection vs the real server.** `l4-badges`'s injected obligation is unknown to crc-sync; any
  real `efsp-alerts` (e.g. a hook tick after the test's own Mutation that changed something) replaces
  it. Assert immediately after injecting, as the spec already does.
- **15 s is the clock's latency, not the Mutation's.** A deadline passing is picked up by the 15 s
  tick; a controller's action by the hook. Tests should drive `tick(now)` with explicit clocks — no
  real timers (ADR 0021's discipline).
- **Never :3000.** E2E uses 3017/3117 only.
