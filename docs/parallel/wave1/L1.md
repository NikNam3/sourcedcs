## 2. Mission

**Done means:** a controller at `OPS` can suspend an INCIRLIK runway for a barrier reconfiguration,
change its arresting-gear states, and resume it only through an attributable inspection; while it is
suspended, every Strip assigned to it has its takeoff/landing NLA inhibited — on the button **and** on
the drag path — with a reason string that reaches the client through the existing `nla` stamp; `TWR`
cannot begin a runway change until `OPS` **and** `APP` have both acknowledged it; every field-state
op (including refusals and `STALE_REV`) is in the Mutation log; field state rides its own
`fieldStateSeq` / `efsp-field-state-delta` and the snapshot; and a crc-sync restart mid-suspension
comes back `SUSPENDED_*`. §13's two acceptance lines are asserted **word for word** in
`tests/efsp-scenario-field-state.test.mjs`, and the D21 case is in `tests/efsp-permission.test.mjs`.

### 5.1 Store: one instance, records keyed by `facilityId` (settled)

- New `crc-sync/src/efsp/field-state-store.js`, class `FieldStateStore`. **One instance** for the
  whole server, **one record per Facility that has a runway inventory** (today: INCIRLIK only).
  Not one store per Facility: nothing about a runway is ever handed across a boundary, so
  `AirspaceStore`'s single-instance reasoning applies (§9.1: *"the field-state model is a peer of
  the Strip model, not a subsidiary of it"*).
- **`rev` is at the FieldState (Facility) level**, not per runway. Two controllers reconfiguring at
  once collide on `STALE_REV` — correct, not costly.
- Constructed **before** `index.js`'s facility loop, so `rules.fieldStateFor` is a plain closure.
- Constructor: `new FieldStateStore(facilityConfig)` — inject the config module (airspace's
  `new AirspaceStore(airspaceConfig, …)` precedent) so tests can pass a fixture object exposing
  `getFacilityIds()` and `getFacilityConfig(id)`.

### 5.2 Config inventory (settled: shipped config in `DEFAULT_CONFIG` only)

Add one key to INCIRLIK's `DEFAULT_CONFIG` (after `aitAuthorized`, line 191). Other Facilities get
no key (absence = no field-state record). *Default shape* (the plan names the keys
`runwayChangeAcknowledgers` and `fieldState.inspectionAuthorityPositionId`; the container name
`fieldState` is chosen so L12/L13 can later add `hotCargoPad`/`alertPad` config beside `runways`):

```js
// [SOURCE-DEFINED] — every value below is squadron data, not doctrine (see ADR 0061).
fieldState: {
  runways: [
    { runwayId: '05', rackId: 'rwy-05', reciprocalRunwayId: '23',
      arrestingGear: [
        { gearId: 'BAK12-05', type: 'BAK_12', position: 'APPROACH_END', distanceFt: 1500, initialState: 'UP' },
      ] },
    { runwayId: '23', rackId: 'rwy-23', reciprocalRunwayId: '05',
      arrestingGear: [
        { gearId: 'BAK12-23', type: 'BAK_12', position: 'APPROACH_END', distanceFt: 1500, initialState: 'UP' },
      ] },
  ],
  activeRunwayId: '05',                      // seed only; runtime value lives in the store
  runwayChangeAcknowledgers: ['OPS', 'APP'], // guide §9.7 rule 3; OPS stands in for the SOF
  inspectionAuthorityPositionId: 'OPS',      // narrows FIELD_STATE_OP_OWNERS.CompleteInspection; cannot widen
},
```

Rules:
- Enums (export from `field-state.js`): gear `type ∈ {BAK_12, E_5, OTHER}`, `position ∈
  {APPROACH_END, DEPARTURE_END, OVERRUN}`, gear `state ∈ {UP, DOWN, OUT_OF_SERVICE}` — the guide's
  §9.7 schema verbatim.
- `gearId` unique per Facility; `runwayId` unique per Facility. Each **physical** cable is declared
  **once**, on the runway whose threshold it is nearest, with `position` relative to that runway
  (*default*, see Q1).
- **`validateConfig` rejects a malformed inventory** (non-array `runways`, missing/duplicate
  `runwayId`/`gearId`, an enum value outside the set, `reciprocalRunwayId` naming no runway,
  `activeRunwayId` naming no runway, `runwayChangeAcknowledgers` / `inspectionAuthorityPositionId`
  naming a Position not in `positions`) — the radar-selector precedent (389–402): malformed can never
  work in any deployment. Put the shape check in a pure `validateFieldStateInventory(fieldState,
  positions)` in `field-state.js` returning a problem string or null, called from `validateConfig`.
- **Cross-references only warn, never reject** (settled): a runway whose `rackId` is not a rack of a
  Bay with `impliesState: 'RUNWAY_QUEUE'`, and vice versa a runway-queue rack no runway names. Pure
  `runwayInventoryWarnings(config)` → `string[]`, logged with `console.warn('[efsp-facility-config]
  …')` from `_loadOne` (or once at startup from `index.js`, *default*: `_loadOne`, after the merged
  config is chosen, so it covers the defaults too).
- Config owns **which runways and gear exist**. Status, gear state, suspension, inspection,
  `activeRunwayId` and `runwayChange` are **store state** — otherwise `setFacilityConfig` (which
  persists the merged config to `state/`, ADR 0048) would pin a runway's status on disk forever.
- `field-state.js` must **not** `require('./facility-config')` (facility-config will require it →
  cycle). It is pure.

### 5.3 The record schema (every field)

What `getFieldState(facilityId)` returns (and what the snapshot/delta carry). Stored fields vs.
derived-at-read are marked.

```js
{
  facilityId: 'INCIRLIK',              // stored, key
  rev: 0,                              // stored; bumped by every successful op (one rev per op, however many runways it touches)
  activeRunwayId: '05',                // stored; seeded from config; changed only by CompleteRunwayChange
  runways: [{                          // stored state, merged at read with config definition fields
    runwayId: '05',
    rackId: 'rwy-05',                  // from config (read-merge)
    reciprocalRunwayId: '23',          // from config (read-merge)
    status: 'OPEN',                    // stored: OPEN | CLOSED | SUSPENDED_BARRIER_CHANGE | SUSPENDED_INSPECTION
    arrestingGear: [{                  // type/position/distanceFt from config, state stored
      gearId: 'BAK12-05', type: 'BAK_12', position: 'APPROACH_END', distanceFt: 1500,
      state: 'UP',                     // stored: UP | DOWN | OUT_OF_SERVICE
    }],
    suspension: null,                  // stored: { cause: 'BARRIER_CHANGE'|'RUNWAY_CHANGE', since, by, positionId, note } while SUSPENDED_*
    closure: null,                     // stored: { since, by, positionId, reason } while CLOSED
    lastInspection: null,              // stored: { at, by, positionId, note } — rule 2's attribution; survives reopening
  }],
  runwayChange: null,                  // stored: see 5.5
  runwayChangeInProgress: false,       // DERIVED at read (guide §9.7 schema's bool): runwayChange?.state ∈ {IN_PROGRESS, PENDING_INSPECTION}
  hotCargoPad: null,                   // stored null — §12 "a deferral leaves its fields present"; L12 populates. No op touches it.
  alertPad: null,                      // stored null — L13 populates. No op touches it.
  transitions: [],                     // stored, append-only: { op, runwayId?, from?, to?, gearId?, at, by, positionId, selfCoordinated? }
  updatedAt: null, updatedBy: null,    // stored
}
```

- Stored records hold only state keyed by `runwayId`/`gearId`; `getFieldState` merges the config
  definition in (airspace's `getAirspace` does `{...record, definition}` — flatten here so a runway
  row is self-describing). `getAll()` → every Facility record. `getFieldState(unknown)` → `null`.
- **Rule-1 read path must be cheap**: `nlaStatusFor` runs for every Strip on every stamp. Give the
  NLA rule a non-cloning accessor (*default*: `fieldStateStore.runwayStatusView(facilityId)` returning
  an internal read-only `{ runways: [{runwayId, rackId, reciprocalRunwayId, status, suspension}] }`
  cached and invalidated in `_touch`), or document that `getFieldState` is cloned per call and
  measure. Never let a caller mutate internal state through it.

### 5.4 Runway status machine — `LEGAL_TRANSITIONS` (rules 1–2, the barrier family)

Exported from `field-state.js` in `airspace-store.js`'s shape:

```js
const RUNWAY_STATUSES = ['OPEN', 'CLOSED', 'SUSPENDED_BARRIER_CHANGE', 'SUSPENDED_INSPECTION'];
const LEGAL_TRANSITIONS = {
  OPEN:                     ['CLOSED', 'SUSPENDED_BARRIER_CHANGE', 'SUSPENDED_INSPECTION'], // the last only via CompleteRunwayChange
  CLOSED:                   ['OPEN'],
  SUSPENDED_BARRIER_CHANGE: ['SUSPENDED_INSPECTION'],   // NOT 'OPEN' — this absent entry IS rule 2
  SUSPENDED_INSPECTION:     ['OPEN'],
};
```

**`SUSPENDED_BARRIER_CHANGE → OPEN` is not a legal edge — that absent entry *is* rule 2**, enforced
structurally (settled). Also absent on purpose (*default*): `SUSPENDED_* → CLOSED`. If it existed,
`BeginBarrierChange → CloseRunway → OpenRunway` would reopen a re-rigged runway **without an
inspection** — a bypass of rule 2 through a side door. Write a graph-search test: *every path in
`LEGAL_TRANSITIONS` from `SUSPENDED_BARRIER_CHANGE` to `OPEN` passes through `SUSPENDED_INSPECTION`.*

**Reciprocal mirroring** (*default*, Q1): `05` and `23` are two directions of one pavement. Every
status change applied to a runway is applied, in the same op, same `rev`, same audit entry, to its
`reciprocalRunwayId`. Gear state is keyed by `gearId` and not duplicated.

### 5.5 The ops, their owners and preconditions

All ops arrive as `efsp-field-state-mutation` (§5.9) and go through `FieldStateStore.apply(mutation,
actingPositionId, by)`. Every refusal carries the current record (`fieldState`) back, like airspace.
Reason codes: **reuse existing ones only** — `VALIDATION_ERROR`, `PERMISSION_DENIED`, `STALE_REV`,
`NOT_FOUND` (plus `NOT_HOLDING_POSITION` from the wire layer). `crc-desktop`'s refusal banner maps
exactly the existing set.

**Barrier family (rules 1–2):**

| Op | Owner (table) | Preconditions | Effect |
|---|---|---|---|
| `BeginBarrierChange {runwayId, note?}` | `OPS` | runway exists; `_canGo(status,'SUSPENDED_BARRIER_CHANGE')` (i.e. `OPEN`) | status → `SUSPENDED_BARRIER_CHANGE` (+ reciprocal); `suspension = {cause:'BARRIER_CHANGE', since, by, positionId, note}` |
| `SetGearState {gearId, state}` | `OPS` | gear exists; `state` ∈ enum; the gear's runway is **`SUSPENDED_BARRIER_CHANGE`** (legal *only* then — settled) | gear state set; transition logged with from/to |
| `CompleteBarrierChange {runwayId}` | `OPS` | status `SUSPENDED_BARRIER_CHANGE` | → `SUSPENDED_INSPECTION` (+ reciprocal); `suspension` kept (cause unchanged) |
| `CompleteInspection {runwayId, note?}` | `OPS` ∩ `inspectionAuthorityPositionId` | status `SUSPENDED_INSPECTION` | → `OPEN` (+ reciprocal); `suspension = null`; `lastInspection = {at, by, positionId, note}` (**rule 2's attribution**); if a runway change is `PENDING_INSPECTION`, mark this runway inspected (5.6) |
| `CloseRunway {runwayId, reason?}` | `OPS` | status `OPEN` | → `CLOSED` (+ reciprocal); `closure = {…}` |
| `OpenRunway {runwayId}` | `OPS` | status `CLOSED` | → `OPEN` (+ reciprocal); `closure = null` |

**Runway-change family (rule 3) — its own two-acknowledgement machine (settled):**

`board-store.js`'s coordination primitives are structurally unusable (Strip-attached; cross-Facility
by construction — `_applyCoordinationPropose` refuses a same-Facility target and TWR/OPS/APP are all
INCIRLIK; one-proposer/one-responder with no AND). So:

```
null ─ProposeRunwayChange(TWR)→ PROPOSED ─(every acknowledger has acked, any order)→ ACKNOWLEDGED
     ─BeginRunwayChange(TWR)→ IN_PROGRESS ─CompleteRunwayChange(TWR)→ PENDING_INSPECTION
     ─(CompleteInspection by OPS on each runway in the inspection set)→ null
PROPOSED/ACKNOWLEDGED ─RejectRunwayChange(an acknowledger)→ REJECTED (terminal)
PROPOSED/ACKNOWLEDGED ─WithdrawRunwayChange(TWR)→ REJECTED (terminal, cause WITHDRAWN)   ← default, Q3
```

`runwayChange` record:

```js
{
  changeId,                              // crypto.randomUUID()
  state: 'PROPOSED' | 'ACKNOWLEDGED' | 'IN_PROGRESS' | 'PENDING_INSPECTION' | 'REJECTED',
  fromRunwayId, toRunwayId,              // from = activeRunwayId at propose time
  proposedBy, proposedPositionId, proposedAt, note,
  acknowledgers: ['OPS', 'APP'],         // FROZEN from config at propose time
  acks: { OPS: null | {by, at, selfCoordinated}, APP: null | {…} },
  rejected: null | { by, positionId, at, cause: 'REJECTED' | 'WITHDRAWN', note },
  beganAt, beganBy, completedAt, completedBy,
  pendingInspection: [runwayId, …],      // set by CompleteRunwayChange, drained by CompleteInspection
}
```

| Op | Owner (table) | Preconditions |
|---|---|---|
| `ProposeRunwayChange {toRunwayId, note?}` | `TWR` | `runwayChange` is `null` or `REJECTED` (a REJECTED record is replaced, after being appended to `transitions`); `toRunwayId` exists and ≠ `activeRunwayId`; target not `CLOSED` |
| `AckRunwayChange` | `OPS`, `APP` (table) **and** acting ∈ `runwayChange.acknowledgers` | state `PROPOSED`; this acknowledger has not acked. When every acknowledger has acked → `ACKNOWLEDGED`. `selfCoordinated = (by === proposedBy)` — guide §4.8.3, airspace's `_approveActivation` precedent (recorded, not refused) |
| `RejectRunwayChange {note?}` | `OPS`, `APP` ∩ acknowledgers | state `PROPOSED` or `ACKNOWLEDGED` → `REJECTED` |
| `WithdrawRunwayChange {note?}` (*default*) | `TWR` | state `PROPOSED` or `ACKNOWLEDGED` → `REJECTED` with `cause: 'WITHDRAWN'` |
| **`BeginRunwayChange`** | `TWR` | **exactly one guard: `runwayChange && runwayChange.state === 'ACKNOWLEDGED'`**. → `IN_PROGRESS` |
| `CompleteRunwayChange` | `TWR` | state `IN_PROGRESS`; inspection set = `toRunwayId` + its reciprocal (and `fromRunwayId` + reciprocal if a different surface); refuse with a reason naming the runway if any is `SUSPENDED_BARRIER_CHANGE` or `CLOSED`. Each `OPEN` one → `SUSPENDED_INSPECTION` with `suspension.cause = 'RUNWAY_CHANGE'`; `activeRunwayId = toRunwayId`; state → `PENDING_INSPECTION`; `pendingInspection` = the set |

**§13's second acceptance criterion is `BeginRunwayChange`'s single `state === 'ACKNOWLEDGED'`
guard — write that assertion first** (settled). The *interpretation* that `CompleteRunwayChange`
suspends the inspection set (so that the plan's "`CompleteInspection` per runway" has a
`SUSPENDED_INSPECTION` runway to act on, and so rule 1 inhibits the new runway until it is
inspected) is this briefing's reading of the plan's arrow; record it in the ADR.

**Rules 1–2 and rule 3 are separate families** (settled — conflating them is the easy mistake): rule
3 changes which runway is active; rules 1–2 reconfigure gear. They meet at exactly one point:
`CompleteInspection` both reopens a runway and drains `pendingInspection`. When
`pendingInspection` becomes empty the change record is appended to `transitions` and
`runwayChange = null`.

### 5.6 Permission (settled): `canActOnFieldState(actingPositionId, opKind)` + `FIELD_STATE_OP_OWNERS`

In `permission.js`, beside `canDeclareMarsa` (after line 285), with the exports extended (419–425):

```js
const FIELD_STATE_OP_OWNERS = {
  BeginBarrierChange:    ['OPS'],
  SetGearState:          ['OPS'],
  CompleteBarrierChange: ['OPS'],
  CompleteInspection:    ['OPS'],   // the CEILING; config inspectionAuthorityPositionId may narrow, never widen
  CloseRunway:           ['OPS'],   // default Q4
  OpenRunway:            ['OPS'],
  ProposeRunwayChange:   ['TWR'],
  WithdrawRunwayChange:  ['TWR'],   // default Q3
  BeginRunwayChange:     ['TWR'],

  const owners = FIELD_STATE_OP_OWNERS[opKind];

```

- **Exactly two parameters** — D21 by construction; test `canActOnFieldState.length === 2`.
- **Not an `OP_KINDS` entry** (settled): test that no `FIELD_STATE_OP_OWNERS` key is in `OP_KINDS`
  (copy `efsp-permission.test.mjs:388`).
- A `USING_AGENCY` (RANGE) Position is refused by absence from every row. That is sufficient here
  because the table is explicit (no `.filter()` over anything).
- The narrowing checks (acting ∈ `runwayChange.acknowledgers`; acting === `inspectionAuthorityPositionId`)
  live **in the store**, which reads config — `permission.js` stays static.
- Attribution needs no new mechanism: `actingPositionId` is session-bound (ADR 0029); the store
  stamps `{by, positionId}` on `lastInspection`, acks, suspension, closure and every transition, and
  writes the Mutation log.
- The comment must say plainly that inspection authority is **not** configurable-wider — widening
  needs config-derived permissions (ADR 0035's shape), a bigger change than this deliverable.

### 5.7 Rule 1 → `nla.js` via `fieldStateFor()` (settled)

- New pure `crc-sync/src/efsp/field-state.js` (the `correlation-match.js`→`correlation-store.js`
  relationship). Holds at least: `RUNWAY_STATUSES`, `LEGAL_TRANSITIONS`, `canGo(from, to)`, the gear
  enums, `RUNWAY_CHANGE_STATES`, `normalizeRunwayId(text)`, **`runwayIdForStrip(strip, fdr,
  fieldState)`**, **`runwayInhibitFor(strip, fdr, fieldState)`**, `validateFieldStateInventory`,
  `runwayInventoryWarnings`. Module header must say it is pure and why (L12 will add a pure function
  here; say so).
- **`runwayIdForStrip`: rack first, FDR field second** (settled). `strip.rackId` is where the
  controller *put* the Strip; the FDR field is filed intent. Rack: the runway whose `rackId ===
  strip.rackId`. Else FDR: DEPARTURE → `fdr.filed.departureRunway`, ARRIVAL →
  `fdr.assigned.landingRunway`, normalized (*default* `normalizeRunwayId`: trim, uppercase, strip a
  leading `RWY`/`RW` and spaces, left-pad a single leading digit — `'5'`→`'05'`, `'rwy 23'`→`'23'`,
  `'5L'`→`'05L'`) and matched against configured `runwayId`s. No match → `null`.
- **`runwayInhibitFor`**: `null` (no inhibit) when `fieldState` is null, the runway is unresolvable, or
  its status is `OPEN`. Otherwise a reason string that **names the runway and the cause**
  (*default* wordings: `runway 05 suspended — barrier reconfiguration in progress`, `runway 05
  suspended — awaiting inspection`, `runway 05 closed` — see Q2 for CLOSED). **Unknown or
  unresolvable runway must not inhibit — fail open** (settled).
- `ctx.fieldStateFor()` — added to `_normalizeCtx` (default `() => null`), threaded by
  `board-store.js`'s `_nlaCtx()` (`fieldStateFor: this._rules.fieldStateFor`), supplied per Facility
  by `index.js` (`fieldStateFor: () => fieldStateStore.<accessor>(facilityId)`). CENTER/TACTICAL
  return `null` → fail open.
- **Cases** (settled), each checked *before* the existing occupancy check in that case:
  - DEPARTURE `TAXI` (→ `RUNWAY_QUEUE`), `RUNWAY_QUEUE` (→ `LUAW`), `LUAW` (→ `DEPARTED`);
  - ARRIVAL **`HANDED_TO_TOWER` (→ `FINAL`)**.
  - **Not `FINAL → LANDED`.** That transition is an *observation* that the aircraft touched down;
    inhibiting it makes the board lie about an event that already happened and strands a landed
    aircraft with no legal transition. Assert this with a test.
  - Nothing else (no OVERFLIGHT, no MISSION, no other state).
- Replace the three placeholder comments (242–244, 251, 255–256) with what is now true, **and say
  explicitly that runway *occupancy* is still not implemented** (§9.7 has no occupancy field; §3.5's
  `RUNWAY_QUEUE` row cites no section — inventing one is D11). Update the module comment (28–31) for
  §9.7 only.

### 5.8 Rule 5: own `fieldStateSeq`, own `efsp-field-state-delta`, audited (settled deviation)

The guide says *"broadcast on the Board sequence like any other Mutation"*. **Deliberately not
followed literally** — the reasoning goes in ADR 0061 (copy it from the WP6 plan's rule-5 paragraph):
`boardSeq` is the index into `board-store.js`'s `_log` ring that `getDeltaSince` (163) replays; all
three literal readings break (field state inside `BoardStore` contradicts §9.1; bumping `boardSeq`
from outside leaves a gap `getDeltaSince` cannot fill and the client cannot detect; riding
`efsp-board-delta` without bumping silently drops field state from resync, so **a controller
reconnecting after a suspension sees an `OPEN` runway**). The sentence's real job is the contrast
(broadcast and audited, not a fire-and-forget alert), which the Airspace/Correlation shape honours.

- Store has `_seq` + `get currentSeq()`; bumped in `_touch`.
- Delta: `{ version: 1, type: 'efsp-field-state-delta', fieldStateSeq, fieldStates: { updated: [record] } }`.
- Snapshot: append `fieldStates: ctx.fieldStateStore ? ctx.fieldStateStore.getAll() : []`.
- **No `efsp-resync` branch** (matches airspace/correlation/MARSA; a reconnect gets the snapshot).
- **Audit every op, success and refusal, including `STALE_REV` and `NOT_FOUND`** (follow correlation,
  not airspace). Entry: `{ clientMutationId, op, fieldStateFacilityId, runwayId: op.runwayId ?? null,
  actingPositionId, actorId, at, ok, reason, detail, before, after }` — its own id field name
  (`fieldStateFacilityId`), because Mutation-log readers key on whichever id is present
  (`stripId`/`airspaceId`/`fdrId`/`marsaId`) and board entries carry no `facilityId`.
- **Getting the new inhibit reasons onto Strips immediately:** a field-state op changes the `nla`
  status of Strips it never touched (the `_handleSetPositions` problem, 566–577). *Default*: after a
  successful op, `_handleFieldStateMutation` calls `ctx.nlaStatusMonitor && ctx.nlaStatusMonitor.tick()`
  — it re-stamps only the Strips whose status moved and broadcasts them through the existing
  `onDelta` → `wsHub.broadcastEfspBoardDelta` (wired at `server.js:452`), with no `ws-hub.js` edit.
  Without it the reason reaches the client within 15 s anyway (the sweep), which is too slow for
  "with the reason shown". In tests, capture via `efsp.nlaStatusMonitor.setOnDelta(fn)`.

### 5.9 Wire contract

Inbound:
```js
{ version: 1, type: 'efsp-field-state-mutation', clientMutationId, facilityId /* default INCIRLIK */,
  baseRev, actingPositionId, op: { kind, runwayId?, gearId?, state?, toRunwayId?, note?, reason? } }
```
`_handleFieldStateMutation(ctx, session, msg, persist)`, in this order:
1. `ctx.fieldStateStore` missing → ack `ok:false, VALIDATION_ERROR, 'no field-state store'`.
2. `facilityId = msg.facilityId || DEFAULT_FACILITY_ID`; no record for it → `NOT_FOUND` (audited by
   the store).
3. **Per-Facility session check** (copy 155–158): `ctx.positionStoreFor(facilityId).primaryOf(
   msg.actingPositionId) !== session.controllerId → NOT_HOLDING_POSITION`. **Not** "Primary
   somewhere" (settled: a field has exactly one Facility; OPS at INCIRLIK must not suspend a runway
   elsewhere). The comment should note this is now the **fifth** dispatch path carrying ADR 0029.
4. `permission.canActOnFieldState(msg.actingPositionId, op.kind)` false → `PERMISSION_DENIED`.
   (Audit this refusal too — either call a store method that audits, or refuse inside `apply`; the
   *default* is to let `apply` run the table check itself as well, so a refusal is always audited.)
5. `store.apply({clientMutationId, facilityId, baseRev, op}, actingPositionId, controllerId)`;
   `persist()` on ok.
6. Ack `{ version, type: 'efsp-field-state-ack', clientMutationId, ..._subject(msg), facilityId,
   ok, fieldState, reason, detail, fieldStateSeq }`; on ok also `broadcast` = the delta; then
   `nlaStatusMonitor.tick()`.

`_subject`: add `case 'efsp-field-state-mutation': return { facilityId: msg.facilityId, runwayId:
msg.op && msg.op.runwayId };` just before `default`.

### 5.10 Persistence and restore

- `_persist` payload: append `fieldStates: fieldStateStore ? fieldStateStore.snapshot() : []`.
- `_restore`: after MARSA (399), `if (fieldStateStore) fieldStateStore.restore(data.fieldStates);`.
- `restore(data)` rules (*default*, config-vs-state reconciliation like `airspaceStore.restore`):
  a record for a Facility with no inventory any more is skipped; a runway no longer configured is
  dropped; a newly configured runway starts `OPEN` with gear at `initialState`; a gear id no longer
  configured is dropped; a stored gear state not in the enum resets to `initialState` with a warn; a
  `runwayChange` naming a runway no longer configured is cleared with a `console.warn`.
- **A suspension survives a restart intact** — `SUSPENDED_BARRIER_CHANGE` comes back
  `SUSPENDED_BARRIER_CHANGE`, with its `suspension` attribution, and the NLA is still inhibited on
  the reborn Board. The MARSA precedent (ADR 0051): a recorded fact made by a person is not made
  untrue by a crc-sync restart; coming back `OPEN` would hand the next controller a lie (§4.8.3).
  Contrast correlation, which resets because a DCS track id genuinely is re-minted.
- `_seq` is not persisted (airspace precedent); clients resync from the snapshot.
- Position occupancy is ephemeral (ADR 0029), so the restart test must re-declare the crew on the
  reborn facade before acting.

## 11. Open questions (with recommended defaults — take the default if unanswered, log it)

**Q1 — Are `05` and `23` two runways or two directions of one?** The config and the plan treat
runway records as rack-per-runway (`rackId: 'rwy-05'`), i.e. per *direction*. Physically they are one
pavement with the same cables: suspending 05 for a barrier change while 23 stays `OPEN` is wrong, and
a cable listed under both would be two answers to one gear state.
- (a) Independent directions (literal plan): simplest; physically wrong — OPS could suspend 05 while
  23 launches.
- (b) **Directions + `reciprocalRunwayId`; status ops mirror to the reciprocal in one op; each
  cable declared once, keyed by `gearId`.** Small, keeps the plan's shape.
- (c) Records per physical surface with `ends`/`rackIds[]`: cleanest model, but changes the plan's
  settled `rackId` shape and the runway-change semantics.
**Default: (b).**

**Q2 — Does `CLOSED` inhibit NLA?** Rule 1 names only `SUSPENDED_*`; `nla.js`'s own TAXI comment
calls the missing check "runway-unavailable".
- (a) Only `SUSPENDED_*` (literal rule 1).
- (b) **`SUSPENDED_*` and `CLOSED`, reason `runway 05 closed`.** A closed runway is at least as
  unavailable, and launching onto one is the worse error.
**Default: (b)**, stated in the ADR as going beyond rule 1's letter.

**Q3 — Can TWR withdraw its own proposal?** The plan's machine has only `REJECTED` via the
acknowledgers. Walking the request ("wind's backed, cancel the change") finds TWR stuck until OPS or
APP rejects for it.
- (a) No — only acknowledgers reject.
- (b) **Yes — `WithdrawRunwayChange` (TWR, from `PROPOSED`/`ACKNOWLEDGED`) → `REJECTED` with
  `cause: 'WITHDRAWN'`.**
**Default: (b).** Nothing after `BeginRunwayChange` can be withdrawn (the change is physically under
way; it must be completed and inspected).

**Q4 — Who may `CloseRunway`/`OpenRunway`?** Real practice: AMOPS owns airfield status; the tower can
suspend runway operations for an immediate hazard.
- (a) **OPS only.**
- (b) OPS and TWR for Close, OPS only for Open.
**Default: (a)** — narrower is safer and trivially widened later; note (b) in the ADR.

**Q5 — Should NLA queue a departure into the rack matching its filed runway?** Today
`_applyInvokeNla` uses `rackIds[0]` (`rwy-05`) regardless (T6), which makes rack-first resolution judge
every NLA-queued departure against 05.

  L1's file list — `board-store.js` is `_nlaCtx` only.)
- (b) Change `_applyInvokeNla`/`_relocateForImpliedState` to pick the rack whose runway matches the
  FDR (a board-store change needing supervisor sign-off).
**Default: (a)**, flagged prominently in `docs/wip/L1.md` as a finding for the supervisor.

**Q6 — Initial `activeRunwayId` and shipped gear.** Both are squadron data; the airspace and stereo
tables ship empty for exactly that reason (D11).
