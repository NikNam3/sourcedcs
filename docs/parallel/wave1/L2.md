## 1. Mission

Deliver guide §9.4, *Military Training Routes*, as **WP6 plan Phase 6** describes it
(`docs/efsp-wp6-plan.md:449-470`). In one lane:

1. Six new Blocks on **all three ATC Roles** (DEPARTURE, ARRIVAL, OVERFLIGHT):
   `9G-MTR` / `9G-ENTRY` / `9G-TIME` (guide `M10`) and `9H-EXIT` / `9H-TIME` / `9H-ALT`
   (guide `M11`), each plain `fdr`-routed to one of the six `fdr.military.mtr.*` fields that
   ADR `0052` already seeds as null.
2. The six `military.mtr.*` paths in `fdr-store.js`'s `WRITABLE_PATHS`, with server-side
   normalisation/validation of the two times and the altitude.
3. `MILITARY_BLOCK_NAMESPACE`'s `M10`/`M11` rows turned from the `9G-*`/`9H-*` wildcard into the
   real ids, and the drift tests extended so they check them.
4. The client mirror (labels, Block Map order), their placement on Layout C's per-Position field
   grid (ADR `0056`), with **`M11`'s exit fix and exit estimate placed prominently** — the guide's
   one explicit design instruction for this deliverable.
5. §9.4's **lost-comms rule as a rendered advisory, not a computation** (the plan's own words),
   placed so it does not break ADR `0058`'s "show nothing when nothing is wrong".
6. ADR `0062`, a sortie scenario, reachability/parity/field-list tests, a Playwright check with
   screenshots, and a hand-walked pilot request (*"request a different exit fix"*) written up in
   `docs/wip/L2.md`.

The guide text you are implementing, whole (`EFSPImplementationGuide.md:1011-1015`):

> ### 9.4 Military Training Routes
> Fields per §6.4 M10/M11. The two that matter operationally are **exit fix estimate** and
> **requested altitude after exit** — these are precisely what a controller asks for by voice and
> must post `[Annex §13.4]`.
>
> Lost-comms rule to implement as an advisory: separate assuming the aircraft maintains **the
> higher of** the minimum IFR altitude for each remaining segment **or** the highest altitude in
> the last clearance.

And the §6.4 rows (`EFSPImplementationGuide.md:780-781`):

> | M10 | MTR designator / entry fix / entry time | §9.4 |
> | M11 | MTR exit fix / exit estimate / requested altitude after exit | §9.4 — the two items a controller asks for by voice |

### Out of scope

- **Any MTR geometry, route table, or MTR designator grammar.** No IR/VR/SR route database exists
  in this repo; inventing one, or inventing a format rule for designators or fix names, is defect
  **D11 Doctrine fabrication** (guide `:1484`). Free text in, free text out.
- **Computing the lost-comms altitude.** There is no minimum-IFR-altitude data for any segment.
  The plan (`docs/efsp-wp6-plan.md:466-470`) is explicit: state the rule, show the half we have.
- **Wiring MTR data from the ATO** (that is L3's parser mapping and L14's import) or from
  sourcedcs-web's flight-plan lookup (`efsp-flight-plan-lookup.js`). `createFdr()` does not need to
  accept an `mtr` seed in this lane.
- **Any Block on `MISSION_BLOCK_MAP`.** Same reasoning as `3F`/`3G` in ADR `0052`: a MISSION Strip
  shares its `fdrId` with its ATC Strip, so a MISSION Block would be a second place to post one
  aircraft's MTR data.
- **The `military` target kind.** These are free-text / time / altitude fields, not an enum or a
  boolean; the plan says so in so many words (`docs/efsp-wp6-plan.md:463-465`).
- **A §3.7 history cell for the MTR fields** (see §11 Q1 — recommended default: plain `fdr`
  fields, gap recorded).
- **The pre-existing time-Block typing bug** (§9 trap T9). Record it; L16 owns §10.5's times.
- `M16` (alert status) and its Block — that is L13.
- The `9F` picker — that is L16.
- Shared docs (briefing, usage guide, CLAUDE.md, READMEs). Write `docs/wip/L2.md` instead.

## 4. Design decisions (settled — implement, do not re-derive)

These come from ADR `0052` and the WP6 plan and are not open:

- Ids are `9G-MTR`, `9G-ENTRY`, `9G-TIME`, `9H-EXIT`, `9H-TIME`, `9H-ALT` — the `9A-*` split's
  shape (`9A-FUEL`, `9A-VECTOR`, …) so per-Block facility narrowing works (`hiddenBlocks`).
  The guide's `M10`/`M11` are **cited in comments**, never used as ids on an ATC map (ADR `0052`;
  `efsp-block-map.test.mjs:389-398` enforces no `M`-prefix on ATC Roles).
- All six on **all three ATC Roles**; none on MISSION.
- **Plain `fdr` target kind**, one path each:

  | Block | Guide | FDR path | Required |
  |---|---|---|---|
  | `9G-MTR`   | M10 designator  | `military.mtr.designator`                 | false |
  | `9G-ENTRY` | M10 entry fix   | `military.mtr.entryFix`                   | false |
  | `9G-TIME`  | M10 entry time  | `military.mtr.entryTimeUtc`               | false |
  | `9H-EXIT`  | M11 exit fix    | `military.mtr.exitFix`                    | false |
  | `9H-TIME`  | M11 exit estimate | `military.mtr.exitEstimateUtc`          | false |
  | `9H-ALT`   | M11 requested altitude after exit | `military.mtr.requestedAltitudeAfterExit` | false |

- The FDR shape (`fdr.military.mtr`, six keys) is settled by ADR `0052` and is **not** reopened.
  No new keys, no renames.
- `setMilitary()` keeps refusing `mtr`; `MILITARY_WRITABLE_FIELDS` does not grow.
- Lost comms: an **advisory that states the rule and shows the altitude in force**, never a
  computed "lost-comms altitude".

- Append the six `military.mtr.*` paths to `WRITABLE_PATHS` as a **new trailing group** with a
  comment (after the `mission.*` group, before `]);` at `:142`).
- Rewrite `WRITABLE_PATHS`' header sentence about `military` (`:83-86`): *every path under
  `military` routes through `setMilitary()` **except the six `military.mtr.*` leaves (ADR 0062),

  and unpopulated" group to "written, via setField()".
- Add a module-level pure helper next to `parseAltitudeFt`, e.g.
  `normalizeMtrValue(path, value) -> { ok:true, value } | { ok:false, detail }`, and call it from
  `setField()` **before `setPath`** (between `:547` and `:555` is a good spot), then call

Normalisation (the helper):

| Path | Accepts | Stores | Refuses with |
|---|---|---|---|
| `designator`, `entryFix`, `exitFix` | any string ≤ `MAX_FREE_TEXT` | `trim().toUpperCase()`; `''` → `null` | (only the existing length cap) |
| `entryTimeUtc`, `exitEstimateUtc` | `HHMM`, `HH:MM`, optional trailing `Z`, 00–23 / 00–59 | the 4-digit string `'1432'`; `''`/`null` → `null` | `MTR exit estimate must be a UTC time as HHMM, e.g. 1432` (entry: *entry time*) |
| `requestedAltitudeAfterExit` | whatever `parseAltitudeFt()` parses | the controller's text, trimmed and upper-cased (`'FL210'`, `'080'`); `''` → `null` | `requested altitude after exit must be an altitude, e.g. FL210 or 080` |

Why a clock string and not epoch ms (§11 Q2): an MTR exit estimate is spoken as a four-digit
time with no date; turning it into epoch requires guessing the day, which is wrong across UTC
midnight, and nothing in this lane does arithmetic on it. The `…Utc` suffix in the field name
(fixed by ADR `0052`) names the time reference, not the type — say so in the ADR.

No format rule for designators or fixes (D11). Upper-casing is the strip convention, not a
validation.

### 5.5 Placement — Layout C's field grid (`strip-fields.js`)

ADR `0056` already placed this deliverable: *"§9.4 MTR fields → the field grid of the Positions
that fly MTRs"*. The criterion for a field (`strip-fields.js:12-17`) is **edit frequency**, and
most flights do not fly an MTR — so six always-on columns at APP/CTR would cost Strip height on
every Strip for data most never have. And the guide wants `M11` **prominent**, not buried in
the ▼ view.

**Recommended: an MTR group that appears on the field grid only when the flight has MTR data,
on its own grid row, with `M11` first.**

1. A new table in `strip-fields.js`, appended after `FIELD_SPANS`:

   ```js
   // §9.4 (docs/adr/0062). Drawn only when the flight has any MTR data posted —
   // most flights never fly one, and a field every Strip pays for must be earned
   // (the criterion above). M11's exit fix and estimate come first: the guide's
   // one explicit instruction is that they are asked for by voice and posted.
   const MTR_BLOCKS_BY_POSITION = {
     DEPARTURE:  { OPS: ['9G-MTR', '9G-ENTRY', '9G-TIME'],
                   CD:  ['9G-MTR'],
                   APP: ['9G-MTR', '9H-EXIT', '9H-TIME', '9H-ALT', '9G-ENTRY', '9G-TIME'],
                   CTR: ['9G-MTR', '9H-EXIT', '9H-TIME', '9H-ALT', '9G-ENTRY', '9G-TIME'] },
     ARRIVAL:    { APP: ['9G-MTR', '9H-EXIT', '9H-TIME', '9H-ALT'],
                   CTR: ['9G-MTR', '9H-EXIT', '9H-TIME', '9H-ALT'] },
     OVERFLIGHT: { APP: ['9G-MTR', '9H-EXIT', '9H-TIME', '9H-ALT', '9G-ENTRY', '9G-TIME'],
                   CTR: ['9G-MTR', '9H-EXIT', '9H-TIME', '9H-ALT', '9G-ENTRY', '9G-TIME'] },
   };
   ```

   Rationale per Position (write this into the ADR, not only here):
   - **OPS** files the flight, so it posts the designator and entry.
   - **CD** reads the designator into the clearance; nothing else.
   - **GND, TWR**: none. Ground movement and the runway do not use MTR data (the same rule that
     keeps FREQ off them).
   - **APP, CTR** are who the pilot calls on exit and who release the aircraft into the route, so
     they get the whole group, `M11` first. An ARRIVAL is already past the route: entry is history,
     so it is left off (still in ▼).
   - **MISSION**: no Blocks at all (§1).
   - A Position no list names (`NOLIST`, e.g. RSU later) gets no group; the ▼ view reaches all six.
   - `[SOURCE-DEFINED]` — which Positions work MTR traffic at Incirlik is squadron knowledge; say so
     in the ADR and in `docs/wip/L2.md` as something a squadron member should confirm.

2. **The trigger is "any of the six is non-empty"**, not "designator set". A controller who
   clears the designator but leaves an exit fix must still see the stale exit fix on the face,
   rather than have it vanish into ▼ while still sitting on the FDR. (Pilot walk, §8.4.)

3. `compactBlocksFor(role, positionId, fdr)` gains an **optional third argument**. With no `fdr`
   (every existing caller and test) it returns exactly what it returns today. With an `fdr` that
   has MTR data, it returns the Position's list followed by `MTR_BLOCKS_BY_POSITION[role][positionId]`
   (filtered by the Role's Block Map, as now). Add a pure `hasMtrData(fdr)` beside it.

4. The two callers pass the flight: `strip-view.js:331` and `bay-view.js:721` become
   `compactBlocksFor(strip.role, strip.ownerPositionId, getEfspFdr(strip.fdrId))`. These are the
   only edits in those two files outside the §7 table's lanes — each is one line; list both in
   `docs/wip/L2.md` under "Shared-file touches" so the supervisor sees them.

5. **Its own row, starting at column 1**, so the group sits in the same place on every MTR Strip
   of a Bay regardless of how many fields wrapped above it (ADR `0056`'s "a field sits in the same
   column on every Strip of a Bay"). CSS only, no `strip-view.js` change, appended to the Layout C
   section of `crc-desktop/app/public/css/efsp-panel.css` (after `:1450`):

   ```css
   /* §9.4 (docs/adr/0062): the MTR group starts its own row, so it lines up
      Strip to Strip. Every group begins with 9G-MTR. */
   .efsp-strip-fields > .efsp-field:has(> .efsp-block-9G-MTR) { grid-column-start: 1; }
   ```

   `:has()` is supported by the Chromium Electron ships; verify it in the Playwright check. If you
   prefer a class, add it in `strip-fields.js` data (e.g. `MTR_GROUP_FIRST = '9G-MTR'`) and have the
   CSS target the cell's existing `efsp-block-9G-MTR` class — do not restructure `_buildStripFields`.
   Note `_buildBlockCell` gives the value span the class `efsp-block-<id>` (`bay-view.js:154`) and
   `data-block` (`:155`).

6. **Prominence = position and grouping, not colour.** ADR `0056`/`0058`: colour means something
   is wrong. Do not tint the MTR row. No span > 1 needed (designators like `IR107` and fix names fit
   66 px); if Playwright shows truncation at 1600 px, give `9G-MTR` span 2 in `FIELD_SPANS`.

7. **Rebuilds**: an MTR write bumps `fdr.rev`, which is already in `_stripRenderSignature`
   (`bay-view.js:2793-2794`), so the group appears/disappears on every Strip of the flight — other
   Facilities' replicas included — without further work. Test it (§8.2).

*Rejected alternative (record in the ADR):* always-on MTR fields at APP/CTR. Simpler (no third
argument), but costs up to six columns on every APP/CTR Strip for data most flights never carry —
against `strip-fields.js`'s own criterion and ADR `0055`'s density finding. *Also rejected:* MTR
as an indicator/badge (ADR `0058`: indicators are for things wrong or in effect; an MTR is data a
controller edits, and an indicator is not a control, ADR `0056`).

### 5.6 Amendment semantics

- `setField()` bumps `fdr.updatedAt`, which `forwarding-obligations.js:66-76` reads as "the flight
  plan was just amended" for `AMENDMENT_INSIDE_30MIN` on a DEPARTURE within 30 min of proposed
  departure. **That is correct for MTR data**: the MTR is part of the filed plan, and amending it
  shortly before departure is an amendment. It is *not* a clearance (contrast ADR `0058`'s
  `clearanceUpdatedAt`). For an airborne flight `proposedDepartureTimeUtc` is in the past and the
  obligation cannot fire. Say this in the ADR and assert the pre-departure case in the scenario.
- No `interlock` tag on any of the six. `9H-ALT` is the pilot's **request**; posting it issues
  nothing. If the controller approves it, they write `ALT` (the clearance), which *is* tagged and
  *does* void MARSA before rendezvous. Assert both in the scenario.
- Conformance (`src/efsp/conformance.js`) must not read `9H-ALT`. Nothing to change; do not wire it.

### 5.7 The lost-comms advisory (and ADR 0058's "nothing when nothing is wrong")

§9.4 asks for an advisory; ADR `0058` says the Strip's face shows nothing when nothing is wrong,
and reason lines (`_buildReasonLines`, amber `▲`) are for things wrong or blocked. An MTR flight
with normal comms is not wrong. **So the advisory does not go on the Strip's face.**

Recommended placement — two places, both only when `hasMtrData(fdr)`:

1. **The expanded (▼) view**, as the first thing in `.efsp-strip-expanded`: one note line, class
   `efsp-expanded-note efsp-mtr-lostcomms` (grey, **not** `efsp-strip-reason`, no `▲`). Added in
   `bay-view.js`'s `_appendExpandedView` (`:729`) — append-only, a few lines — and it must render
   even when `_expandedBlockIdsFor` returns nothing (today the function returns early at `:735`;
   move the note above that early return or restructure minimally).
2. **The `title` of the `EXIT ALT` field's label** on the face, so hovering the requested altitude
   shows the rule. (Set it where labels are built only if that can be done from data; otherwise
   skip this and keep 1 — do not restructure `_buildStripFields`.)

The text, built by a pure function appended to `strip-fields.js` (it is loaded in every sandbox
and needs no new `<script>` tag), e.g. `mtrLostCommsAdvisory(fdr) -> string | null`:

> Lost comms (§9.4): separate assuming the higher of the minimum IFR altitude for each remaining
> segment — not available in this system — or the altitude in the last clearance: **FL180**.

- "the altitude in the last clearance" = the ACTIVE entry of `fdr.clearance.altitude` (ADR
  `0058`), rendered as the controller wrote it (`entry.value`). No active entry → "…or the
  altitude in the last clearance: none posted (ALT is empty)."
- Never print a computed "lost-comms altitude", never compare with `9H-ALT`, never call the MIA
  "0" or omit the clause saying it is unavailable. Showing only the half we have without saying the
  other half is missing would present the advisory as complete (D11).
- Cite §9.4, not a regulation. (The underlying real-world rule is 14 CFR 91.185; the guide
  paraphrases it. Do not quote the CFR in UI text — the guide is our source.)
- Rebuilds: `fdr.rev` in the render signature covers both an MTR write and an ALT amendment.

*Rejected (record in ADR):* a permanent reason line on every MTR Strip (violates `0058`; trains the
controller to ignore amber); an indicator slot (same); computing an altitude from `9H-ALT` (that is
a request, not a clearance — the rule says "last clearance").

**Q2 — Times as `HHMM` strings or epoch ms?**
Other `…Utc` fields are epoch numbers (`proposedDepartureTimeUtc: Date.now()`), but typed time
Blocks already arrive as strings (T9). *Default: normalised `'HHMM'` strings, validated server-side,
because an MTR estimate is a spoken four-digit clock time with no date and nothing does arithmetic
on it.* Record in the ADR; flag for L16 so the §10.5 work does not "fix" these.

**Q3 — Which Positions get the MTR group?**
*Default: §5.5's table — OPS (designator + entry), CD (designator), APP and CTR (all six on DEP/OVF,
designator + M11 on ARR), none at GND/TWR, none on MISSION; `[SOURCE-DEFINED]`, for a squadron
member to confirm.*

**Q4 — Conditional row vs always-on fields.**

supervisor rules always-on, drop the third argument and put the lists straight into
`COMPACT_BLOCKS_BY_POSITION` — everything else stands.

**Q5 — Should clearing `9G-MTR` clear the other five?**

field"* (mirrors ADR `0050`: clearing the stereo label never touches the route). Record how it felt
in the walk.

`parseAltitudeFt` rejects them. *Default: refuse; single altitude only.* The guide's field is
"requested altitude after exit" (singular). Note it in the wip doc if the walk wants blocks.

*Default: a grey note at the top of the ▼ view, plus (if cheap from data) a `title` on the `EXIT ALT`
label; never on the collapsed face.* If the supervisor wants it visible without opening ▼, the
next-least-bad option is a `title` on the `MTR` chip — still not a reason line.

**Q8 — Upper-case free text?**
*Default: yes for designator and fixes (strip convention), trimmed; no format validation (D11).*

**Q9 — Is posting MTR data pre-departure an amendment for `AMENDMENT_INSIDE_30MIN`?**
