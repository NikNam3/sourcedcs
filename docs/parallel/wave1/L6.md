## 1. Mission

Build a driver that runs crc-sync's whole EFSP subsystem under simulated traffic for N minutes. It
has to do four things:

- Create Strips, advance them, reorder them, coordinate them across Facilities and drop them.
- Churn correlation: aircraft appear and vanish, DCS re-mints ids, squawks go wrong.
- Disconnect and reconnect clients, and restart the server partway through.
- Report on memory, order-key growth and dropped Mutations.

The acceptance line this serves is `EFSPImplementationGuide.md` §13 WP8, bullet 2:

> A four-hour soak with simulated traffic shows no memory growth, no order-key exhaustion, and no
> dropped Mutations.

It also serves §11.1: no Mutation may be lost on reconnect, and a server restart must not lose the
Board. The default run is ten minutes. A four-hour run is the §13 criterion.

**The lane is done when the harness works, not when the soak passes.** This briefing's research
suggests a first honest run will **FAIL** on at least order-key growth and retained-record memory
growth (§5.9). If the harness reports that with evidence, the lane has succeeded.

### Out of scope, and binding

- **No production code changes.** Do not edit anything under `crc-sync/src/`, `crc-sync/server.js`,
  `crc-sync/tests/`, `crc-sync/package.json`, `crc-desktop/` or the shared docs. If the soak finds
  a leak, a lost Mutation, a stale replica or anything else, **record it in `docs/wip/L6.md` with
  evidence and do not fix it.** Evidence means the report excerpt, the seed and command, and the
  file:line you believe is responsible. The owning lane or the integrator fixes it.
- **No npm script.** `package.json` is not yours. Propose `soak` / `soak:smoke` scripts in

  which picks files up by name (§8, trap T1).
- **Never touch the crc-sync on :3000** or its `crc-sync/state/` directory. That directory holds
  the human's live dev Board (`crc-sync/state/efsp-board.json` exists). Every byte the soak writes
  goes to a temp directory (§3).
- No wire mode that spawns `server.js` for this lane. It is deferred (§10, Q9).

### 3.2 The wire handler: `crc-sync/src/efsp/efsp-ws.js`

- `_handleResync` is at :246. The delta path runs when `lastSeq >= 0`, `!rewound` and

### 3.3 The Board: `crc-sync/src/efsp/board-store.js`
- `APPLIED_MUTATIONS_CAP = 5000` (:36) is the idempotency cache, evicted FIFO (:262-266).
- `_strips` (:126) **never deletes**. A DROPPED Strip stays queryable (:146, :1400), and
  `snapshot()` (:2384) persists all of them.
- The `_log` ring: `_touch` (:154), and `_pruneLog` trims to the last 1000 once it passes 2000
  (:158-160). `getDeltaSince(afterSeq)` is at :163.
- `_nlaHistory` (:132-138) implements the **400 ms double-tap guard** (`_applyInvokeNla`,
  :1275-1284) and the 30 s Undo window. It is set after every state-only NLA **including the
  terminal Drop** (:1334-1336). It is deleted only on transfer (:1040) and Undo (:1346).
- Order keys: `_resolveOrderKey` (:180-209) calls `keyBetween`. **Only** when that throws
  `ORDER_KEY_EXHAUSTED` does it `_rebalanceRack` (:211-219), which gives every Strip in the Rack a
  new key, `rev += 1`, and a `_touch`, **inside the one Mutation**.
- `applyMutation` (:238) is the one choke point. An unexpected throw becomes `{ ok:false,
  reason:'VALIDATION_ERROR', detail:'internal error processing mutation' }` and logs
  `console.error('[board-store] unexpected error applying Mutation …')` (:250-260, `console.error` at :258).
- `_dispatch` (:270): `CreateStrip` carries **no** `baseRev` (:293-297). Every other op checks
  `STALE_REV` (:301) and `NOT_OWNER` (:307).
- `_recordAudit` (:366-381) appends to the Mutation log **only when `result.ok`**. A double-tap
  no-op returns `ok:true` and **is** audited (before equals after).
- `_nextCid` (:221-227) zero-pads a 3-digit counter per Board lifetime (§5.9, H7).
- `reassignPositionStrips` (:2363-2381) writes audit lines with `clientMutationId: null, op:
  'SystemReassign', actorId: 'system'`.
- `restore()` (:2387-2401) does **not** restore `_seq`, `_log`, `_appliedMutations` or
  `_nlaHistory`. The comment at :2397-2400 says so on purpose.

### 3.4 Order keys: `crc-sync/src/efsp/order-key.js`
- The base-62 alphabet is at :30. `keyBetween(a, b)` is at :66. "Insert after everything" appends
  a digit to `a` (:92), and "insert before everything" digs below `b` until it throws (:97-115).
  The general case digs deeper each time the gap closes (:122-154).
- `REBALANCE_KEY_LENGTH = 40` and `needsRebalance(keys)` are at :160-163, and **nothing outside
  this file calls them** (`grep -rn needsRebalance crc-sync/src` finds only order-key.js).
- `rebalance(orderedIds)` is at :190. It produces fixed-length, evenly spaced keys.
- **"Exhaustion", concretely.** There are two failure modes, and the soak measures both:
  1. A key grows without bound because no proactive rebalance ever runs. While this briefing was
     being written, a scratch script in a temp dir (not committed) made **200 pairs of same-slot
     `MoveStrip`s** in one Rack. Max key length was 25 after 50 pairs, 45 after 100 and **94
     after 200**, and no rebalance happened. Reproduce it in step 4 of §6.
  2. `ORDER_KEY_EXHAUSTED` escapes the retry in `_resolveOrderKey`, or the retry itself throws.
     Either reaches the catch-all at board-store.js:258 as "internal error processing mutation".

## 4. Decisions this briefing takes (overridable only via `decisions.md`)

| # | Decision | Why |
|---|---|---|
| D1 | **Forked host process by default.** The EFSP subsystem, WsHub and monitors run in a child (`child_process.fork`, `execArgv: ['--expose-gc']`, `serialization: 'advanced'`). The driver and all its bookkeeping stay in the parent | Heap is measured on the server only, not polluted by the driver's ledger of tens of thousands of ids. A restart is a real `SIGKILL` plus re-fork, with fresh module state, a real restore and a real atomic-rename test. `--inproc` loads the same host core in-process for debugging |
| D2 | **Virtual clock by default.** The host replaces `Date.now` with a clock the driver advances. Every host command carries `now` | Nothing under `src/efsp`, `tracks.js` or `stca.js` uses `new Date(` or timers (checked with grep). Every clock read is `Date.now()` or a `now` parameter, so a 4-hour soak runs in minutes and the 400 ms guard is satisfied by arithmetic. `--realtime` paces virtual time to wall time for the literal four-hour run |
| D3 | **`--minutes` means simulated minutes** | So `--minutes 240` is "the four-hour soak" in either clock mode |
| D4 | **Traffic goes through the real `WsHub` with fake sockets** (`_onConnect` / `_onMessage`) | This is ws-hub's own routing: the ack to the sender, three broadcast kinds to everyone, JSON round-tripping, and disconnect → `onDisconnect`. `--direct` calls `efsp.handleMessage` like the scenario tests do, with the harness doing the fan-out, as a fallback if WsHub internals move |
| D5 | **A seed controls every driver choice.** The host also swaps `Math.random` for a seeded PRNG. `crypto.randomUUID` is left alone | Order-key jitter (`order-key.js`:40-42) becomes reproducible, so key-length growth is too. UUIDs differ between runs, which does not matter for any criterion |
| D6 | **No production edits, and instrumentation by wrapping inside the host only** (e.g. wrap each `boardStore._rebalanceRack` to count calls, intercept `console.*`) | This is the lane's ownership rule. Wrapping instance methods in the host changes nothing that ships |

## 5. Design

### 5.1 Process layout

```
crc-sync/tools/soak/
  run.js          CLI entry: parse args, make temp state dir, fork host, run scheduler, write report
  host.js         child entry: set env + Date.now + Math.random, then require src/*, then serve IPC
  host-core.js    createHost(opts) -> { handle(cmd) }  (transport-agnostic; used by host.js and --inproc)
  traffic.js      flight scripts (per role), controller model, reorder storms, janitor
  sky.js          simulated aircraft: spawn/move/re-mint/despawn, squawk faults, TrackStore feed
  shadow.js       per-client replica (snapshot/delta/ack semantics of efsp-state.js) + convergence diff
  ledger.js       submitted-Mutation ledger, ack matching, audit-log reconciliation (streamed)
  metrics.js      samples, order-key histogram, least-squares slope, verdict
  report.js       report.json + summary.txt writer
  prng.js         seeded PRNG + helpers (pick, weighted, exp-distributed think time)
  selfcheck.mjs   runs short soaks with injected faults and asserts each detector fires (NOT *.test.*)
  .gitignore      out/
```
Change the names if you like, but **not to any name `node --test` collects** (T1).

**Host commands** (driver → host). Each is `{ id, now, type, … }`, and each returns `{ id,
out: [{ clientId, msg }], … }`, where `out` is every message the fake sockets received while the
command ran:
- `connect { clientId, user }` → `hub._onConnect(fakeWs, { crcUser: user })`. The snapshot arrives
  in `out`.
- `send { clientId, msg }` → the fake socket's registered `message` handler with
  `JSON.stringify(msg)`.
- `close { clientId }` → `readyState = 3`, remove from `_wss.clients`, call the `close` handler.
- `tick { what: [...] }` → any of `reconcile | conformanceStca | obligationsNla | expireTracks |
  heartbeat`. The driver's scheduler decides the cadence (§3.8).
- `tracks { upsert: [...], remove: [...], squawks: {...} }` → feeds `TrackStore`.
- `missionReload` → `trackStore.clear()` + `reconciler.resetPicture('MISSION_RELOAD')`.
- `truth { facilities? }` → server truth for the convergence and restart checks: per Facility,
  `boardStore.getAll()` mapped to the compared fields (§5.6) plus `currentSeq`.
- `sample { gc: true, heavy?: bool }` → §5.7.
- `inject { fault }` → selfcheck faults (§6, step 9).

**Fan-out cost:** with N clients each broadcast becomes N IPC messages. N ≤ 12, so this is fine.
Forward every `send` straight away and keep nothing in the host (T6).

### 5.2 Traffic model

**Controllers (default crew, 9 sessions):**
- one Primary each at OPS, CD, GND, TWR, APP (INCIRLIK), CTR (CENTER) and TAC_C2 (TACTICAL);
- one Primary at the fixture's range Position;
- one **observer** that selects APP after APP's Primary, so it is an Observer (§4.8.2, D18). It
  never acts and is the purest shadow.

Each session sends `efsp-set-positions` right after `connect`, with `crew()`'s shape
(`efsp-scenario.mjs`:17-26). `--crew combined` adds a controller holding `GND+TWR` together, for
§4.8.3's combined-Position case.

**The airspace fixture** is written to the temp `CRCSYNC_EFSP_AIRSPACES_PATH` before the host
requires anything. Use one MOA (`controllingFacilityId: 'CENTER', controllingPositionId: 'CTR'`)
and one RANGE with a `usingPositionId`, copied from `tests/efsp-scenarios.test.mjs`:36-61.

**Flight scripts.** Each flight is a small state machine. The scheduler (a binary heap on virtual
time) wakes it after a think time, it emits one Mutation, and it reads the **ack** to decide the
next step. **The driver never assumes the server did what it asked.** Owner, state, rev and peer
ids always come from the latest ack, broadcast or truth.

| Script | Weight | Walk | Source |
|---|---|---|---|
| `civilRoundTrip` | 30% | Full civil walk incl. `24A` there and back, `ConvertToArrival`, handback, arrival chain, NLA Drop | scenarios.test.mjs:123-197 |
| `departureOut` | 20% | OPS→…→APP `HANDED_OFF`, HANDOFF→CTR accepted, APP drops its Strip, CTR drops its replica later | helpers :107-128 + scenarios :364-367 |
| `popupArrival` | 15% | APP creates ARRIVAL at `app-inbound`, then APP→TWR→GND, Drop | coordination :154 |
| `overflight` | 10% | CTR creates OVERFLIGHT at `ctr-overflight`, POINT_OUT/TRAFFIC to APP (accept or reject), Drop | coordination :129, :222 |
| `militarySortie` | 15% | Departure → CTR → TOFI ENTRY to TAC_C2 (`separationRegime`), `SREG`, TOFI EXIT, MISSION Drop, return leg | scenarios.test.mjs:246-370 |
| `rangeVisit` | 10% | Activate the range once per run (`activate()`'s op sequence, helper :133-145), `ApproveAirspaceEntry` / `ClearAirspaceEntry` on a working Strip | scenario-airspace :74 |

**Intermediate edits on the way through** (each with a probability per step):
- `SetBlock 21` / `20` (assigned altitude and heading; these feed conformance);
- `SetFlag` (`highlight`/`attention`);
- a same-Bay `MoveStrip` reorder;
- `BindTrack`/`UnbindTrack` via `efsp-correlation-mutation`, 2% per airborne step;
- `Undo` right after an NLA, 1% (virtual time must stay inside 30 s, board-store.js:1341-1347).

**MARSA** is optional for v1. If you add it, copy `DeclareMarsa`'s shape from
`efsp-scenario-marsa.test.mjs`:55-60.

**Order-key stress (the WP8 bullet).** Three patterns, applied to Racks that hold Strips:
1. **Same-slot repeated insert:** repeatedly `MoveStrip` a Strip to `afterStripId = X`,
   `beforeStripId = <whatever is now right after X>`. This is the pattern measured in §3.4, where
   the gap halves every time.
2. **Top-of-Rack insert:** `beforeStripId = first`, `afterStripId = null`. It digs below the
   minimum and eventually throws, which exercises the rebalance path.
3. **Ping-pong:** A after B, then B after A, repeated. With jittered ties this reaches the swap
   branch at board-store.js:205.

Also create `CreateStrip`s at OPS in `ops-filed` with identical `afterStripId` bounds. In the
**realistic** profile, 20% of flights get one storm of 3-6 moves. In **stress**, 40% get 10-30
moves, all three patterns.

**The janitor.** Every virtual minute it takes `truth`. For every live Strip whose flight script
has finished, it `DropStrip`s as the owner if that controller is connected. Coordination and TOFI
replicas that outlive their flight are the usual case, as :364 and :367 show. A Strip the janitor
cannot drop for 3 consecutive passes is an **orphan**. Report it with its refusal. A rising orphan
count means live Strips leak onto controllers' Boards, which is a finding. The live-Strip count
must stay stationary. If it does not, suspect the janitor first and the server second.

**Profiles:**

| | `realistic` (default) | `stress` | `smoke` (CI-safe) |
|---|---|---|---|
| New flights / virtual hour | 30 | 150 | 60 |
| Think time between a controller's steps on one Strip | 15-90 s (exp.) | 0.5-8 s | 2-10 s |
| Reorder storms | 20% × 3-6 moves | 40% × 10-30 | 30% × 5 |
| Disconnect per client | ~1 / 45 min | ~1 / 5 min | 2 in the run |
| Restarts | 1, at a random point in the middle third | 3 | 1 |
| Mission reloads (DCS id re-mint of everything) | 1 / 2 h | 1 / 20 min | 1 |
| Expected live Strips | ~10-25 | ~40-80 | ~10-20 |

The NLA guard: the scheduler keeps ≥ 410 ms of virtual time (`NLA_DOUBLE_TAP_MS + 10`) between two
`InvokeNla` on **the same Strip**. Separately, with 1% probability it deliberately double-taps
inside 400 ms. That press must come back `ok:true` with **no** state change and **one** audit line
(board-store.js:1278-1284). Count it as `doubleTapNoop` and not as progress.

### 5.3 Sky and correlation churn (`sky.js`)
- A departure that reaches `DEPARTED`, and every ARRIVAL/OVERFLIGHT/MISSION once airborne, spawns
  one aircraft. It gets a DCS-style numeric id, a callsign from the FDR and the squawk from
  `fdr.identity.beaconAssigned` (from the ack's `fdr` or the broadcast's `fdrs.updated`). It flies
  a straight line: lat/lon/alt plus `course`, `groundSpeed` and `verticalSpeed`, which conformance
  and STCA need.
- Upserts go to the host every virtual 2 s, and the reconciler ticks every virtual 1 s.
- **Faults, each per aircraft, seeded:**
  - 8% squawk the wrong code (a contradicted exact callsign gives PROVISIONAL,
    correlation-reconciler.js:268-279);
  - 5% have no transponder (null);
  - 5% have a callsign typo (fuzzy rung);
  - 3% share a callsign with another airborne aircraft (AMBIGUOUS_CALLSIGN).
- **Re-mint:** every ~10 virtual minutes per aircraft, remove the track and re-add it under a new
  id with the same callsign and squawk.
- **Mission reload:** at the profile's rate, re-mint everything at once and send `missionReload`.
- **Linger:** keep the aircraft alive 2-5 virtual minutes after its Strip is dropped.
  `CodeAllocator.allocate` hands out the **lowest** free code first (code-allocator.js:67-76), so
  the next flight usually gets that code while the old aircraft still squawks it. Count any
  correlation of a new FDR to a lingering track that belongs to a **different** flight as
  `misbinding` (H8).
- **Conflicts:** twice an hour, put two aircraft on converging courses so STCA raises and clears
  (`efsp-alerts`). Occasionally set `21` to an altitude the aircraft does not fly, so conformance
  raises and then clears.
- Run `expireTracks` every virtual 5 s. `TrackStore` reads `Date.now()`, which is virtual.

### 5.4 Clock and time compression
- The host does `let now = <start>; Date.now = () => now;` **before** requiring anything. Every
  command sets `now = cmd.now`. The start is the real `Date.now()` at launch, so timestamps look
  sane and any L5 retention logic, which compares ages, sees nothing expire.
- The driver is a discrete-event loop: pop the next event, advance virtual `now` to its time, send
  the command, and process `out` synchronously before the next event. **Never** `setTimeout` for
  pacing, except in `--realtime`.
- `--realtime`: before each event, `await sleep(max(0, eventWallTarget - wallNow))`. With
  `--minutes 240` this is the literal four-hour run (§10, Q2).
- Measure latency with `performance.now()`, which `Date.now` overriding does not affect. Take the
  `handleMessage` duration in the host around each `send`, and return it in the reply as
  `serverMs`.

### 5.5 "No dropped Mutations": the ledger (`ledger.js`)
Every message the driver sends carries a fresh `clientMutationId`. `set-positions` and `resync`
have none, and their replies are checked separately. The ledger stores, per id: kind, message type,
client, virtual time sent, the ack's `ok`/`reason`/`detail`, and the ack's `strip.rev`.

**Invariants.** Each is checked continuously; at the end the Mutation log is **streamed** (use
`readline`, not `MutationLog.readAll`, which loads the whole file into memory).

| Id | Invariant | Failure name |
|---|---|---|
| M1 | Every sent message whose socket was open when sent gets **exactly one** matching ack before the next event | `lost`, `duplicateAck` |
| M2 | Every `efsp-mutation-ack` with `ok:true` has **exactly one** log line with that `clientMutationId` | `auditMissing`, `auditDuplicate` |
| M3 | Every `efsp-mutation-ack` with `ok:false` has **zero** lines (board-store audits only successes, :367) | `auditForRefusal` |
| M4 | For airspace, correlation and MARSA acks, the stores audit refusals too (e.g. correlation-store.js:233, :245, :270). A store-level answer has exactly one line, and a wire-level refusal (`NOT_HOLDING_POSITION`, efsp-ws.js :329, :397, :465) has zero. Minimum invariant: at most one line, and exactly one when `ok` | `auditMissing` |
| M5 | Every log line with a non-null `clientMutationId` belongs to the ledger. Lines with `clientMutationId: null` (`SystemReassign`, board-store.js:2374) and `actorId: 'system'` lines are counted separately | `auditOrphan` |
| M6 | No ack has `detail === 'internal error processing mutation'`, and no host `console.error` starts with `[board-store] unexpected error` | `internalErrors` |
| M7 | **Idempotent replay.** With probability 1%, re-send an earlier message verbatim. It must be within the last 1000 of the same Board, so it is well inside `APPLIED_MUTATIONS_CAP`, and the server must not have restarted since. It must come back byte-equal in `ok`/`reason`, with no new audit line and no rev bump | `replayNotIdempotent` |
| M8 | A successful ack is followed in the same `out` by a board-delta carrying that Strip (or its id in `gone`) to **every** connected client, the sender included | `broadcastMissing` |

**Refusals are data.** Tabulate every `ok:false` by `(op.kind, reason)`, and split them into
expected and unexpected:
- **Expected:** `STALE_REV` after a known race, `NLA_INHIBITED` on an inhibit the script walked
  into, and `NOT_HOLDING_POSITION` while disconnected.
- **Unexpected:** anything else. List the first 20 of each with the full ack in `events.ndjson`.

The script must re-read truth and carry on after any refusal.

**Across a restart:**
- **R1.** Snapshot the driver's **oracle** just before the kill. The oracle is the union of the
  latest successful ack or broadcast per Strip, which is what a perfectly connected observer
  holds. After restart, `truth` must contain every oracle Strip with an equal `rev` and equal
  compared fields. Anything missing or older is `boardLostOnRestart`, a §11.1.3 FAIL.
- **R2 (ambiguous disconnect).** Once per restart, send one Mutation and `SIGKILL` the host
  **without waiting for the ack**. After the re-fork, replay it with the same `clientMutationId`.
  Classify the result with the log and truth: `appliedOnce`, `appliedTwice` (expected for a
  `CreateStrip`, since `restore()` drops the idempotency cache, board-store.js:2397-2400, H5) or
  `lost` (audited before the kill but not in the restored Board, which is the log-before-persist
  window in efsp-ws.js:160-163). Alternate the op kind between restarts, `CreateStrip` then a strip
  op. **Report R2; do not fail on it.** It measures a documented gap. The supervisor decides
  whether that gap is acceptable (§10, Q1).

### 5.6 Shadow replicas and convergence (`shadow.js`)
Each client keeps, per Facility, `Map<stripId, compared>` plus `boardSeq`, and applies messages
exactly as §3.10 does:
- snapshot: clear and refill every Facility from `strips[].facilityId` and `boardSeqByFacility`;
- `efsp-board-delta`: upsert `updated`, delete `gone`, take `boardSeq` for `msg.facilityId`;
- ack: upsert `ack.strip`, on success or refusal.

**Compared fields:** `stripId, rev, state, ownerPositionId, bayId, rackId, orderKey, role, fdrId`.
Do not compare the stamped `nla` or `facilityId`.

**Checkpoint (every virtual 60 s, and after every reconnect):** diff each **continuously
connected** client's shadow against `truth`. Classify every difference by which of that client's
shadow fields is stale and by the last op that touched the Strip on the server. Record the
server-side cause when it can be inferred:
- `REBALANCE_SIDE_EFFECT`: the Strip's rev moved inside another Strip's Mutation, detected by the
  wrapped `_rebalanceRack` in the host (H1);
- `SYSTEM_REASSIGN`;
- `PEER_REPLICA`;
- `UNKNOWN`.

A difference on a client that **never disconnected** since its last snapshot counts as
`silentStaleness`. That is a broadcast the client should have received and did not, and it is a
"dropped Mutation" in WP8's sense, so it is a FAIL. The fix to the shadow is **not** automatic:
leave the client stale until its next scheduled resync, to measure how long staleness persists.

**Reconnect (the two §5.6 paths).** On a scheduled disconnect: `close`, wait 5-90 virtual seconds
while traffic continues (the Position is released and other clients see it), then `connect` again,
`set-positions`, and **also** send `efsp-resync { facilityId, lastBoardSeq }` for each Facility
the client holds. The connect-time snapshot fixes the replica anyway. To exercise the **delta**
path on its own:
- 50% of reconnects **discard** the connect-time snapshot from the shadow and rely on the resync
  answer alone;
- choose the wait so some reconnects fall inside the 900 window (delta) and some outside it
  (snapshot);
- count `resync.delta` and `resync.snapshot`. Both must be > 0 by the end of any profile except
  `smoke`.

After the resync, the diff must be empty. If not, record `resyncDivergence` with the path taken, a
FAIL.

**The post-restart resync probe (H4).** After a restart the server's seq starts again from 0
(`restore()` does not restore `_seq`). Keep one client disconnected across the restart. Reconnect
it **after** enough post-restart traffic that `currentSeq > its lastBoardSeq`, discard the
snapshot, and resync. If the diff is non-empty, report `resyncAcrossRestartDivergence` with
`{lastSeq, currentSeqAtResync, missing, stale}`. It is expected to fire, because there is no epoch
in the resync (efsp-ws.js:272-273). Report it in `docs/wip/L6.md` as a finding. It is a FAIL
under M8/§11.1.2.

  - `fs.statSync` of the Board snapshot file;
  - `fs.statSync` of the Mutation log.

|---|---|---|

| `_log.length` | board-store.js:127 | ≤ 2000 |

- **Order-key histogram (every light sample):** over all **live** Strips, the distribution of
  `orderKey.length` (buckets 1, 2, 3-5, 6-10, 11-20, 21-40, 41-80, 81-160, >160), the max, the
  p99, the Rack holding the max, the count of wrapped `_rebalanceRack` calls, and the count of
  `ORDER_KEY_EXHAUSTED` seen. Wrap `order-key.keyBetween` in the host only to count throws; the
  module export is a plain object, so reassigning the property before board-store requires it
  works. Otherwise count retries through the rebalance wrapper.
- **Leak analysis:**
  - Drop the warm-up: the first 20 virtual minutes, or 10% of the run, whichever is longer.
  - Fit ordinary least squares to post-GC `heapUsed` against virtual hours, and report the slope
    (MB/h), R² and the net change.
  - Do the same for each structure count, and for `snapshotBytes` against DROPPED count, to
    attribute growth.
  - A heap slope with R² > 0.8 whose residual after subtracting "per-DROPPED-Strip bytes ×
    DROPPED slope" is still positive points at something other than retention. Get the per-Strip
    bytes as the regression coefficient of heap on DROPPED count.
- **Latency:** per 10-virtual-minute window, p50/p95/p99/max of host `serverMs` per message type,
  and of `_persist`. Time `_persist` by wrapping `fs.writeFileSync` inside the host for the
  snapshot path only. Latency growth with DROPPED count is expected, because of `getRack`,
  `_persist` and `liveStripsForFdr`, which are all O(total Strips).

- **T2: the 400 ms double-tap guard** (board-store.js:1278). Two `InvokeNla` on one Strip less
  than 400 virtual ms apart give `ok:true`, **no transition** and **one audit line**. A script
  that treats that ack as progress will desynchronise from the server. Always read `ack.strip.state`.
  Transfers clear the guard (:1040), and state-only NLAs arm it.
- **T3: timers keep the process alive, or fire on real time.** Never call `WsHub.attach()`. Never
  `require('../../server.js')`. Build the monitors yourself and tick them from the scheduler. At
  the end, `hub._sessions.clear()`, disconnect the IPC channel (`process.disconnect()` in the
  child), and let the parent exit. If it hangs, `process._getActiveHandles()` in the host shows
  what is holding it. `auth.js`:109's interval is `unref`'d and harmless.
- **T4: persistence writes.** `_persist` runs after every successful Mutation and writes the whole
  world (index.js:412-437). Two consequences:
  1. **Point every path at the temp dir before the first require.** The paths are captured at
     module load (index.js:57-58, mutation-log.js:20, facility-config.js:47-53,
     airspace-config.js:32, stereo-routes.js:44), and a mistake writes into the human's
     `crc-sync/state/`. Hence the startup assertion in step 1.
  2. **Disk.** Log lines are ≈1.2 KB each (10 lines were ≈11.8 KB in the research probe) and an
     FDR is ≈2.2 KB of JSON. A 240-minute stress run can write gigabytes in total, because the
     whole snapshot is rewritten per Mutation. Check free space up front, clean the temp dir
     unless `--keep-state`, and report total bytes written. If a run becomes I/O-bound, report
     that as data (it is H3's cost). Do not stub `_persist` out: the restart checks need it.
- **T5: memory noise from logging.** crc-sync logs through `console.warn/error`. Examples: the
  correlation rate warning (correlation-reconciler.js:324), `[efsp-facility-config] failed to load
  …` at every boot, and the board-store catch-all. In the host:
  - replace `console.*` **before** requiring `src/` with a function that increments a counter per
    message prefix, keeps only the first 20 full texts per prefix, and writes lines to
    `out/host.log` via an append stream;
  - never accumulate strings in memory;
  - in the driver, cap `events.ndjson` at 50 entries per category, then count only;
  - with `advanced` serialization, forward nothing the driver does not use.
- **T6: host-side buffers.** A fake socket's `send` must forward and forget. Keeping `sent` arrays
  (as the heartbeat test does, ws-hub-heartbeat.test.mjs:13) is a leak the soak would then
  "find".
- **T7: the ledger is O(run).** Tens of thousands of UUIDs in the **driver** are fine. That is the
  reason for D1. In `--inproc` mode, say in the report that heap numbers include the driver.
- **T8: a disconnect releases Positions** (`efsp.onDisconnect` → `positionStore.onDisconnect`,
  position-store.js:197-201). A released Position's Strips stay owned by it, since
  `onDisconnect` does not reassign; set-positions vacating does (efsp-ws.js:545-563). Scripts
  whose next actor is disconnected must **wait**, not fail. `NOT_HOLDING_POSITION` from a
  reconnecting client is expected until its `set-positions` ack arrives.
- **T9: the observer and combined Positions.** An Observer's Mutations are refused
  `NOT_HOLDING_POSITION` (efsp-ws.js:155-158). Never schedule actions for it.
- **T10: `restore()` resets `_seq` to 0.** Any shadow logic keyed on seq monotonicity across a
  restart is wrong by construction. That is H4. Detect it; do not code around it.
- **T11: parallel lanes move code under you.**
  - L5 edits `mutation-log.js` (retention) and `index.js` (registration).
  - L7 reshapes obligation alerts in `ws-hub.js`/`forwarding-obligations.js`.
  - L1 adds a store to `_persist`.
  - L10 changes `surveillance/iff.js`.

  Depend only on the constructors and methods listed in §3. Treat `broadcastEfspObligationAlert`
  as optional (`typeof … === 'function'`). If the log gains rotation, read every file matching
  the log's basename in the temp dir. List these touch-points in `docs/wip/L6.md` so the
  integrator re-runs the soak after merging L1, L5 and L7.
- **T12: `readAll()` is not for this.** `MutationLog.readAll` (mutation-log.js:42) parses the
  whole file into memory. Use `readline` over a read stream.
- **T13: the tracks' `Date.now`.** `TrackStore.update` stamps `Date.now()`, which is virtual. If
  you forget to send `now` with a `tracks` command, every track looks 12 s stale and correlation
  collapses into TRACK_LOST storms. The symptom is a correlation rate of 0.
