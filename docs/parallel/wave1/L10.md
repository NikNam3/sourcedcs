## 1. Mission

Today the colour of every contact (`iffState`) is computed from the **DCS coalition**
(`crc-sync/src/surveillance/iff.js:24-39`). No real sensor knows a contact's coalition. ADR 0059
built a surveillance model where the wire carries only what the controller's own sensors know
(position from a radar return, code and Mode C from an interrogating radar, height from a 3D radar,
identity from the datalink) and left one leak open, in its own words (`docs/adr/0059-sensors-decide-what-the-wire-says.md:217-218`):

> **Auto-IFF still reads the DCS coalition** (`surveillance/iff.js`). That is truth leaking through
> colour, and it should come from IFF interrogation (Mode 4/5) instead.

Your job is to close it:

1. Automatic IFF comes from **what an interrogator got back**: a valid Mode 4/5 reply (crypto,
   own side only), a Mode 3/C reply, a datalink PPLI, or nothing. A controller's declaration still
   wins over all of it.
2. It is computed **per session**, from that controller's own radars, inside
   `surveillance/presentation.js`, like everything else on the wire. Two controllers looking at the
   same aircraft through different radars can see different colours, and that is correct.
3. The `invisible` state (enemy aircraft on the ground are never sent) is also a coalition read. It
   is replaced by a rule that reads no coalition (§5.4).
4. The label-revision mechanism in `ws-hub.js` keeps working: a declaration still shows at once
   without waiting for a sweep.

### Out of scope

- **The client.** `crc-desktop/app/public/js/iff.js`, `geojson.js`, `map-setup.js` and
  `track-label.js` need no change: the set of `iffState` values on the wire does not change, and
  the client already has no `invisible` handling (checked: `grep -rn invisible
  crc-desktop/app/public/js` finds only unrelated comments). **The client's BLUE/RED
  `userCoalition` toggle (`crc-desktop/app/public/js/iff.js:21-45`) stays exactly as it is.** It
  picks the airport panel's bullseye and drives nothing about the picture. Do not touch it.
- New IFF states. `IFF_STATES` (`crc-sync/src/surveillance/iff.js:15`) must stay byte-identical to
  the client copy (`crc-desktop/app/public/js/iff.js:10`). No `unknown` or `pending`.
- Mode 1/2 codes, Mode 5 as a separate mode, an IFF "source" on the wire (see open question Q7).
- Whether an AI correlated to a Strip squawks the Strip's code (0059's second open item).
- Correlation. **A correlated Strip does not change IFF.** Correlation gives a callsign (label), not
  an affiliation, and a flight plan is not an IFF reply.
- Any EFSP file (`crc-sync/src/efsp/**`, `panels/efsp/**`).

## 4. The model options

The question is which sensor answers "whose side is it on", and what each kind of contact answers
back.

### Option A: per-session interrogation in `presentTrack` (recommended)

- Radars gain **`caps.mode4`**: the radar carries a Mode 4/5 interrogator. It is independent of
  `caps.ssr` (Mode 3/C). Tactical radars (awacs, fighter, carrier search) have it, ATC radars
  (airport, approach, carrier approach) do not (Q2).
- The transponder model gains **`mode4Of(track)`**: would this contact give a *valid* Mode 4 reply
  to our interrogator? Valid means the right crypto, so only own-side units can:
  - a player: SRS entry present, `squawkStatus !== 0`, `mode4` true, **and** own coalition (an enemy
    player with the switch on has the wrong keys);
  - own AI aircraft and own ships: yes, from config `transponder.mode4For: ['own']` (Q1, Q5);
  - neutral and hostile AI, ground vehicles: no.
- `describe()` stops computing `iffState`. It carries `mode4` (a boolean) beside `transponder`.
- `presentTrack` classifies from what *this session's current radars* got (§5.3 table). Declaration
  first, then datalink PPLI, then Mode 4, then Mode 3/C, else `bogey`.
- `invisible` is replaced by a ground-clutter rule: an aircraft on the ground is presented only when
  it answers an interrogation or reports on the datalink (§5.4).
- The label fingerprint drops the automatic `iffState` and keeps `iffOverride`. An automatic change
  arrives with the next fresh return, which is when a real interrogation happens anyway.

**Why:** it is the model 0059 already uses for Mode 3/C and height. It reads no coalition in
classification (coalition stays only inside the transponder model, where it stands for crypto keys,
exactly as `syntheticFor` already does), and it is per session by construction.

### Option B: coalition-free but global, in `describe()`

Classify from `mode4Of` and `transponderOf` in `describe()`, ignoring which radars saw the contact.

- Smaller: no fingerprint change, `presentTrack` untouched apart from `invisible`.
- **Rejected:** a controller with a primary-only radar, or an ATC radar with no Mode 4 interrogator,
  would still be told "friendly". That is the same kind of leak one layer down: the aircraft's
  answer reaches a controller whose sensors never asked the question. It also breaks 0059's rule
  that the presentation runs against the session's own sensors.

### Option C: Option A plus a new `unknown`/`pending` state

Separate "not interrogated" (`pending`) from "interrogated, no reply" (`unknown`/`bogey`).

- **Rejected for this lane:** it changes `IFF_STATES`, which must stay byte-identical with the client
  (`crc-desktop/app/public/js/iff.js:4-10`), needs icons and colours in `map-setup.js:332-348`, and
  would let declarations be made to it (`collab-store.js:13`). `bogey` already means "identity
  unknown" in GCI brevity. Record it in the ADR as a considered alternative.

### Sub-options for `invisible` (the enemy on the ground)

- **A1, ground clutter (recommended):** an aircraft on the ground (`onGround`) with no cooperative
  answer (no Mode 3/C to an SSR radar, no valid Mode 4 to a Mode 4 radar, no datalink) is not
  presented. A parked aircraft is a stationary return on the surface, and moving-target filtering
  removes it; a squawking one is shown by its reply. It keeps today's behaviour for the common
  cases: hostile AI (no transponder) parked → hidden, own and neutral AI (synthetic squawk) parked →
  shown. It changes one: **an own player on the ground with no SRS client disappears from the
  airport radar** (today it is `friendly`, Q4).
- **A2, drop it:** the airport radar shows every aircraft on the ground it sees, classified like any
  other. Simplest, but without terrain data (`CRCSYNC_MAPTILER_KEY` is optional) the 40 nm airport
  radar then shows the ramp of every airfield within 40 nm, including enemy ones.
- **A3, a surface range gate** (ground aircraft only within a few nm of the radar, like a surface
  movement radar). Most realistic, but it belongs in `coverage.js`, which this lane does not own.
  Name it in the ADR as the later refinement.

### 5.4 Per-session consequence and the relabel mechanism

- The automatic state now depends on the session's radars, so it cannot be in `describe()` or in the
  global fingerprint. The **declaration** (`iffOverride`) is global and stays in the fingerprint,
  so declare/clear still bumps `rev` and relabels at once (the `ws-hub-coverage.test.mjs:174-191`
  case).
- An automatic change (Mode 4 switched on, a new radar with an interrogator, a new datalink report)
  reaches the client with the **next fresh return** in `updated`. That is when a real interrogation
  happens, so it is the correct timing, not a compromise. Every datalink report moves `hit.at`
  (`ws-hub.js:283-286`), so PPLI is fresh by construction.
- A relabel for another reason (a tag, a correlation) recomputes `iffState` from the current
  transponder state, which can reveal a Mode 4 change a few seconds before the next sweep. Accept
  it, and note it in the ADR. Caching the last interrogation per session is not worth the state.

### Step 2: `mode4Of` (`crc-sync/src/surveillance/transponder.js`, `tests/transponder.test.mjs`)

Put it in `Transponders`, beside `transponderOf`: it is "what the aircraft sends", it already
holds `srs`, config and `coalitionClass`. **Do not put it in `iff.js`**: `transponder.js:23`
requires `iff.js`, so `iff.js` requiring `transponder.js` is a require cycle.

```js
// constructor (transponder.js:61-66): also
this._mode4For = new Set((config && config.mode4For) || ['own']);

/**
 * Would this contact give a VALID Mode 4/5 reply to one of our interrogators?
 * Valid means our crypto, so only our own side can. A player needs SRS with
 * the transponder on and the Mode 4 switch on. AI aircraft and ships of a
 * `mode4For` class are assumed keyed. Vehicles have no IFF.
 */
mode4Of(track) {
  if (!track) return false;
  const cat = track.category;
  if (cat !== 1 && cat !== 2 && cat !== 4) return false;
  if (coalitionClass(track.coalition) !== 'own') return false;   // the crypto key, not the colour
  if (track.player) {
    const e = this._srs ? this._srs.getTransponder(track.player) : null;
    return !!(e && e.squawkStatus !== 0 && (e.mode4 === true || e.mode4 === 1));
  }
  return this._mode4For.has('own');
}
```

`mode4For` is a class list like `syntheticFor`, for symmetry, but only `'own'` can ever be honoured
(the crypto check comes first). Document that in the config comment.

Tests (reuse `srsWith` / `air`, `transponder.test.mjs:11-16`):
- own player: mode4 true + status 1 → true; mode4 false → false; status 0 → false; no SRS entry →
  false; legacy entry with `squawkStatus` undefined and `mode4: true` → true.
- hostile player with `mode4: true, squawkStatus: 1` → false. Neutral likewise.
- own AI aircraft → true; neutral and hostile AI → false; `config.mode4For: []` → own AI false.
- own ship (category 4) → true; own vehicle (category 3) → false.

## 11. Open questions (with the default to take)

Log each one you rely on under "Defaults taken" in `docs/wip/L10.md`. Check `docs/parallel/decisions.md`
first: a decision there wins.

- **Q1 — Do own AI aircraft answer Mode 4?** DCS AI has no IFF switch. Default: **yes**, via
  `transponder.mode4For: ["own"]`. Otherwise every own AI flight is neutral on the GCI scope.
- **Q2 — Do ATC radars (airport, approach, carrier approach) interrogate Mode 4?** Default: **no**.
  ATC radars read Mode 3/C only, tactical radars read Mode 4 too. Consequence: on TWR/APP/CTR,
  cooperative traffic is `neutral` and non-cooperative traffic is `bogey`, own or not. If the human
  wants own traffic blue on the RAPCON scope, it is a one-line `DEFAULT_CAPS` flip
  (`approach: {mode4: true}`); nothing else changes.
- **Q3 — A Mode 3/C reply with no valid Mode 4: `neutral` or `bogey`?** Default: **`neutral`**. It
  keeps civil and neutral AI (synthetic squawk) grey as today and separates cooperative from silent
  traffic. It is an ID criterion, so it is `[SOURCE-DEFINED]`: say so in the ADR.
- **Q4 — What replaces `invisible`?** Default: **the ground-clutter rule (A1)**. Accepted cost: an
  own player on the ground with no SRS client is no longer shown on the airport radar. The A3 range
  gate is the later refinement, in `coverage.js`, not this lane.
- **Q5 — Ships and ground vehicles.** Default: own ships answer Mode 4 (warships carry IFF), under
  the same `mode4For`; no ship answers Mode 3; ground vehicles answer nothing and are `bogey` unless
  declared.
- **Q6 — Should a moving aircraft on the ground show as a primary return (MTI)?** Default: **no**.
  It would flicker at every hold-short. Name it in the ADR as a possible refinement.
- **Q7 — Should the wire say why a contact is friendly** (a `MODE4` entry in `sources`)? Default:
  **no**. It changes the wire vocabulary and the client, both out of scope. Note it as follow-up.
