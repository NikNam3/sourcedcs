## 1. Mission

Build the carrier's **pure domain model** under `crc-sync/src/efsp/carrier/`, with unit tests.
Then write **ADR 0064**, which designs how L17 will wire that model into the EFSP (the Roles, the
CARRIER Facility, permissions, broadcast state and client surfaces). L17 should be able to build it
without redesigning anything.

"Pure" means what `correlation-match.js`, `release-envelope.js` and `radars.js` mean: plain
functions over plain objects. That rules out:

- a clock (callers pass `now`);
- `require` of any store, `index.js`, `facility-config.js`, or anything that reads disk at load time;
- sockets or mutation of arguments.

Every function returns a new value. Every function that can refuse returns
`{ ok: false, reason, detail }` and **never throws on bad input**, so that L17's store can call it
from inside an `apply()` without a try/catch per op. It will still have the store-wide backstop
every store has, e.g. `marsa-store.js:290-295`.

What you deliver, concretely:

1. **The marshal stack**. The stack index is the authoritative value. Angels, marshal DME and push
   time are derived from it. Insertion renumbers everyone above in one operation, and nothing
   derived can be written.
2. **The recovery Case as a value**. It has transitions, weather-floor advice, and a derivation
   that changes every entry's displayed fields when the Case changes.
3. **Ship state**. A record built from a DCS ship track, with the final bearing computed from ship
   heading and the angled-deck offset. It cannot be hand-entered.
4. **The carrier flight record**. The FDR-level fields the marshal message needs (EEAT, approach
   button, bingo, fuel/low state), shaped so that EEAT survives launch to recovery by construction.
5. **The four heterogeneous transfer kinds, as data.**
6. **ADR 0064**, covering both what you built and the design L17 must implement.
7. **`docs/wip/L4.md`**, your notes for the shared docs plus the defaults you took.

## 3. What the guide says, distilled (§9.12 is binding; quotes are verbatim)

- **Case is global session state, owned by `CV_PRIFLY`**, that "reinterprets every carrier Strip
  simultaneously. Model it as a broadcast session property, never a per-Strip attribute."
- Case criteria:
  - **Case I**: ceiling ≥ 3,000 ft and visibility ≥ 5 NM.
  - **Case II**: ceiling ≥ 1,000 ft and visibility 5 NM.
  - **Case III**: any ceiling below 1,000 ft or visibility below 5 NM, **and all night
    operations**.
- **Case III: "one integer drives four displayed fields."**
  - Marshal holding is on the **180 relative to BRC**, at **1 NM per 1,000 ft plus 15** (angels 8
    → 23 DME).
  - Minimum altitude **6,000 ft**, with **1,000 ft** vertical separation.
  - **1-minute** push separation, and aircraft arrive **±10 seconds**.
  ```
  stackIndex   uint8     // AUTHORITATIVE — everything below is derived
  angels       = 6 + stackIndex
  marshalDme   = angels + 15
  pushTime     = charlieTime + stackIndex minutes
  ```
- Rule 1: "Store the index; compute the display. Do not let a controller hand-edit DME."
  Defect **D16**: "Marshal DME, angels or push time editable independently of stack index."
- Rule 2: "A low-fuel aircraft inserted low renumbers everyone above it, shifting altitude, DME and
  push time together." Re-sequence MUST be the cheapest gesture, and per-field editing MUST NOT be
  the path to it.
- Rule 3: "**Case I is not a controller-sequenced recovery.**"
  - Stack altitudes are squadron-assigned, from 2,000 ft AGL, 1,000 ft apart, within 5 NM.
  - Under Zip Lip the pilots break the deck themselves.
  - The Case I Bay is a low-interaction altitude-keyed list. "**Do not build Case I around push
    times.**"
- Rule 4: the Case II transition fires on a **pilot report**. Aircraft fly Case II procedures
  outside 10 NM, and Case I inside 10 NM or after "see you". This is an ownership transfer
  `CV_MARSHAL` → `CV_PRIFLY` with an unusual trigger type.
- Rule 5: "Ship state is a banner, not a field." Speed, heading, position, time and altimeter are
  shared by every carrier Position, and "**final bearing is computed from ship heading, not
  typed**."
- Rule 6: store the approach **button** number, never a frequency.
- Rule 7: "`EEAT` is issued before launch … MUST survive from the departure Strip through to
  recovery. It is the field most likely to be missed."
- Marshal message field set, in order:
  `CALLSIGN · TYPE · CASE · APPROACH TYPE · MARSHAL RADIAL · MARSHAL DME · ANGELS · EAT/PUSH ·
  EXPECTED FINAL BEARING · APPROACH BUTTON · ALTIMETER · SHIP WX · FUEL/LOW STATE · BINGO FIELD ·
  BINGO FUEL · EEAT`.
- "SHOULD validate internal consistency": angels + 15 = DME, and the marshal radial is roughly the
  reciprocal of the final bearing.
- Four transfers, "MUST NOT be unified behind one button":

  | Transfer | Trigger |
  |---|---|
  | Marshal → Approach | controller-initiated |
  | Approach → Final | radar acquisition |
  | Final → LSO | the pilot's "ball" call |
  | Case II Marshal → PriFly | pilot report ("see you") |

- `CV_APP1`/`CV_APP2` are **parallel lanes**, fed **alternately from the Marshal stack in push
  order**. The division of duties is **OQ8**, not documented publicly. Whatever SOURCE picks is
  `[SOURCE-DEFINED]`.
- §7.10: `PAR` and the carrier Final are "the same job". The `FINAL` Strip is minimal, needs **no
  data entry during the approach**, and a `FINAL` Bay holds one Strip at a time.
- §4.1: `CV_MARSHAL` → `MARSHAL`; `CV_PRIFLY` → `PATTERN`, owns the CCZ and **sets the recovery
  Case**; `CV_APP1`/`CV_APP2` → `MARSHAL` → `FINAL`. Rule 4: PriFly (like RSU) is "supervisory …
  over a visual pattern, not radar control"; its Bay is a pattern board, not a strip rack.
- §4.2 Bays:
  - `CV_MARSHAL`: Marshal Stack (ordered by stack index) · Departures · Coordination.
  - `CV_PRIFLY`: Deck state · Pattern board · Case selector.
  - `CV_APP1`/`CV_APP2`: Lane (one Rack, ordered) · Bolter/Waveoff.
- §9.13: the carrier does **not** talk to Centre (FACSFAC instead, OQ9). `separation_regime =
  DUE_REGARD` inside the Carrier Control Area.

WP7A's acceptance bullets (§13, lines 1406-1415). **Yours are 1, 2 and 5**; the rest are L17's or
L18's but your design must make them possible:

1. Inserting an aircraft low in the marshal stack renumbers altitude, DME and push time for everyone above it, in one gesture.
2. Marshal DME, angels and push time are **not independently editable**.
3. Changing the Case re-renders every carrier Strip at once.
4. The four transfer triggers are distinguishable in the UI — controller-initiated, radar acquisition, pilot "ball" call, pilot "see you" report.
5. Final bearing is computed from ship heading and cannot be hand-entered.
6. A `FINAL` Strip requires no data entry during an approach.
7. `SFA` transfer rotates a controller onto the aircraft's frequency; the Strip's frequency does not change.
8. `EEAT` set before launch is still present on the recovery Strip.

Common result shapes, used everywhere:

```js
// refusal — reason is one of the codes the stores already use

```

`changed` is how L17 turns "one gesture" into **one delta**. It lists every `fdrId` whose
*derived* display changed, in stack order.

### 5.1 `angles.js`

### 5.2 `recovery-case.js`: Case as a value

```js
const CASES = ['I', 'II', 'III'];
// Any Case → any other Case. PriFly may go I→III directly (weather closes in), and III→I at dawn.
// Written as a table anyway (airspace-store.js:31-43's shape), so a future restriction is one edit.
const LEGAL_CASE_TRANSITIONS = { I: ['II', 'III'], II: ['I', 'III'], III: ['I', 'II'] };
const DEFAULT_CASE = 'III';   // recommended default, see Open Question Q5

/** The record L17's store will hold per hull and broadcast. */
// RecoveryCase = { value: 'I'|'II'|'III', setBy: string|null, setAt: number|null,
//                  history: [{ at, by, from, to, note }] }      // append-only

initialRecoveryCase()                         // → { value: DEFAULT_CASE, setBy: null, setAt: null, history: [] }
setCase(current, to, { by, at, note })        // → { ok, case } | { ok:false, reason:'VALIDATION_ERROR' }
                                              //   refuses unknown `to`, and to === current.value (no-op is not a transition)
caseFloor({ ceilingFt, visibilityNm, night }) // → 'I' | 'II' | 'III' | null
caseAdvisory(caseValue, wx)                   // → null | { floor, detail }
isSequencedCase(caseValue)                    // → caseValue === 'II' || caseValue === 'III'
```

**`caseFloor`, from the §9.12 criteria verbatim.** It returns the *least restrictive Case the
weather allows*:

- `night === true` → `'III'` ("and all night operations");
- `ceilingFt < 1000 || visibilityNm < 5` → `'III'`;
- `ceilingFt < 3000` → `'II'` (it is ≥ 1000 and vis ≥ 5 by now);
- otherwise → `'I'`.

If any input is `null`/`undefined`/non-finite, it returns `null` (unknown weather). **It never
guesses.**

**`caseAdvisory` is advice, not a gate.** It returns a mismatch only when the set Case is *less*
restrictive than the floor (I when the floor is III, for example). `null` otherwise, including when
the floor is unknown. **`setCase` never consults the weather.**

- Guide §4.1 says PriFly *sets* the Case.
- The weather inputs are not reliably available.
- ADR 0058's "indicators only when wrong" is the house style.
- Refusing PriFly's call on a model's reading would be D11 (fabricating authority).

Say this in the ADR.

**Why the Case is a record and not a Strip field** is §9.12's first paragraph. Your derivation in
§5.3 takes the Case as a *parameter*, so no stack entry stores it. The acceptance test "changing
the Case changes every entry's derived fields" (§8) follows from that shape.

### 5.3 `marshal-stack.js`: the stack

#### The stored record: only authoritative values

```js
// MarshalStack = {
//   hullId: string,
//   charlieTimeUtc: number|null,   // epoch ms, UTC — when push index 0 is due. Set by CV_MARSHAL.
//   entries: MarshalEntry[],       // sorted by stackIndex ascending; stackIndex unique
// }
// MarshalEntry = {
//   fdrId: string,                 // KEY. Never a stripId — docs/adr/0045 (see trap T3)
//   stackIndex: integer,           // AUTHORITATIVE. 0 ≤ stackIndex ≤ maxIndex
//   status: 'HOLDING' | 'PUSHED',
//   caseIAngels: integer|null,     // Case I only: squadron-assigned altitude, thousands of feet, ≥ 2
// }
const ENTRY_KEYS = ['fdrId', 'stackIndex', 'status', 'caseIAngels'];   // exhaustive — see validateStack
const STACK_DEFAULTS = { maxIndex: 19 };   // [SOURCE-DEFINED] — Q4; angels 6..25, DME 21..40
```

**No `angels`, `marshalDme`, `pushTimeUtc`, `marshalRadial` or `finalBearing` is ever stored.**
The rules:

- `validateStack(stack)` **rejects** any entry carrying a key outside `ENTRY_KEYS`, with
  `VALIDATION_ERROR` and "angels/DME/push time are derived from the stack index (§9.12) and cannot
  be set".
- `normalizeStack(raw)` is for restore. It **drops** such keys rather than failing, then validates
  the rest. Restore should come up (T9).

This is what makes bullet 2 structural, not a UI convention. It is the same move as
`block-map.js:462`'s `resolveBlockTarget` returning `null` for `system` Blocks.

#### Derivation: a pure function of (entry, Case, stack, ship state)

```js
deriveEntry(entry, { caseValue, charlieTimeUtc, shipState })
// Case II / III (sequenced):
//   angels            = 6 + stackIndex                       // §9.12
//   marshalDme        = angels + 15                          // §9.12
//   pushTimeUtc       = charlieTimeUtc == null ? null : charlieTimeUtc + stackIndex * 60_000
//   pushWindowUtc     = pushTimeUtc == null ? null : [pushTimeUtc - 10_000, pushTimeUtc + 10_000]   // "arrive ±10 seconds"
//   marshalRadialDeg  = shipState && shipState.brcDeg != null ? reciprocal(shipState.brcDeg) : null  // "the 180 relative to BRC"
//   expectedFinalBearingDeg = shipState ? shipState.finalBearingDeg : null   // computed in ship-state.js, never here
//   minimumAltitudeOk = angels >= 6                          // always true by construction; asserted in a test
// Case I (not sequenced):
//   angels            = entry.caseIAngels                    // may be null → the Strip shows "assign altitude"
//   marshalDme        = null                                 // render "≤5 NM" — §9.12 "within 5 NM"
//   pushTimeUtc       = null, pushWindowUtc = null           // "Do not build Case I around push times."
//   marshalRadialDeg  = null                                 // overhead holding, no radial
//   expectedFinalBearingDeg = shipState ? shipState.finalBearingDeg : null
// → { fdrId, stackIndex, status, caseValue, angels, marshalDme, pushTimeUtc, pushWindowUtc,
//     marshalRadialDeg, expectedFinalBearingDeg } — a NEW object; Object.freeze it
deriveStack(stack, { caseValue, shipState })   // → derived entries in stackIndex order
checkConsistency(derived, { radialToleranceDeg = 15 } = {})
// → [] or [{ code, detail }] — §9.12's "SHOULD validate": angels + 15 === marshalDme (sequenced Cases),
//   and angularDiff(marshalRadialDeg, reciprocal(expectedFinalBearingDeg)) <= tolerance when both known.
//   With the guide's own conventions the second difference is exactly the angled-deck offset (~9°),
//   hence a default tolerance of 15 — [SOURCE-DEFINED], Q3.
```

`checkConsistency` exists even though the derivation can never break it. It will catch the day
someone "optimises" a stored DME back in, and §9.12 asks for it.

#### Operations: each is one op, and returns the whole new stack plus `changed`

```js
emptyStack(hullId)                                   // → { hullId, charlieTimeUtc: null, entries: [] }
insertAt(stack, { fdrId, stackIndex, caseIAngels = null }, opts = STACK_DEFAULTS)
append(stack, { fdrId, caseIAngels = null }, opts)   // insertAt(next free index above the highest entry)
move(stack, { fdrId, toIndex }, opts)                // re-sequence: remove + insert atomically — THE cheap gesture
remove(stack, { fdrId, closeUp = false })            // diverted / bingo / dropped
closeUp(stack, { fromIndex })                        // explicit "close up the stack" above a gap
markPushed(stack, { fdrId })                         // commenced — NO renumbering
setCharlieTime(stack, { charlieTimeUtc })            // shifts every push time; changed = every HOLDING sequenced entry
setCaseIAngels(stack, { fdrId, caseIAngels })        // Case I only; integer ≥ 2 — the one per-entry value a controller types
applyStackOp(stack, op, opts)                        // dispatcher: op.kind ∈ STACK_OP_KINDS, else VALIDATION_ERROR
const STACK_OP_KINDS = ['InsertAt', 'Append', 'Move', 'Remove', 'CloseUp', 'MarkPushed', 'SetCharlieTime', 'SetCaseIAngels'];
```

Rules. Each one is a test.

- **Insertion renumbers everyone at or above, together** (§9.12 rule 2). `insertAt(i)` gives every
  entry with `stackIndex >= i` `stackIndex + 1`, in one returned stack. `changed` = the inserted
  `fdrId` plus every shifted `fdrId`. Deriving before and after shows every shifted entry's angels,
  DME **and** push time each moving by +1 / +1 / +60 s. That is bullet 1.
- **Refusals** (`VALIDATION_ERROR`):
  - `stackIndex` not an integer;
  - `stackIndex < 0`;
  - an index that would push any entry above `maxIndex` (the stack is full; say so and name the
    top entry);
  - `stackIndex > highest + 1` (no gap created by insertion);
  - `fdrId` already in the stack;
  - **inserting at or below the highest `PUSHED` entry's index**. You cannot slide an aircraft
    under one that has already left the stack; its push time is in the past and renumbering it
    would rewrite history.
- **`markPushed` does not renumber** (trap T4). Aircraft push bottom-up at their own times. If a
  push shifted everyone above down a slot, every other aircraft's push time would jump a minute
  earlier. That is the exact drift D16 names.
- **`remove` leaves a vacancy by default.** A gap is legitimate: the aircraft above keep their
  altitude and push time.
  - `closeUp: true` (or a separate `closeUp` op) shifts every entry above the gap down by one, again
    in one op with a `changed` list.
  - The controller chooses. Neither happens implicitly.
- **`move`** is remove-without-close-up plus insert, atomically, with the same refusals. It is the
  "re-sequence is the cheapest gesture" path. Moving an entry *down* renumbers the entries it passes.
- **Nothing changes the input**: deep-freeze the input in tests and assert no throw.
- Ops never read the Case. The stack is the same stack in every Case; only the *derivation* reads
  the Case. That is why a Case change needs no stack op (§5.2) and why a Case I → III switch yields
  a valid sequenced stack immediately, in check-in order.

### 5.4 `ship-state.js`: hull config and the ship-state record

#### Hull config (the shape L17 will persist; you only define and validate it)

```js
// HullConfig = {
//   hullId: string,                          // SOURCE's own name, e.g. 'CVN-1' (Flashbang 1.6.yaml:31)
//   match: { unitName?: string, type?: string, coalition?: 'own'|'any' },   // how to find the live track
```

- **Match by DCS unit name first, then by type.** Never by track id: ids re-mint on every crc-sync
  restart (ADR 0045, trap T3).
- If `type` matches more than one ship, return `null` with no guessing. The caller shows "hull
  ambiguous — configure unitName".
- `coalition: 'own'` compares against an injected `ownCoalition`, the same idea as
  `station-coverage.js:42`'s opt. Do **not** `require('../../surveillance/iff')` for
  `USER_COALITION`; inject it.

**The angled-deck offset is not in the guide.** §9.12 says the final bearing is computed from ship
heading and gives no offset.

- The ~9° port angle of a Nimitz-class landing area is the commonly published figure, and the
  squadron flies `CVN_75` (§4.1).
- Ship it as a per-type default table **labelled `[SOURCE-DEFINED]`**, overridable per hull.
- For any type not in the table (`CV_59`, `LHA_Tarawa`, `Kuznetsov`, anything new),
  `angledDeckDeg` is `null` and the final bearing is **`null` with a reason**, not a guess. That is
  D11's rule: do not fabricate a number.

Record this in ADR 0064 and as Q2.

#### The ship-state record

```js
// ShipState = {
//   hullId, trackId /* transient, never trusted after restore */, unitName, type,
//   lat, lon,
//   headingDeg,                 // from track.heading, normDeg'd, as delivered
//   headingRef: 'GRID',         // DCS-gRPC orientation.heading is flat-world (common.proto:419-420)
//   brcDeg,                     // = Math.round(headingDeg) normalised — see below
//   finalBearingDeg,            // = normDeg(brcDeg - angledDeckDeg), or null
//   finalBearingUnavailable: null | 'angled deck not configured for <type>' | 'no ship track',
//   speedKt,                    // track.groundSpeed (m/s) × 1.943844, rounded; null if groundSpeed null
//   altimeterInHg,              // from inputs, see below; null if unknown
//   atUtc,                      // `now` passed in
//   stale: boolean,             // true when the track is missing and this is the last-known state
// }
computeFinalBearing(brcDeg, angledDeckDeg)          // → normDeg(brcDeg - angledDeckDeg) | null if either is null
buildShipState({ hull, track, altimeterInHg = null, now })   // → ShipState  (track null → see staleFrom)
staleFrom(previous, now)                              // → previous with stale:true, atUtc unchanged
shipStateChanged(prev, next, { headingStepDeg = 1 } = {})   // → boolean: brcDeg / finalBearing / speedKt / altimeter / stale changed
applyShipStateInput(state, input)                     // the ONLY controller-writable path
// accepts exactly { altimeterInHg } (a number in a sane band, e.g. 27.00–32.00) → { ok, shipState }
// ANY other key — finalBearingDeg, brcDeg, headingDeg, speedKt, lat, lon — → VALIDATION_ERROR
//   "final bearing is computed from ship heading (§9.12 rule 5) and cannot be entered"
inHgFromPa(pa)                                        // helper for L17's weather-derived default: pa / 3386.389
```

- **BRC.** §9.12 rule 5 says "computed from ship heading", so BRC *is* the ship's heading, rounded
  to a whole degree.
  - A real ship in a turn is not on BRC. `shipStateChanged`'s 1° step keeps the banner from
    re-broadcasting every tick while it turns.
  - Do **not** add a typed BRC override. Rule 5 is explicit that the real system computes it. A
    typed BRC is Q6 if anyone asks.
- **Final bearing = BRC − angled-deck offset.** The landing area is angled to port, so the final
  bearing is *left of* (less than) the ship's heading. Test the wrap: BRC 5°, offset 9° → 356°.
- **Altimeter.** This is the one banner value DCS does not give per ship. The module takes it as an
  input. L17 decides the source; the recommendation is theater sea-level pressure from
  `grpc-client.js`'s `'weather'`, with PriFly/Marshal allowed to override it through
  `applyShipStateInput`.
- **Time** is `atUtc`, the `now` you are given (the banner's "time"). No clock read.

### 5.5 `flight-record.js`: FDR-level carrier fields, EEAT, and the marshal message

**The design point: EEAT survives launch → recovery because it is on the flight, not on a Strip.**

- One FDR spans the flight's whole life. Strips come and go:
  - the launch Strip at CV_MARSHAL's Departures Bay is dropped after launch;
  - the recovery Strip is a new `MARSHAL` Strip on the **same `fdrId`** (see §6.3);
  - per-Facility replicas are covered by ADR 0013.
- An EEAT held as a Strip annotation dies with the launch Strip. That is exactly "the field most
  likely to be missed", missed by the software.
- So EEAT, the approach button, bingo and fuel/low state live in an **`fdr.carrier` namespace**.
  L17 adds it to `fdr-store.js` the way `defaultMilitary()` (`fdr-store.js:195-220`) was added.
  You define the shape and the validators.

### 6.6 Where the carrier's state lives: `CarrierStore` (new store, L17)

A **sixth store**, peer to MarsaStore. It is not on the Board and not on the FDR, for the same
reason airspace (ADR 0034) and MARSA (0051) are not: the Case and the stack are facts about the
*ship's recovery*, spanning many flights.

- **Keyed by `hullId`.** One record per configured hull:
  `{ hullId, rev, recoveryCase, stack, shipInputs: { altimeterInHg }, transitions: [] }`.
- **`apply(mutation, actingPositionId, by)`** with `op.kind`:
  - `SetCase` → `setCase`, needs `canSetRecoveryCase`;
  - the `STACK_OP_KINDS` → `applyStackOp`, needs `canSequenceMarshalStack`;
  - `SetShipInput` → `applyShipStateInput`.

  Plus `baseRev`/`STALE_REV`, `_recordAudit` with a `hullId` field, and never throwing
  (`marsa-store.js:241-306`).
- **Ship state is derived, not stored.** A 1 Hz server tick builds `ShipState` from the track store
  via `matchHullTrack` + `buildShipState`, and publishes only when `shipStateChanged`. The
  correlation reconciler's tick is the pattern (`correlation-store.js:328`).
  - It is **not** audited per tick.
  - On restore, `trackId` is discarded and re-matched (T3).
- **Wire.** Append per plan §2:
  - `efsp-carrier-mutation` (dispatch case + `_handleCarrierMutation` appended at the end of
    `efsp-ws.js`);
  - `efsp-carrier-delta` carrying the **whole hull record** plus the current `shipState`;
  - one snapshot key, `carriers`.
- **A Case change is one delta carrying one record.** Every client re-derives every carrier Strip
  from `(stack, Case, shipState)` with the same pure `deriveEntry`. That is how bullet 3 ("at
  once") is satisfied without per-Strip fan-out: MARSA's "the alert is a field on a record
  broadcast whole" (`marsa-store.js:34-42`).
- **The client needs `deriveEntry`.** crc-desktop cannot import crc-sync (separately deployed;
  `block-map.js:8-12`). L17 either:
  - ships derived values inside the delta (server-derived, preferred: one implementation), or
  - duplicates `deriveEntry` client-side under a parity fixture like `efsp-block-map-parity`.

  Recommend server-derived: the delta carries `derived: deriveStack(...)`.
- **The Strip ↔ stack link is `fdrId`.** A stack entry whose FDR is retired is removed without
  close-up. That is the `onFdrRetired`/`evictMissingFdrs` pair, as MARSA has it
  (`marsa-store.js:592-617`).
- **Persist** in `_persist`/`_restore` under key `carriers`, restored **intact** (Case and stack
  are controller declarations; MARSA's reasoning at `marsa-store.js:626-637`), via
  `normalizeStack`.

## 9. Traps

- **T1. Do not edit the core files** (`nla.js`, `block-map.js`, `permission.js`,
  `facility-config.js`, `index.js`, `efsp-ws.js`, `board-store.js`, `fdr-store.js`,
  `correlation-reconciler.js`, `station-coverage.js`, `radars.js`). L1 and L2 are editing some of
  them right now, and L17 owns the rest in wave 3. Your ADR *proposes* changes; it does not make
  them. A tempting "just add `MARSHAL` to `STATES_BY_ROLE` so I can test it" is a merge conflict and
  a plan violation.
- **T2. The string `FINAL`** is already an ARRIVAL **state** (`nla.js:56`, Bay `twr-final`
  `facility-config.js:159`). Your Role is `FINAL`, and your states must not be `FINAL`
  (`INELIGIBLE_STATES` and `impliesState` are role-blind string sets). Use `ON_FINAL`.
- **T3. Key by `fdrId` and `hullId`, never `stripId` or DCS track id.**
  - One flight has several Strips over its life (launch Strip, recovery Strip, per-Facility
    replicas); the stack is about the airframe.
  - DCS track ids are re-minted every crc-sync restart (ADR 0045).
  - Match the hull by unit name.
- **T4. Pushing is not removing.** `markPushed` must not renumber. If it does, every aircraft above
  gets an earlier push time the moment the bottom one commences, which is D16's drift arriving by a
  side door.
- **T5. Trigger types are metadata, not automation.** "Radar acquisition" must never become "the
  correlation reconciler moved the Strip to FINAL". §10.3 / D5 forbid surveillance-driven advances,
  and the plan's L19 has a test that nothing moves a Strip. Every carrier transfer is a controller
  gesture tagged with what prompted it.
- **T6. Heading reference.** `track.heading` is grid (flat-world, `common.proto:419-420`). Carry
  `headingRef: 'GRID'`, do all arithmetic in that reference, and never silently add magnetic
  variation. The magnetic-vs-grid call is reserved for the human (plan §5). The client's display
  conversion (`geojson.js:535-543` shows the chain) is L17's.
- **T7. Time.** EFSP stores use wall-clock UTC epoch ms (`nla.js:146-148`). DCS game time
  (`grpc-client.js` `'game-time'`) differs from it. Push times are in the EFSP convention. Do not
  mix. If a controller says "Charlie 1430", L17's UI converts HHMM to epoch ms on the current UTC
  day (§11.2: "All times UTC, four digits HHMM on Strips").
- **T8. Case I is not a sequenced stack.** No push times, no DME, no radial. It is a list keyed by
  squadron-assigned altitude (§9.12 rule 3). Resist making it "Case III with different numbers".
- **T9. Restore must not fail on legacy junk.** `normalizeStack`/`normalizeCarrierFlight` drop or
  default rather than refuse. A crc-sync that restarts into an empty carrier because one entry had
  a stray `angels` key is worse than the stray key. `validateStack` (strict) is for mutations,
  `normalize*` (lenient) for restore.
- **T10. `computeNla` falls back to DEPARTURE for an unknown role** (`nla.js:369`). This is L17's
  trap, not yours, but name it in the ADR. A MARSHAL Strip created before its NLA table is
  registered would show "Send to Clearance".
- **T11. Do not invent annex citations or real frequencies.** The annex is not in the repo, and
  §9.12 rule 6 says real carrier frequencies are not publicly documented. The only real-world
  number you add (the ~9° angled deck) is labelled `[SOURCE-DEFINED]`, overridable, and `null` for
  types you do not know.
- **T12. CJS named exports.** `module.exports = { a, b, c }` as a literal, or `.mjs` tests cannot
  `import { a }`. Match the other EFSP modules. A barrel `index.js` that does
  `module.exports = { ...require('./x') }` **defeats** Node's static detection. Write the names out
  explicitly in the barrel.
- **T13. Radar selectors do not distinguish hull or radar role.** Your ADR must not claim
  `{kind:'carrier'}` gives Approach only the approach radar. It gives everything ship-borne
  (`station-coverage.js:43`).
