# 0022 — WP4A gap-closure: APP↔CTR departure coordination, OPERATIONAL_REQUEST's 3rd response, AIT gating, and giving `trackDegradationFlag`/`airspace-owner` a real write path

## Context

WP4A's first slice shipped and was end-to-end tested for the `CTR→APP` arrival flow only. A user-reported symptom ("APP only gives me a Drop button, how does the handoff to Center work?") led to a wider gap audit against `docs/efsp-wp4a-briefing.md` §4's recommended first slice and the guide's §4.6 primitive rules. That audit found the symptom traced to something deeper than a missing button: `receiveCoordinationProposal`/`_applyCoordinationAccept` (`crc-sync/src/efsp/board-store.js`) hardcoded `role: 'ARRIVAL'`/`state: 'INBOUND'` on every minted coordination replica, regardless of which primitive or Strip proposed it — the entire replica mechanism was built exclusively for the `CTR→APP` arrival shape. The client's `_canProposeCoordination` (`bay-view.js`) compounded this by gating the Coordinate button to `strip.role === 'ARRIVAL'` for all 5 primitives, not just `HANDOFF`.

The audit also confirmed, by direct code inspection (not inference):
- `OPERATIONAL_REQUEST` only supported a binary Accept/Reject, where the guide specifies a 3-way `APPROVED`/`UNABLE`/`STAND BY` response.
- `AIT` had no config gate at all, despite guide §4.6 rule 7 requiring it be "configuration, not a default."
- `identity.trackDegradationFlag` had **no route to the UI at all**, even though `fdr-store.js` already validated it via `setField()`/`WRITABLE_PATHS` (since `docs/adr/0019`) — no Block Map entry anywhere ever routed a `SetBlock` mutation at it. The interlock that checks it (`_applyCoordinationPropose`'s degraded-note requirement) is real and tested, but nothing in the app could ever set the flag away from its `'NONE'` default through the actual UI. (An earlier draft of this ADR mischaracterized this as "no write path anywhere" and built a redundant dedicated setter before the existing `setField` validation was found — reverted; the fix below is the Block Map wiring alone.)
- `setAirspaceOwner` (Block 24A) had a working server-side setter but genuinely zero client UI — `docs/adr/0018`'s "read-only display" framing was inaccurate; `resolveBlockValue` (`strip-template.js`) didn't even have a branch for the `airspace-owner` target kind, so Block 24A always rendered blank regardless of the FDR's actual value, and `isBlockEditable()` structurally excludes it from the only edit path that existed.

This ADR also corrects a citation error found while writing it: several existing comments (`permission.js`, `bay-view.js`) cited "docs/adr/0012" for the TOFI/TACTICAL/MRU scope-cut deferral — that deferral is actually recorded in `docs/adr/0020`; `docs/adr/0012` is an unrelated, earlier ADR about NLA transitions crossing `DEPARTURE_STATE_OWNERS` boundaries. Fixed at the same time as this work, since it was found while reading the same code.

## Decision

**1. Generalize the coordination-replica mechanism to carry the sender's actual (role, state), not a hardcoded ARRIVAL/INBOUND shape.** `coordination.js` gains `COORDINATION_ELIGIBLE_STATES = { ARRIVAL: 'INBOUND', DEPARTURE: 'HANDED_OFF' }` — the doctrinal table of which (role, state) combos have a landing Bay configured on the *other* side. `_applyCoordinationPropose` validates the sender's Strip is in an eligible (role, state) combo before proposing (server-side authoritative check; `bay-view.js`'s `_canProposeCoordination` mirrors it client-side as a convenience gate, same drift-guarded duplication pattern as `COORDINATION_TARGETS`/`COORDINATION_EFFECTS`). `receiveCoordinationProposal` mints the replica with `role: fromRole, state: fromState` (passed through from the sender), not a hardcoded value. `_applyCoordinationAccept` resolves the landing Bay via `bayForImpliedState(ownerPositionId, strip.state)` (the state the replica already carries) instead of a hardcoded `'INBOUND'`, and no longer force-sets `strip.state` at all — accept only relocates a replica, it never advances its state.

No new EfspState was invented for the `DEPARTURE`/`APP→CTR` direction: `DEPARTURE_STATE_OWNERS.HANDED_OFF` already exists as `APP`'s own terminus (Drop-only, guide's real hand-off-to-Center point in the departure lifecycle); a CTR-held `HANDED_OFF` DEPARTURE Strip gets the identical Drop-only terminus, via a new `ctr-departures` Bay in `CENTER`'s facility-config mirroring `app-departures`'s exact shape. This is a **narrow correction to `docs/adr/0020`**: CTR gains the ability to *receive and hold* a handed-off DEPARTURE Strip; the actual deferred scope (`TACTICAL` Facility, MRU Positions, the D12 refusal audit, `TOFI`) is untouched and still deferred. `docs/adr/0016`'s "user-confirmed scope" framing of the original `APP→CTR` omission overstated what was, on reflection, a unilateral narrowing during implementation, never explicitly confirmed by the user — noted here rather than rewriting that ADR after the fact.

Because the eligibility check is role-based, not primitive-based, this single change also closes the audit's other finding that `POINT_OUT`/`TRAFFIC`/`OPERATIONAL_REQUEST`/`AIT` were equally ARRIVAL-only, not just `HANDOFF`.

**2. `OPERATIONAL_REQUEST`'s `STAND_BY` response.** `coordination.js`'s existing `acceptPhrase: 'APPROVED'` already made `ACCEPT`/`REJECT` semantically `APPROVED`/`UNABLE` for this one primitive — only `STAND_BY` was genuinely missing. Added as a third `op.action` value, handled by a new `_applyCoordinationStandBy` that validates the primitive is `OPERATIONAL_REQUEST` and stamps `coordination.lastStandByAt` **without** touching `coordination.state` (the request stays `PROPOSED`, unresolved) — mirrored to the peer via `receiveCoordinationResponse`'s new `'STAND_BY'` branch. Client relabels Accept/Reject to Approve/Unable and adds a third Stand By button, only for this one primitive; every other primitive's 2-button Accept/Reject is unchanged.

**3. AIT requires a written directive on file.** New per-Facility `aitAuthorized: false` config flag (`facility-config.js`, mirroring `dataOnly`'s existing shape). `_applyCoordinationPropose` rejects `primitive === 'AIT'` with `VALIDATION_ERROR` unless set. The client's snapshot payload (`efsp-ws.js`'s `_snapshotMessage`) carries `aitAuthorizedByFacility` so the popover can proactively disable the AIT option with an explanatory tooltip, rather than let a PROPOSE submit-and-silently-fail — this codebase has no generic mutation-rejection-to-toast UI at all (a separate, pre-existing, systemic gap, not fixed here), so a silent server-side-only rejection would have been a dead end for the controller.

**4. `trackDegradationFlag` and `airspace-owner` (24A) both get their first-ever UI.** These two turned out to need different fixes once actually traced:
   - `trackDegradationFlag` already had a working, validated write path (`setField`/`WRITABLE_PATHS`, since `docs/adr/0019`) — it just had no Block wired to it. `block-map.js` gains Block `'5A'`, plain `'fdr'`-routed (`path: 'identity.trackDegradationFlag'`), exactly like Block `'14B'`/`'14C'` — no new server-side machinery needed.
   - `airspace-owner` (24A) genuinely had no display path either, not just no edit path: `strip-template.js`'s `resolveBlockValue` had no branch for the `'airspace-owner'` target kind at all, so it fell through to the null/`SYSTEM_DERIVED` catch-all — Block 24A never actually showed `fdr.airspace.owner`, even read-only. Fixed by adding the missing branch.
   - Both are rendered client-side via a new dedicated `<select>`-based cell (`bay-view.js`'s `_buildEnumSelectCell`, driven by `strip-template.js`'s `enumSelectOptionsFor` — keyed by Block ID, not target kind, since `'5A'` and `'24A'` need the same picker UX despite routing differently server-side) rather than the generic free-text click-to-edit path (`isBlockEditable` still returns `true` for `'5A'` since it's plain `'fdr'`-routed, but `_buildBlockCell` checks `enumSelectOptionsFor` first and never falls through to that path for either Block).

## Alternatives considered

- **Invent a new EfspState for CTR-held departures** (e.g. `'CENTER_TRANSFERRED'`) instead of reusing `HANDED_OFF`. Rejected: `HANDED_OFF` already means exactly the right thing (owned by a Position past the point of active departure-lifecycle work, Drop-only terminus) and `DEPARTURE_STATE_OWNERS` already supports multiple owning Positions for one state (mirrors `ARRIVAL_STATE_OWNERS.INBOUND`'s existing `['APP', 'CTR']` entry) — a new state would duplicate that shape for no behavioral difference.
- **Let the client freely offer AIT and rely only on the server-side rejection.** Rejected given this codebase has no generic mutation-error surface — a controller clicking Send and getting silent nothing is worse than a disabled, explained option. Considered building a generic error-toast system instead (would also help the pre-existing silent-rejection gap for every other Mutation kind); out of scope for this pass, noted as a reasonable follow-on.
- **Give `trackDegradationFlag` a dedicated setter, mirroring `setAirspaceOwner`.** Tried first, then reverted: `identity.trackDegradationFlag` was already in `WRITABLE_PATHS` and validated inline by `setField()` (confirmed by an existing, passing test in `efsp-fdr-store.test.mjs`) — a second, parallel setter would have created exactly the "two paths to the same field" situation this codebase's `airspace-owner`/`setBeaconAssigned` precedent deliberately avoids elsewhere. The actual gap was the missing Block Map entry, not a missing setter.

## Consequences

- `docs/adr/0020`'s scope cut is narrowed, not overturned: `TACTICAL`/MRU Positions, `TOFI`, and the D12 refusal audit remain fully deferred and structurally inapplicable (no MRU Position exists). Only the civil `APP↔CTR` DEPARTURE direction is added.
- `ForwardingObligationMonitor.recordMet()` remains dead code (zero callers) — still correctly documented as a deferred gap in `docs/adr/0021`, not addressed here.
- The `coordination.state` enum's `'CLOSED'` value remains unused (an `ACTIVE` link never transitions further) — noted, not fixed; no acceptance criterion depends on it.
- `crc-sync/tests/efsp-board-store-coordination.test.mjs`, `efsp-facility-config.test.mjs`, and `fdr-store.test.mjs` gained coverage for all four changes above. `crc-desktop`'s coordination-table drift test was extended to also assert `COORDINATION_ELIGIBLE_STATES` matches between client and server.
