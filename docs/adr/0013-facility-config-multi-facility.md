# 0013 — A second Facility (`CENTER`/`CTR`) added; the EFSP backend becomes N Facility-scoped `{BoardStore, PositionStore}` pairs sharing one `FdrStore`

## Context

WP4A (`docs/efsp-wp4a-briefing.md`, confirmed by the project owner as the next work package per the guide's own build-order note, §16: *"WP4A must not slip... every other work package assumes both"*) requires inter-Facility coordination. The user confirmed the briefing's recommended scope cut: civil ATC↔ATC only — a new `CENTER` Facility (Ankara Center) with a `CTR` Position, coordinating with the existing `APP` Position. `TOFI` and the `TACTICAL` Facility/MRU Positions are deferred (see `docs/adr/0020`).

Direct code inspection at the start of this work confirmed the entire EFSP backend was single-Facility with zero Facility-scoping anywhere: one module-level `facility-config.js` singleton loaded from one JSON file; one `BoardStore` instance (`this._strips = new Map()`, no `facilityId` field on `Strip` at all); one `PositionStore`; one fixed `ctx = {boardStore, fdrStore, positionStore, facilityConfig}` threaded through `efsp-ws.js`. Adding a second Facility is not a parameterization of this — it is new machinery.

## Decision

**1. `facility-config.js` becomes a `Map` of Facility configs, keyed by `facilityId`, loaded from two files.** Every exported function (`getPositionSet`, `getCoveringChain`, `getBaysFor`, `getAllBays`, `bayImpliesState`, `bayForImpliedState`, `getFacilityConfig`, `setFacilityConfig`) gains an **optional trailing `facilityId` parameter defaulting to `DEFAULT_FACILITY_ID` (`'INCIRLIK'`)**. Every zero-arg call site that predates this ADR — `index.js`'s original wiring, every existing test — keeps compiling and behaving identically; `getPositionSet('CENTER')` is the only new call shape. New `getFacilityIds()` returns `['INCIRLIK', 'CENTER']`, used by `index.js` to iterate generically rather than hard-coding a Facility count. `CENTER`'s config is new, `[SOURCE-DEFINED]` (the guide gives no published Bay set for CTR): one Position (`CTR`), no covering chain (mirrors `OPS`'s "absent from the chain" precedent), one `ctr-enroute` Bay implying `INBOUND`, one `ctr-app-coordination` Bay.

**2. `index.js`'s composition root now builds one `{BoardStore, PositionStore, rules}` pair per Facility**, not exactly one of each — `createEfsp()` iterates `facilityConfig.getFacilityIds()`. A single `FdrStore`/`CodeAllocator`/`MutationLog` stay shared across every Facility (see `docs/adr/0015` for why). `ctx` keeps `boardStore`/`positionStore` as direct properties aliased to `INCIRLIK` purely for pre-WP4A caller/test back-compat; `boardStoreFor(facilityId)`/`positionStoreFor(facilityId)` are the real, general accessors.

**3. `efsp-ws.js`'s wire messages (`efsp-mutation`, `efsp-resync`, `efsp-set-positions`) gain an OPTIONAL `facilityId` field, defaulting to `INCIRLIK`** — this is a deliberate departure from the plan drafted before implementation began (which proposed a *required* field with no wire back-compat, reasoning that crc-sync/crc-desktop deploy together so back-compat wasn't needed). During implementation, making it optional-with-default turned out to cost nothing (one extra `|| DEFAULT_FACILITY_ID` per handler) while leaving the entire existing single-Facility test suite (`efsp-ws.test.mjs`, `efsp-index.test.mjs`, ~30 test cases) passing completely unmodified — the same back-compat philosophy as point 1, applied consistently at the wire layer instead of stopping at the config layer. `_snapshotMessage` sends **both** Facilities' strips/fdrs/positions/bays in one message (each record stamped `facilityId`), since one client can now hold Positions and act across both.

**4. The covering chain is NOT extended from `APP` to `CTR`.** `INCIRLIK`'s `coveringChain` stays exactly `{CD:'GND', GND:'TWR', TWR:'APP'}` — unchanged from before this ADR. The covering chain (guide §4.5 rule 3, §4.8.6) is an *intrafacility* occupancy-fallback mechanism ("route to the covering Position within this Facility"); the cross-Facility `HANDOFF` primitive (§4.6) has its own PROPOSE/ACCEPT protocol and is a categorically different mechanism. Conflating them — which an earlier draft of this change briefly did, before being caught and reverted during implementation — would have silently and incorrectly routed an unoccupied-`APP` transfer to `CTR`, a different Facility's `PositionStore`, where `CTR` would always read as unoccupied (it isn't tracked in `INCIRLIK`'s `PositionStore` at all) and the fallback would just silently fail closed rather than doing anything coherent.

## Alternatives considered

- **A single shared `BoardStore` with a `facilityId` column on each Strip**, rather than N instances. Rejected: the guide itself settles this directly (§4.8.5): *"Holding CTR and TAC_C2 does not collapse the CENTER and TACTICAL Facilities into one... The controller works two Boards; the Boards remain two."* Concretely, `board-store.js`'s `_dispatch()`, occupancy gating, and `_applyTransferStrip`'s covering-chain fallback are all written assuming "the Board" == "one Facility's Position set" — parameterizing all of that with a Facility dimension would touch every one of the 9 pre-existing op kinds, when none of them need to know about a second Facility at all. Separate instances confine every new cross-Facility concept to the 5 new coordination op kinds (`docs/adr/0015`) and — critically — make independent Strip-replica removability (a WP4A acceptance criterion) fall out of instance separation *by construction*, rather than needing an explicit guard.
- **A required `facilityId` on every wire message, no back-compat.** Rejected during implementation for the reason in point 3 above — it was the original plan, but proved to cost real test-suite breakage for zero benefit once the optional-default pattern was already established at the config layer.

## Consequences

- `efsp-facility-config.test.mjs` gained coverage for `CENTER`, `getFacilityIds()`, and the "every zero-arg call site keeps behaving identically" back-compat guarantee explicitly.
- A test that mutates `CENTER`'s config via `setFacilityConfig(..., 'CENTER')` must override `CRCSYNC_EFSP_FACILITY_CONFIG_PATH_CENTER` before importing, exactly as the existing `CRCSYNC_EFSP_FACILITY_CONFIG_PATH` convention requires for `INCIRLIK` — omitting this was caught during this work (a test wrote to the real, committed `config/efsp-facility-center.json` before the fix; the file self-healed via the test's own restore step, but the isolation gap was real and is now fixed).
- `Strip` objects still carry no `facilityId` field internally (each Facility's `BoardStore._strips` Map is implicitly scoped by which instance holds it) — `facilityId` is stamped onto a Strip record only at the WS boundary (`efsp-ws.js`), for the client's benefit. Any future direct `BoardStore` consumer inside `crc-sync` must track which Facility's instance it's holding by other means (closures, as `index.js`/every test fixture in this codebase now do).
- A client's resync (`efsp-resync`) requesting a within-window delta only ever refreshes ONE Facility's data; a full snapshot (the common case for any real reconnect gap) always covers both. A resync landing in the rare short-gap delta window for one Facility while the other has also changed very recently is a known, minor, accepted gap — not exercised by this session's tests.
