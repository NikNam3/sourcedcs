# 0021 — Timed forwarding obligations get new periodic-scan machinery, a new WS broadcast type, and unpersisted compliance counters

## Context

Guide §4.6.1: 15-minute advance forwarding, >3-minute ETA-revision re-forwarding, verbal-plus-automated coordination inside 30 minutes of proposed departure, and 3-minute post-transfer verification for a data-only receiving facility — *"exactly the obligations a paper strip cannot track and an electronic panel can. Implement each as a countdown with an alert, and instrument compliance."* No timer or alert machinery of any kind existed anywhere in `crc-sync`'s EFSP subsystem before this work — confirmed by exhaustive grep at the start of this session. `nla.js`'s own `isVoidExpired()` comment (*"alerting on this is a periodic job elsewhere"*) was aspirational, describing a job that had never actually been built.

## Decision

**Pure logic, then a stateful scanner** — the same two-layer shape `nla.js` already establishes. A new module, `forwarding-obligations.js`, exports `computeDueObligations(strip, fdr, now, ctx)`, a pure function returning due obligations given a Strip/FDR/clock/context, and `ForwardingObligationMonitor`, a stateful class that ticks over every Strip across every Facility.

Concrete mappings, each a deliberate simplification recorded here rather than silently:
- **`ADVANCE_FORWARDING`** — fires 15 minutes before `fdr.filed.estimatedArrivalTimeUtc`, only while the Strip has no coordination link at all (`strip.coordination` absent) — i.e. genuinely unforwarded. Escalates from `WARNING` to `OVERDUE` once the ETA itself passes with still no link.
- **`ETA_REVISION`** — fires when the current ETA has drifted more than 3 minutes from `strip.coordination.lastForwardedEtaUtc` (a field stamped by `docs/adr/0015`'s coordination methods), on an open (`PROPOSED`/`ACTIVE`) link.
- **`AMENDMENT_INSIDE_30MIN`** — **[simplified]**: "just amended" is approximated as `fdr.updatedAt` being within the last 60 seconds, since no separate amendment-event feed exists to check against instead. A real amendment-event stream is future work, not built this session.
- **`DATA_ONLY_VERIFICATION`** — gated on a new per-Facility `dataOnly: boolean` config flag (`facility-config.js`). Neither `INCIRLIK` nor `CENTER` sets this `true` — both have a real controller interface — so this branch is exercised only by a synthetic test fixture. **[documented gap]**: no "verification" action exists this slice, so once due, this obligation stays raised indefinitely rather than being cleared by a controller action; a future work package adding a real verification Mutation should clear it there.

**Delivery**: a new `ForwardingObligationMonitor`, constructed once in `server.js` and ticked via a **separate** `setInterval` (15 seconds) placed after the existing stale-track-reaper's own interval — deliberately not sharing that reaper's 5-second cadence, since it's an unrelated subsystem with no reason to couple timing. Each newly-due obligation is de-duplicated (`stripId:obligationType`, alerted at most once) and pushed through a new `ws-hub.js` method, `broadcastEfspObligationAlert`, mirroring the existing `broadcastRadarLocks` — unconditional to every connected client, no per-client filtering (matching every other EFSP broadcast type in this codebase). A new WS message type, `efsp-obligation-alert`, since none of the four existing EFSP message types fit.

**Compliance instrumentation** (§11.5, "measured acceptance, not asserted") is an in-memory `{obligationType: {met, missed}}` counter, incremented on `missed` automatically (every raised alert) and exposing a `recordMet()` hook for a future caller to increment on `met` — **not wired automatically this slice**, since no dispatch-level signal yet distinguishes "this coordination Mutation resolved a pending obligation" from "the controller was just doing their job anyway." This mirrors `efsp-panel.js`'s existing `_searchInvocationCount` precedent exactly: a minimal, documented, unpersisted instrumentation hook, not a real dashboard — reset on every server restart, same as that client-side counter is reset on every page reload.

## Alternatives considered

- **Reuse the existing 5-second stale-track-reaper interval** rather than a new one. Rejected: coupling an unrelated subsystem's cadence to a track-eviction timer is a maintenance hazard for no benefit — 15 seconds is comfortably fine-grained for minute-scale obligations regardless, and decoupling means either can change frequency independently later without touching the other.
- **Build a real amendment-event feed now**, so `AMENDMENT_INSIDE_30MIN` doesn't need the `updatedAt`-recency approximation. Rejected as disproportionate to this slice: it would require `fdr-store.js`'s `setField()` to distinguish "this write is materially an amendment" from every other write, a genuinely new concept with no other consumer yet.
- **Auto-wire `recordMet()` from every successful coordination Mutation**, treating any post-alert coordination action as compliance. Rejected: this would overstate compliance — a controller proposing `TRAFFIC` doesn't necessarily satisfy an outstanding `ADVANCE_FORWARDING` obligation on the same Strip, and getting this wrong silently corrupts the one metric §11.5 exists to make honest.

## Consequences

- `efsp-forwarding-obligations.test.mjs` covers all four obligation types' boundaries directly (pure-function tier), plus the monitor's de-duplication, DROPPED-Strip skipping, and compliance-counter behavior (stateful tier) — 21 tests, no real timers used anywhere (clock is always passed explicitly, same discipline as `nla.js`'s `isVoidExpired`).
- The client (`efsp-state.js`'s `applyEfspObligationAlert`/`getEfspObligation`, `bay-view.js`'s rendering, `efsp-panel.css`'s new third alert tier — deliberately not reusing the existing error-red or warning-amber, since a due-but-not-missed obligation is a different signal from either) has no way to *dismiss* an obligation badge once raised — it clears only when the Strip itself is dropped and re-rendered, or a future server-side "resolved" broadcast is added. This is consistent with the server-side "stays raised" gap noted above.
- `docs/adr/0013`'s shared-`FdrStore` simplification is what makes `ADVANCE_FORWARDING`/`ETA_REVISION` meaningful as *compliance* instrumentation rather than *data-consistency* instrumentation — the ETA itself is never actually stale across the boundary (both Facilities read the same object), only the **procedural act of telling the other Facility's controller** can be late, which is exactly what these two obligations measure.
