# 0014 — ARRIVAL Strips now originate at `CTR` and reach `APP` via the real cross-Facility `HANDOFF`, superseding ADR 0008's local self-creation stub

## Context

ADR 0008 (Phase 2) gave `APP` a local `CreateStrip` right for `role: 'ARRIVAL'`, explicitly labelled as a stub: *"the seam WP4A's real HANDOFF will eventually replace... an inbound flight will then originate its Strip from a forwarded cross-Facility exchange, not a local CreateStrip."* `docs/adr/0013` adds the `CENTER` Facility and `CTR` Position this stub was waiting on. `docs/adr/0015` adds the real `HANDOFF` primitive. This ADR is the seam actually closing.

## Decision

1. **`CTR` gets `CreateStrip` for `role: 'ARRIVAL'`** (`permission.js`'s `CREATE_ROLE_PERMISSIONS.CTR = new Set(['ARRIVAL'])`) — the same "no Facility further upstream is built yet" terminus-stub shape `APP`'s entry used to have, since `CENTER` has no third Facility upstream of it this slice. `CTR` also needs the coarse `CreateStrip` op-kind gate, so `PERMISSIONS.CTR` includes the full `OP_KINDS` set (mirroring `APP`'s own entry).
2. **`APP`'s `CREATE_ROLE_PERMISSIONS` entry is narrowed to an empty set** (`CREATE_ROLE_PERMISSIONS.APP = new Set([])`) — not removed entirely, so the existing "every CreateStrip-eligible Position has a CREATE_ROLE_PERMISSIONS entry, even if empty" invariant test still finds one, and so the change reads as an intentional narrowing rather than a deletion. This is exactly what ADR 0008's own "Consequences" section asked for: *"an intentional, reviewed permission-table change... not a silent regression."*
3. **`nla.js`'s `computeArrivalNla`'s `INBOUND` case becomes Facility-aware.** A CENTER-held `INBOUND` Strip's real next action is the cross-Facility `HANDOFF` (a genuinely different mechanism, guide §4.6), fired via the client's new Coordinate button — not the ordinary intrafacility `transferTo: 'TWR'` path, which assumes a `TWR` Position that doesn't exist inside `CENTER`'s own `PositionStore` at all. `computeNla`'s injected `ctx` gains an optional `facilityId` field (threaded from `board-store.js`'s `_nlaCtx()`, itself reading `this._rules.facilityId`); when `ctx.facilityId === 'CENTER'`, `INBOUND` returns `{inhibited: 'cross-Facility HANDOFF required — use Coordinate'}` instead of attempting the TWR-occupancy check. Every pre-WP4A caller that never sets `ctx.facilityId` is unaffected — the check only fires for the new value.
4. **`permission.js`'s `ARRIVAL_STATE_OWNERS.INBOUND` gains `CTR`** (`['APP', 'CTR']`) — a CENTER-held `INBOUND` Strip's owning Position needs to be authorized to act on it too (per-State authority, ADR 0010), even though "acting on it" now means proposing a `HANDOFF` rather than an ordinary NLA transfer. Mirrored client-side in `efsp-nla.js`'s `ARRIVAL_STATE_OWNERS`, verified byte-identical by the existing drift-guard test.
5. **The client no longer renders the ordinary NLA button for a CENTER-facility `INBOUND` Strip at all** (`bay-view.js`'s `isCenterInbound` check) — since it's known client-side that this state's NLA is always inhibited, rendering an always-failing enabled button would be worse than not rendering one; the Coordinate button (ADR 0015) is the real affordance.

## Alternatives considered

- **Leave `APP`'s local self-creation stub in place alongside the new `HANDOFF` mechanism**, letting both coexist. Rejected: this would leave two structurally different ways for an `ARRIVAL` Strip to appear at `APP` — one honest (a real cross-Facility exchange) and one fake (self-origination pretending nothing crossed a boundary) — exactly the "looks correct in every demo, wrong under scrutiny" trap the guide warns about elsewhere for D21. ADR 0008 itself named this as the intended migration point; there is no reason to defer it further now that the real mechanism exists.
- **Give `computeArrivalNla`'s `INBOUND` case a generic `inhibited: 'no receiving Position present'` message** (reusing the existing wording) instead of a Facility-aware branch with new text. Rejected: it would satisfy WP4's "every State has exactly one NLA or a rendered inhibit reason" acceptance criterion technically, but the message would be actively misleading — the real reason isn't "TWR isn't occupied," it's "you're in the wrong Facility for this transition at all, use Coordinate instead." Guide §3.5 rule 2 requires the inhibit reason be attributable to a *named condition*, not merely present.

## Consequences

- `efsp-permission.test.mjs` gained explicit coverage: `canCreateStripRole('APP', 'ARRIVAL')` is now `false`; `canCreateStripRole('CTR', 'ARRIVAL')` is `true`; the D21 regression pairing that used to contrast `OPS`/`APP` now contrasts `OPS`/`CTR` (the same shape-of-guard test, updated to the Position that actually carries the asymmetry now).
- `efsp-nla.test.mjs` gained coverage for the `ctx.facilityId === 'CENTER'` branch and confirmation that every caller omitting `facilityId` is unaffected.
- A CTR-originated Strip that is never handed off (no `HANDOFF` proposed) simply sits, permanently inhibited, in `ctr-enroute` — this is correct (nothing forces a controller to act), and is exactly the condition `docs/adr/0021`'s `ADVANCE_FORWARDING` obligation alert exists to surface after 15 minutes of inaction.
- `DEPARTURE`'s `DEPARTED` case in `nla.js` is explicitly **not** touched by this ADR — see `docs/adr/0016`.
