# 0025 — `positionClass`, the `TACTICAL` Facility, MRU Positions, and TOFI

## Context

`docs/adr/0020` deliberately deferred the remainder of WP4A — `TOFI` (guide §4.6.3), the `TACTICAL` Facility, MRU Positions (`TAC_C2`, `AIC`, `GCI`, `JTAC`), the three-field separation model, and defect D12's MRU-refusal audit — into "the next work package," and named the exact mechanism that work should introduce in its own Consequences section:

> "A future work package building `TOFI`/`TACTICAL`/MRU Positions should introduce a `positionClass` concept (e.g. `MILITARY_ATC`/`MRU`/`CIVIL_ATC`) in `facility-config.js`'s Position definitions and gate the 5 coordination op kinds on it in `permission.js`, rather than the current flat per-Position-ID `PERMISSIONS` table."

That ADR also explained why the concept wasn't built preemptively: "a permission table gated on a class with only one real value proves nothing about correct per-class evaluation... The concept is better introduced alongside the first real Position that needs it (`TAC_C2`), where a genuine positive/negative test pair becomes possible." That first real Position now exists. This ADR is that work package.

The guide's own §13 acceptance criteria for WP4A name three things this session closes: `TOFI` and the three-field separation model as deliverables, and — as the work package's own named acceptance test (§13, line 1294) — *"A `HANDOFF` attempted on a `TAC_C2`-owned Strip is refused, even though the same controller holds `CTR`."*

## Decision

**`positionClass`.** `facility-config.js`'s Position definitions gain a `positionClasses: { [positionId]: classString }` map per Facility, additive alongside the existing bare-string `positions` array (not replacing its shape — every existing `getPositionSet()` caller keeps working unmodified). A new `getPositionClass(positionId)` accessor searches every known Facility's own map (Position IDs remain globally unique across Facilities, the same assumption `permission.js`'s flat `PERMISSIONS` table already relied on). Classes assigned this slice: `MILITARY_ATC` (`CD`/`GND`/`TWR`/`APP`), `BASOPS` (`OPS`), `CIVIL_ATC` (`CTR`), `MRU` (`TAC_C2`/`GCI`), `MRU_POSITION` (`AIC` — the guide's own Class column distinguishes `AIC`'s "MRU position" from `TAC_C2`/`GCI`'s "MRU"), `NON_ATC` (`JTAC`).

`permission.js` requires `facility-config.js` directly and layers a structural guard on top of its hand-authored `PERMISSIONS` table: after construction, a loop strips every `COORDINATION_OP_KINDS` entry from any Position whose class is `MRU`/`MRU_POSITION`/`NON_ATC`, regardless of what that Position's table entry was built with. This makes D12 true *by construction*, not merely by careful authoring — the exact "future-proof, not implicit" property ADR 0020 asked for, since a future MRU Position automatically inherits the refusal with no new line in `PERMISSIONS` needed. `canMutate(actingPositionId, opKind)`'s two-argument, D21-proof signature is unchanged.

**The `TACTICAL` Facility.** A third `DEFAULT_TACTICAL_CONFIG`, added the same way `CENTER` was (ADR 0013) — its own env var (`CRCSYNC_EFSP_FACILITY_CONFIG_PATH_TACTICAL`), added to `DEFAULT_CONFIGS`, picked up by `index.js`'s `getFacilityIds()` loop with zero changes to `index.js` or `board-store.js` (both already iterate generically and inject `rules.peerBoard(facilityId)` per Facility). Positions: `TAC_C2`, `AIC`, `GCI`, `JTAC`, with Bays following guide §4.2's own table (`Tasked · Airborne · On Station · Tanker · Coordination` for `TAC_C2`; `On Station · Committed · Coordination` for `AIC`/`GCI`; a single read-only viewing Bay for `JTAC`). `AIC`/`GCI` → `TAC_C2` is a legal intrafacility covering-chain entry; `TAC_C2` → `CTR` is deliberately **not** added, for the identical reason ADR 0013 point 4 rejected extending `APP` → `CTR` the same way — `position-store.js`'s `coveringPositionFor()` is structurally scoped to one Facility's own `PositionStore` instance, so a chain entry can never resolve across a Facility boundary. An unoccupied `TAC_C2` with no successor is an accepted "warn the controller, route nowhere" stranding case (guide §4.8.6 rule 5), not a silent gap.

**`MISSION`, minimal scope.** See `docs/adr/0026` for the dedicated scope-cut reasoning; in brief, `TAC_C2`/`GCI` originate `MISSION` Strips (`CREATE_ROLE_PERMISSIONS`), own their entire guide-specified 6-state lifecycle (`TASKED → AIRBORNE → ON_STATION → OFF_STATION → RTB → DROPPED`, guide line 215) solo, and `AIC`/`JTAC` are deliberately absent from ownership — `JTAC`'s absence alone is what makes it read-only ("MISSION (read-only)," guide §4.1), no separate mechanism.

**TOFI.** A genuinely different sub-protocol from the 5 ATC↔ATC primitives, not a 6th row in `coordination.js`'s `COORDINATION_EFFECTS` table — jurisdiction (data ownership, separation responsibility) never transfers in TOFI at all (guide rule 2: "the Strip stays live and posted throughout tactical control"), so there's nothing analogous to `dataOwnerPositionRef`/`separationResponsibilityRef` to move. Concretely, `board-store.js` gains:

- A `strip.tofiCoordination` record, symmetric on both sides of an exchange (`peerFacilityId`/`peerStripId`/`peerPositionId`, mirroring `strip.coordination`'s own naming), kept structurally separate from `strip.coordination` so the two sub-protocols' "already has an open link" guards never fight each other.
- **`PROPOSE` always originates on the ATC-side Strip; `ACCEPT`/`REJECT`/`TRANSFER_COMMS` always land on the MISSION-side Strip** — the receiving MRU controller's own record, for both `ENTRY` and `EXIT`. This mirrors exactly which side acts in the real-world exchange and let two new peer-callback methods (`receiveTofiProposal`, `receiveTofiResponse`) stay simple, single-direction functions rather than needing to branch on which side called them.
- **`ENTRY`'s `PROPOSE` mints a genuine `MISSION` Strip** on the target MRU Facility's own Board via `receiveTofiProposal` — reusing D13's proven replica-minting mechanism (`crypto.randomUUID()`, landing in the receiving Position's Coordination Bay) but **sharing the ATC-side Strip's own `fdrId`** instead of generating a fresh one. This realizes guide §9.8's "bind it to the same FDR as any tower Strip for that flight" now, rather than deferring it to WP7 — and it costs nothing new mechanically, since every one of the 5 existing primitives' replicas *already* share the sender's `fdrId`; TOFI is simply the first primitive to bind two **different** Strip Roles (the ATC-side role, and `MISSION`) to one shared FDR instead of mirroring the same role on both sides.
- **`EXIT`'s `PROPOSE` re-enters the SAME already-existing link** (`receiveTofiExitProposal`) rather than minting anything — the mission has been live in `TACTICAL`'s own Board throughout `ENTRY`'s `ACTIVE` window. This is the one place the 5 primitives' one-shot "already has an open link, ever" guard genuinely doesn't apply to TOFI: `PROPOSE`'s guard only rejects a currently-`PROPOSED` link, deliberately allowing a fresh proposal once a prior exchange reached `COMPLETE`.
- **Rule 3 (exit is the safety-critical direction) is a hard precondition on `ACCEPT`, never a derived side effect.** `EXIT`'s `ACCEPT` checks `fdr.tofi.separationRegime === 'ATC'` and refuses otherwise — the controller must make the explicit Block edit first, then accept. Auto-deriving it from `ACCEPT` would violate "MUST NOT be derived" the same way deriving it from airspace type would.
- **A distinct `TRANSFER_COMMS` action**, invocable on either side of an accepted exchange, never folded into `ACCEPT`'s effect the way `commsTransfers` is for the 5 primitives — guide §4.6.3's own text: "followed by a **separate** transfer of communications."
- **`DropStrip` is rejected outright (not a soft warn) while `tofiCoordination.state === 'ACTIVE'`**, on either side — guide rule 2's "dropping the Strip breaks all three [separation-model fields]" is a data-integrity fact, not a coordination nicety like the verbal-path soft interlocks elsewhere in §4.6.
- **The guide §4.6 rule 5 track-degradation interlock applies to TOFI too**, both directions — TOFI sits in the same primitive table that rule sits directly under; a degraded track (`CST`/`FAIL`/`IF`/`NT`/`TRK`) requires a non-empty `note` on `PROPOSE`, identical to the existing 5 primitives (ADR 0019).
- **`TOFI_OP_KINDS = ['TOFI']`**, granted only to `CTR`, `TAC_C2`, `GCI` — **not** `APP` (excluded even though `APP` otherwise gets the full `OP_KINDS` set: guide §4.1's own Position table lists `TOFI` only for `CTR` among the built ATC Positions) and **not** `AIC` ("works under `TAC_C2`'s TOFI," per the guide — acts on `MISSION` Strips only after `TAC_C2` has already completed an exchange, never independently).
- **`TOFI_COUNTERPARTS`**, a small static table (`permission.js`, mirrored client-side in `bay-view.js`) resolving which Position(s) are valid TOFI targets for a given acting Position — `CTR` has two candidates (`TAC_C2`, `GCI`), so the client renders a genuine target picker rather than the deterministic 1:1 stub `COORDINATION_TARGETS` still uses for the 5 ATC↔ATC primitives; `TAC_C2`/`GCI` each have exactly one candidate (`CTR`) and skip the picker.

## Alternatives considered

- **Extending `coveringChain` cross-Facility** (`TAC_C2` → `CTR`) to literally match the guide's own §4.8.6 chain notation. Rejected for the identical reason ADR 0013 already rejected `APP` → `CTR`: `coveringPositionFor()` is structurally one-Facility-scoped, and an earlier draft of that ADR's own change briefly tried the cross-Facility extension before being caught and reverted. Repeating that mistake here would silently route an unoccupied-`TAC_C2` transfer to `CTR`'s `PositionStore`, where `TAC_C2` is never tracked at all.
- **`AIC` holding an independent TOFI grant** (e.g. as a covering-chain-style delegate when `TAC_C2` is unoccupied). Rejected: the guide's own Class column distinguishes `AIC` ("MRU position") from `TAC_C2`/`GCI` ("MRU"), and its Primitives column reads "works under `TAC_C2`'s TOFI" rather than listing TOFI itself. A delegate grant would also need its own D12/D21 test row identical to `TAC_C2`'s, for a scenario the guide doesn't actually describe.
- **TOFI acting purely by reference, with no MISSION-side Strip minted at all.** Rejected: guide §9.8 and the Position table both name `MISSION` as `TAC_C2`/`GCI`'s Strip Role, and a Bay Map needs a real Role to exist. Reusing D13's replica-minting mechanism (with a shared `fdrId` instead of a fresh one) was simpler than inventing a new "act by reference" pathway, and required no new Board-level machinery beyond the two new peer-callback methods.
- **A 4th boolean axis on `COORDINATION_EFFECTS`** to fold TOFI into the existing 5-primitive table. Rejected: TOFI's defining property (jurisdiction never transfers) has no analogue in that table's axes at all, and forcing it in would make the table's meaning — "how does ACCEPT move jurisdiction" — read as if TOFI has an answer to a question it structurally doesn't.

## Consequences

- D12, D21 and D20 now have genuine positive-and-negative test pairs (`efsp-permission.test.mjs`, `efsp-tofi.test.mjs`) rather than the single-value-class situation ADR 0020 explicitly flagged as proving nothing.
- Rule 5 ("`DUE_REGARD`/`MARSA` mutually exclusive," §4.6.3) is resolved by construction — `separation_regime` is one 5-value enum field, not two independent booleans — so no cross-field validation code exists; see `docs/adr/0026` and `fdr-store.js`'s `setTofi()` for the full separation-model design.
- `bay-view.js`'s `COORDINATION_TARGETS` comment, which named this exact gap ("D12 will extend once one does"), is now closed: `TAC_C2`/`AIC`/`GCI`/`JTAC` structurally never appear as its keys, so no `HANDOFF`/`POINT_OUT`/`TRAFFIC`/`OPERATIONAL_REQUEST`/`AIT` button can ever render for them — TOFI's own button is the only coordination-shaped affordance any of the 4 Positions get, and it is structurally incapable of dispatching one of the 5 forbidden primitives (it only ever sends `kind: 'TOFI'`).
- A future Facility whose Position-ID space collides with an existing one (breaking the "globally unique across Facilities" assumption both `PERMISSIONS` and `getPositionClass()` rely on) needs its own ADR before landing — this is unchanged from the pre-existing caveat in `permission.js`'s header comment, just now shared by two lookups instead of one.
