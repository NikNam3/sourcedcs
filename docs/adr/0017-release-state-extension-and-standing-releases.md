# 0017 — `EDCT`/`CALL_FOR_RELEASE` extend the existing release-state model; standing-release envelopes are new facility-config data with an `OPERATIONAL_REQUEST` fallback

## Context

Guide §3.8 (Phase 2, already built) models four departure release states — `RELEASED`, `HOLD_FOR_RELEASE`, `RELEASE_TIME`, `CLEARANCE_VOID_TIME` — with a derived 30-minute void deadline, fully implemented in `fdr-store.js`'s `RELEASE_STATES`/`voidDeadlineUtc` and wired into `nla.js`'s `HELD`/`CLEARED` inhibit logic. Guide §4.6.2 ("Departure release across the boundary") extends this: *"Five states, per §3.8 plus [Coord §2.7]: RELEASED · HOLD_FOR_RELEASE · RELEASE_TIME · EDCT (±5 min) · CALL_FOR_RELEASE (−2/+1 min)."* — a superset, plus a standing-release envelope concept with an explicit fallback: *"anything outside the envelope falls back to a per-flight OPERATIONAL_REQUEST."*

## Decision

**`EDCT`/`CALL_FOR_RELEASE`** are added to `fdr-store.js`'s `RELEASE_STATES` set. Two new writable FDR fields (`assigned.edctTimeUtc`, `assigned.callForReleaseTimeUtc`) each derive a window on write — `edctWindowStartUtc`/`EndUtc` at ±5 minutes, `callForReleaseWindowStartUtc`/`EndUtc` at −2/+1 minutes — using the exact same derive-on-write pattern `voidDeadlineUtc` already established (recomputed whenever either the release state or the relevant time field is written; cleared to `null` whenever the release state moves away). New Block-Map entries `14B`/`14C` (FDR-routed, `required: false`) mirror `docs/adr/0008`'s `9A-*` sub-field precedent — independently omittable per facility with no new validator logic needed.

**Standing releases** are new per-Facility config data (`facility-config.js`'s `standingReleases: []`, living on `APP`'s/`INCIRLIK`'s config — the guide's own wording: *"the agreement normally converts the per-flight call into a standing release... granted BY the delegating/center facility TO the approach facility"*). A new pure module, `release-envelope.js`, exports `matchesStandingRelease(fdr, standingReleases)` — matches on `stereoRoute` (exact) and/or `atOrBelowAltitude` (ceiling), `active: false` never matches, and a `radiusNm`-only envelope never matches (no coordinate data exists to check it against — WP5 track correlation isn't built). An envelope with no criteria at all matches nothing, not everything — a configuration mistake shouldn't silently waive every hold.

**The `OPERATIONAL_REQUEST` fallback** is wired into `nla.js`'s `HELD` case: when `releaseState === 'HOLD_FOR_RELEASE'` and the FDR does not match any configured standing release, `HELD`'s NLA is inhibited with `'outside standing release envelope — file OPERATIONAL_REQUEST'`, pointing the controller directly at the new coordination primitive (`docs/adr/0015`). Only `HOLD_FOR_RELEASE` triggers this — `RELEASE_TIME`/`EDCT`/`CALL_FOR_RELEASE` already have their own time-based gates, and `RELEASED` has none. `computeNla`'s `ctx` gains `standingReleases` (defaulting to `[]`), threaded the same way `facilityId` (`docs/adr/0014`) is — every pre-WP4A caller that never sets it keeps the exact prior behavior (always inhibited for `HOLD_FOR_RELEASE`, since an empty envelope list never matches).

## Alternatives considered

- **Model `EDCT`/`CALL_FOR_RELEASE` as their own independent boolean flags rather than `RELEASE_STATES` members.** Rejected: the existing model already treats release state as one mutually-exclusive value (a flight is `RELEASED` XOR `HOLD_FOR_RELEASE` XOR ...); §4.6.2 explicitly lists these as two more members of the same set, not an orthogonal dimension, and reusing the existing `assigned.releaseState`/inhibit-wiring pattern (`nla.js`'s `CLEARED`/`HELD` cases already switch on it) is far less code than a parallel model.
- **A generic "outside envelope" boolean on the FDR, computed once and cached**, rather than a pure predicate evaluated at `computeNla` time. Rejected: an envelope's membership can change as either the FDR (route/altitude amendment) or the facility config (an envelope activated/deactivated) changes — caching it risks exactly the kind of stale-derived-value bug `docs/adr/0011` had to fix elsewhere. `matchesStandingRelease` is cheap and pure; there's no correctness reason to cache it.

## Consequences

- `efsp-fdr-store.test.mjs` gained coverage for both windows' derivation, including the "switching release state away clears the window even though the time field itself is untouched" case (mirroring `voidDeadlineUtc`'s existing test shape).
- `efsp-release-envelope.test.mjs` covers `matchesStandingRelease`'s matching rules directly; `efsp-nla.test.mjs` covers the `HELD`/`HOLD_FOR_RELEASE` inhibit wiring, including the "every pre-WP4A caller is unaffected" back-compat case.
- `strip-template.js` (crc-desktop) mirrors `14B`/`14C` — verified by the existing `efsp-block-map-parity.test.js`, which does not require `14B`/`14C` to be `fdr`-routed identically in *content* beyond `required`/writability/path/provenance (its own documented scope).
- The client has no dedicated EDCT/CALL_FOR_RELEASE input UI this slice — these fields are reachable only via the generic Block-editing path (`SetBlock` on `14B`/`14C`), same as most optional Blocks. A dedicated release-state control panel is a natural follow-on, not required to demonstrate the model.
